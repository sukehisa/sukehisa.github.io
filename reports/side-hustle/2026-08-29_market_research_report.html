1. 調査の背景と市場の変曲点

前回（08-28）の総括で、次回の探索軸に条件をひとつ足すと書きました。 買い手が既に別の何かに金を払っている領域を優先する、という条件です。 3回連続で Tier 1 に届かず、点数を押し下げていたのが一貫して収益性の軸だったためです。 支払い習慣の有無は市場側の性質であり、こちらの工夫では作れません。

そこで今回は、「すでに毎月請求書が届いている場所」から探索を始めました。 AI APIの利用料、消費税、そしてリリースパイプラインの3つです。 いずれも支払いが既に発生しており、金額が変わる予定が確定しています。

第一に、AIのトークンが電力のように時間帯で値付けされ始めました。 DeepSeek は V4 系の公開に合わせて価格をピークとオフピークに分け、2026年8月16日16:00 UTC から適用しています。 ピーク帯は平日の 01:00–04:00 UTC と 06:00–10:00 UTC で、それ以外はすべてオフピークです（Codersera）。 値上げの幅は大きく、V4-Pro の出力はピークで100万トークンあたり $3.96、オフピークで $1.98 です（InfoWorld）。 改定前は $0.87 の一律だったため、時刻を選ばずに投げると4倍以上を払うことになります。

この変化は1社の値付けにとどまりません。 GitHub は2026年6月1日に Copilot の全プランを従量課金へ移しました（The GitHub Blog）。 供給が逼迫し、AIの費用が定額から変動へ移りつつあるという同じ流れの上に、DeepSeek の時間帯課金があります。

第二に、インボイス制度の2割特例が2026年9月30日で終わります。 2割特例は売上税額の2割を納税額とする経過措置で、これが消えると本則課税か簡易課税へ移ります。 後継として3割特例が新設されましたが、対象は個人事業者に限られ、2027年分と2028年分の申告だけです（TCNB）。 法人には後継措置がなく、緩衝なしで移行します。

第三に、npm の公開資格が段階的に失効していきます。 2026年7月31日から、2FAをバイパスする granular access token では権限まわりの操作ができなくなりました。 そして GitHub は次の段階の日付を明示しています。 原文は "2FA-bypass tokens will also lose direct publish." とし、"We are targeting January 2027 for this update." と書いています（GitHub Changelog）。

三者に共通するのは、請求書はすでに届いていて、その金額の決まり方だけが変わるという点です。 新しい支出を説得する必要がなく、既存の支出が増えるか減るかの話になります。 これは前回までの3案（広告収益が縮む層、母数の小さい実験者、無償代替のある一回きりの需要）と、買い手の性質が明確に違います。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: token-clock (時間帯レートを持つAIジョブの実行ゲート)

  • ターゲット: LLM APIに月数百ドル以上を払っていて、その一部がバッチ処理・夜間評価・埋め込み再生成・合成データ生成である小規模SaaSと個人開発者。とくに日本・シンガポール・インドなど、業務時間がピーク帯と重なるタイムゾーンの開発者。
  • 解決する課題: 価格が時刻の関数になったのに、コードは時刻を知らない。既存のLLMゲートウェイは「どのモデルへ流すか」「いくら使ったか」を扱うが、「いつ実行するか」を扱わない。結果として、待てる仕事が最も高い時間帯に流れる。

検知した生の声（一次ソース）

  • DeepSeek の変更を解説した開発者は、値付けの変化が比較の前提を壊したと書いています。原文は "Price comparisons are now time-dependent." です（DEV Community）。同じ記事は、既存の Spring AI 連携が価格を定数として書かれていたため、時間帯を扱う処理を自分で足す必要があったと述べています。既存のフレームワークが時間帯を前提にしていないことを、実装した当人が書いている点で価値の高い記述です。
  • 調査会社の Greyhound Research は、割引の受け取り手を「注意を払っている買い手」に限定して表現しています。原文は "The schedule's own clock and cache hand most of it back to any buyer paying attention." です（InfoWorld）。裏返せば、注意を払っていない買い手は値上げをそのまま被ります。
  • 割引の価値が地理に強く依存することも、数字で示されています。米国の太平洋・東部時間では 9–17 時のうちピーク帯は0%、シンガポール・北京では75%です（Codersera）。引用したピーク帯（01:00–04:00 UTC と 06:00–10:00 UTC）から機械的に計算すると、日本時間 9:00–18:00 の9時間のうち6時間がピーク帯に当たります。 日本の開発者は、何もしなければ業務時間の3分の2を高い側で払うことになります。
  • パターン判定: 新APIラッパー型（先行者利益） と マイクロDevExツール型 の複合。加えて、ピーク帯の定義がUTC固定であるため、タイムゾーンによる不利をそのまま需要にできる 地理アービトラージ の側面を持ちます。
  • Why Now: 時間帯課金の導入が13日前であり、既存のゲートウェイ・SDK・オーケストレータのいずれもレート表に時間軸を持っていません。値上げの体感が強い一方、対応策が「自分でcronを書く」以外に流通していない期間が、いま開いています。
  • コア機能 (MVP):
    • プロバイダ別・モデル別の時間帯レート表（UTC基準、夏時間の影響を受けない形式）をデータとして持つCLI/ライブラリ。
    • ジョブに「締切」と「遅延許容」を宣言させ、レート表とバッチAPIの選択肢を突き合わせて投入時刻を決める実行ゲート。
    • 実行後に「即時実行した場合との差額」を出す精算ログ。削減額が見えなければ課金の根拠が立たないため、これを中核に置く。

アイデア 2: shohizei-switch (2割特例終了後の申告方式の有利試算と届出期限の管理)

  • ターゲット: インボイス制度を機に課税事業者となった小規模事業者。とくに一人法人（法人成りしたフリーランス、マイクロ法人）と、顧問税理士を付けずに自分で申告している個人事業主。
  • 解決する課題: 2割特例が終わった後の選択肢は、個人と法人で違う。個人は3割特例・簡易課税・本則課税の3択、法人は簡易課税・本則課税の2択になる。どれが有利かは業種区分（みなし仕入率）と実際の仕入率で入れ替わり、しかも簡易課税は2年間の拘束を伴う。加えて、3割特例が2028年分で終わるため、判断は単年ではなく数年をまたいで比較しなければ答えが出ない。

検知した生の声（一次ソース）

  • 経過措置の改正内容は日付で確定しています。2割特例について、原文は「法人の2割特例は、2026年（令和8年）9月30日を含む課税期間をもって原則通り終了します」です。控除率も段階的に下がり、「〜2026年9月30日：80％控除」「2026年10月1日〜：70％控除（2年間）」と示されています（TCNB）。
  • 3割特例の対象は限定されています。「基準期間の課税売上高が1,000万円以下などの要件を満たす個人事業者」が対象で、「2027年（令和9年）分および2028年（令和10年）分の消費税申告」に適用されます（TCNB）。法人は対象外です。
  • 届出の期限は、誤ると1年を失う種類のものです。個人事業主が簡易課税を選ぶ場合、「2026年12月31日が提出期限となります」とされ、「期限を過ぎると翌年度まで簡易課税が利用できなくなるため、提出忘れのないよう注意しましょう」と書かれています（MONEYIZM）。
  • 一方で法人には救済の余地があります。「2割特例の適用を受けた法人は、特例の適用を受けた課税期間の翌課税期間に係る確定申告期限までに、簡易課税制度選択届出書を提出することができます」とされています（木下公認会計士税理士事務所）。期限の切迫度が個人と法人で異なるという、訴求を分けるべき事実です。
  • パターン判定: 規制・プラットフォーム変更対応型。加えて、日本の税制に固有の判断であり海外SaaSが扱わない 言語・制度障壁 に守られます。
  • Why Now: 2割特例の終了が1か月後、個人の届出期限が4か月後に迫っています。判断材料（3割特例の要件、控除率の段階表）は2026年度税制改正で確定済みであり、いま計算できます。
  • コア機能 (MVP):
    • 売上・業種区分・概算仕入率を入力すると、3割特例／簡易課税／本則課税の納税額を2027年から2029年まで年度別に並べる試算表。単年ではなく、簡易課税の2年拘束と3割特例の終了を跨いだ合計で比較する。
    • 法人か個人か、決算月はいつかを入力させ、自分に適用される期限日を1つだけ返す期限判定。
    • 出力は税額の試算と期限日に限定し、「どれを選ぶべきか」の助言は行わない。税理士法上の税務相談に踏み込まない設計上の制約として固定する。

アイデア 3: pubcred-watch (公開資格の静かな失効を監視するリリース経路の点検)

  • ターゲット: npm や PyPI へCIから継続的に公開している受託開発会社・SaaS企業のリリース担当と、社内向けパッケージを配っているプラットフォームチーム。
  • 解決する課題: レジストリ側の認証仕様が短い周期で変わり続けており、変更のたびにリリースパイプラインが予告された日に静かに壊れる。しかも壊れるのは「次にリリースしたとき」であって、変更日ではない。四半期に一度しか公開しないパッケージほど、気づくのが遅れる。

検知した生の声（一次ソース）

  • 次の失効日は明示されています。原文は "2FA-bypass tokens will also lose direct publish. Their publishing surface will reduce to reading private packages and staging a publish, which a maintainer approves with 2FA. We are targeting January 2027 for this update." です（GitHub Changelog）。
  • 移行先にも制約が残っています。npm の公式ドキュメントは "Self-hosted runners are not currently supported but are planned for future releases." と書いており、対応するCIも "GitHub Actions (GitHub-hosted runners), GitLab CI/CD Pipelines (GitLab.com shared runners), CircleCI (CircleCI cloud)" に限られます（npm Docs）。セルフホストランナーで公開しているチームには、まだ移行先が存在しません。
  • 設定の既定値が日付で分岐しています。原文は "Trusted publisher configurations created before May 20, 2026 are automatically set to allow npm publish only" と "Configurations created after May 20, 2026 require you to explicitly select at least one allowed action." です（npm Docs）。同じ画面で作った設定が、作った時期によって許可範囲が違います。
  • 多数のパッケージを抱えるメンテナが手作業に追い込まれた実例も記録されています。Babel のメンテナは200個のパッケージを移行するために Puppeteer スクリプトを書く必要があり、その後2026年2月18日に npm trust コマンドが提供されて一括設定が可能になりました（Socket）。
  • パターン判定: 規制・プラットフォーム変更対応型 と マイクロDevExツール型。
  • Why Now: 2027年1月の直接publish停止まで4か月あり、いま点検すれば直せます。ただし後述するとおり、この「まだ4か月ある」ことが収益性の側では不利に働きます。
  • コア機能 (MVP):
    • 組織配下の全パッケージについて、公開に使われている認証方式（classic の残骸、bypass-2FA トークン、OIDC）をレジストリ側とワークフロー側の両方から突き合わせる棚卸し。
    • trusted publisher 設定の許可範囲と、実際のワークフローが実行するコマンドの不一致検出。5月20日前後の既定値の差をここで吸収する。
    • セルフホストランナー利用など、現時点で移行先が存在しない構成の明示。「直せない」ことを早く知らせるほうが、直し方を示すより価値がある。

配点理由

Idea 1: token-clock — 18点 (Tier 2)

  • タイミング 4: 改定が13日前で、値上げ幅も大きい。V4-Pro 出力はピークで $3.96、改定前の一律 $0.87 と比べると4倍を超える。加えて Copilot の従量課金化（6月1日）と重なり、「AIの費用は変動する」という前提が今年になって定着した。減点材料: 時間帯課金を実際に導入しているのは現時点で DeepSeek のみである。他社が追随しなければ、対象は「DeepSeek を使っている開発者」に縮む。追随の見通しは仮説であって、証拠ではない。
  • 技術的実現可能性 4: 中核はレート表・UTCクロック・遅延許容付きのキューであり、いずれも軽い。1〜2週間で1プロバイダ分は動く。減点材料: 削減額を出す精算ログが難しい。「即時実行していたらいくらだったか」は反実仮想であり、キャッシュヒット率やリトライを含めると単純な掛け算では出ない。ここを雑に作ると、製品の中核である「いくら助かったか」が信用されない。
  • 収益性 3: 買い手はすでにトークン代を払っており、削減額で説明できる。月$300以上使っているチームなら、30%削減に対して月$19は通る。減点材料: 母数の大半がそこに届かない。報道で引かれた個人の例は「月$5が$15になる」規模であり、この層は月額を払うより手でcronを書く。「誰がいくら払うか」を具体的に書けるのは月$300以上の層に限られ、その層の人数を今回の調査では確認できていない。
  • 競合優位性 3: LiteLLM・Portkey・Helicone・OpenRouter のいずれも、レート表に時間軸を持つという記述は確認できなかった。予算管理とリアルタイムの支出追跡はあるが、いずれも事後の可視化である。空白は現に存在する。減点材料: その空白は浅い。レート表に時間帯の列を足すのは、OSSゲートウェイなら数週間の作業である。大手が3か月で真似したらどうなるかという問いに対して、残るのは「価格改定を追い続けた記録」だけであり、これは薄い。4点は付けられない。
  • 個人開発適性 4: 実行は利用者の環境で完結し、サーバーもデータベースも不要である。減点材料: 各社の価格改定を追い続けなければレート表が腐る。腐った表は誤った時刻にジョブを流し、そのまま損失になる。放置の害が大きい種類の製品である。

Idea 2: shohizei-switch — 17点 (Tier 2)

  • タイミング 4: 2割特例の終了が2026年9月30日、個人の簡易課税届出が2026年12月31日と、期限が2つとも確定している。逃すと1年間は選び直せない。買い手はすでに消費税を納めており、金額が変わることも決まっている。減点材料: 市場が国内に閉じており、対象はインボイスを機に課税事業者となった小規模層に限られる。海外展開の余地がなく、上限が最初から見えている。
  • 技術的実現可能性 4: 計算そのものは売上税額とみなし仕入率の四則演算であり、数日で書ける。減点材料: 正確性の担保にかかる工数が本体より重い。業種区分の判定は実務上の解釈が入り、複数事業を営む場合の按分規定もある。ここを誤ると製品が有害になるため、検証と免責の設計に時間を取られる。
  • 収益性 3: 選択を誤った場合の差額は年間で数万円から十数万円に及び、支払いの根拠としては強い。買い手はすでに会計ソフトや税理士に払っている層である。減点材料: 需要が単発かつ季節的である。試算は一度やれば終わりで、山は2026年12月と2027年3月に寄る。買い切り3,000円前後が現実的な上限であり、月額の継続前提は立たない。フレームワークの4点（月額$10〜$30の帯が成立する）には届かない。
  • 競合優位性 3: freee・マネーフォワード・弥生はいずれも記帳が本体であり、簡易課税の2年拘束と3割特例の終了を跨いだ複数年度の合計比較という形の試算は薄い。税理士に頼めば答えは出るが、顧問を付けていない層は相談先を持たない。減点材料: この差は機能の差であって構造の差ではない。会計SaaSが確定申告シーズンに向けて同等のシミュレータを足す可能性は十分にあり、その日に価値は消える。
  • 個人開発適性 3: 実行はローカルで完結し、インフラは不要である。減点材料: 税制は毎年変わるため、年1回の改修が構造的に必須になる。加えて、試算の誤りが利用者の納税額に直結するため、サポートの重さが他の2案と質的に違う。「判断は行わず試算に留める」という設計上の制約を守り続ける必要もある。

Idea 3: pubcred-watch — 16点 (Tier 2)

  • タイミング 3: 2027年1月という日付が一次ソースで明示されており、対象も「CIから公開している組織」と明確である。減点材料: 期限まで4か月あり、この種の変更は壊れるまで誰も動かない。購買が直前に集中する一方、その頃には対処法の記事が出揃っている。加えて npm は過去に日程を動かした実績があり（classic token の削除は12月9日へ移動）、日付そのものが確定ではない。
  • 技術的実現可能性 4: レジストリのAPIとワークフローのYAML解析で足り、推論も独自インフラも要らない。1〜2週間で npm 分は出せる。減点材料: 「実際にどの資格で公開されたか」はレジストリ側の公開情報だけでは追い切れず、組織の設定画面への権限が必要になる場面がある。導入時の権限説明が障壁になる。
  • 収益性 3: 一度きりの点検ではなく、レジストリ仕様の変更を追い続ける継続監視として売るなら、月額の根拠は立つ。過去12か月で npm 側の変更は5回以上あり、「また変わった」が定常状態である。減点材料: それでも単価は低い。壊れて困るのはリリース日だけであり、平時の支払い意欲は弱い。月額数百円から数ドルの帯であり、100人で月10〜20万円には届かない。
  • 競合優位性 2: 最大の弱点である。一括設定という最も大きな不便は、2026年2月の npm trust コマンドで既に解消されている。残る空白は「設定と実際のワークフローの不一致検出」と「移行先が無い構成の明示」に限られ、狭い。減点材料: Socket や StepSecurity が隣接領域で既に顧客を持っており、この検査を機能として足すのは彼らにとって小さな追加である。参入余地が構造ではなく、単に誰も手を付けていないことだけに依存している。
  • 個人開発適性 4: CIの中で完結し、サーバーもデータベースも不要である。減点材料: 対象レジストリを増やすほど（PyPI、crates.io、RubyGems）、仕様追随の負荷が線形に増える。

4. リスク・反証分析 (Fail-safe Analysis)

1. token-clock のリスクと対策

最大のリスクは、スケジューリングより先に手を付けるべき手段があることです。 同じ記事が、キャッシュヒットは時間帯に関係なくキャッシュミス時の約3%であり、プロンプトの接頭辞を安定させるほうがスケジューリングより効果が大きいと述べています（Codersera）。 これが正しければ、利用者は「まずキャッシュを効かせる」で満足し、時刻の最適化まで到達しません。 対策は、製品の入口をスケジューリングではなく精算ログに置くことです。 「いま何にいくら払っているか」を時間帯とキャッシュヒット率に分解して見せ、そのうえで削減余地の大きい順に手段を提示します。 キャッシュのほうが効くなら、そう言う道具にします。

第二のリスクは、対象プロバイダが増えないことです。 DeepSeek が単独で終われば市場は成立しません。 対策は、レート表を「時間帯課金の表」ではなく「バッチAPIを含む待てる仕事の投入先の表」として定義することです。 OpenAI と Anthropic のバッチAPIは約50%引きであり、これも「待てるなら安い」という同じ構造です。 時間帯課金が広がらなくても、バッチAPIの選択自動化として価値が残ります。

第三のリスクは、ピーク帯の定義が変わることです。 プロバイダは負荷に応じて時間帯を動かせます。 対策は、レート表を製品内にハードコードせず、更新可能なデータとして外部に置き、更新日を利用者に見せることです。

2. shohizei-switch のリスクと対策

最大のリスクは、判断が多くの人にとって自明であることです。 3割特例は納税額を売上税額の3割に抑えます。 一方、簡易課税のみなし仕入率はサービス業で50%であり、この場合の納税額は売上税額の50%です。 つまりサービス業の個人事業主にとっては3割特例が明確に有利であり、比較するまでもありません。 判断が割れるのは卸売業（みなし仕入率90%）のように仕入率の高い業種に限られ、対象はさらに狭まります。 対策は、Day 1 で業種別に判断が割れる範囲を先に計算し、割れる業種の事業者数を確認することです。 割れる範囲が狭ければ、製品を試算ツールではなく「あなたは計算不要です」と言い切る診断へ組み替えます。

第二のリスクは、税理士法との距離です。 個別の税務相談は有償無償を問わず税理士の独占業務です。 対策は、出力を「入力値に基づく税額の試算」と「制度上の期限日」に限定し、選択の推奨を一切行わないことです。 会計ソフトのシミュレーション機能と同じ立ち位置に留めます。

第三のリスクは、法人の期限が緩いことです。 法人には翌課税期間の確定申告期限までに届出できる特例があり、切迫感が個人より弱くなります。 対策は、訴求を個人事業主の12月31日に寄せ、法人向けは「期限は緩いが選択肢が2つしかない」という別の切り口で分けることです。

3. pubcred-watch のリスクと対策

最大のリスクは、空白が既に埋まりつつあることです。 一括設定という最大の不便は npm trust で解消済みであり、残る空白は狭い。 対策は、検査対象を npm 単体ではなく複数レジストリを跨いだリリース経路に置くことです。 npm と PyPI の両方へ公開している組織にとって、仕様変更は別々にやって来ます。 横断の視点はレジストリ提供者側からは出てきません。

第二のリスクは、2027年1月という日付が動くことです。 GitHub は "targeting" という語を使っており、確定ではありません。 対策は、製品の価値を特定の期限に紐付けず、「リリース経路の資格が今どうなっているか」の常時可視化として設計することです。

第三のリスクは、買い手が「壊れてから直す」を選ぶことです。 リリースが1日遅れる程度の損害であれば、事前の支出は正当化されません。 対策は、Day 1 でこれを直接聞くことです。過去1年でリリースパイプラインが認証周りで壊れた経験の有無と、そのときの停止時間を確認し、経験者が多数を占めない場合は着手しません。

5. 参考ロードマップ (14日間MVPの想定仕様)

最有力候補である token-clock について、14日間の想定を置きます。

期間工程内容
Day 1-2事前検証リスク分析の前提を潰す工程。実装には入らない。(a) 自分の手元のバッチ処理で、時間帯を変えた実測とキャッシュ接頭辞を安定させた実測を別々に取り、どちらの削減幅が大きいかを数字で確定する。(b) LLM APIに月$300以上払っている開発者・チーム5〜10件に接触し、待てる仕事の割合と、投入時刻を今どう決めているかを聞く。(c) キャッシュ最適化のほうが常に大きい、または待てる仕事が全体の2割未満である場合は、製品をスケジューラではなく精算ログへ組み替える。
Day 3-4レート表の定義何をデータとして持つかを確定する。プロバイダ×モデル×時間帯の単価、バッチAPIの割引率と所要時間の上限、キャッシュヒット時の単価を、UTC基準の単一スキーマへ落とす。夏時間の影響を受けない形式であることを制約として固定する。
Day 5-7精算ログの実装中核から作る。実行済みのリクエストを時間帯・キャッシュ状態別に集計し、「別の時刻に投げていた場合の差額」を出す。反実仮想の計算方法（リトライとキャッシュヒット率の扱い）をここで明文化し、出力に前提を併記する。
Day 8-10実行ゲートの実装ジョブに締切と遅延許容を宣言させ、レート表と突き合わせて投入時刻を決める。即時実行・オフピーク待機・バッチAPI投入の3経路を選択肢として持ち、選んだ理由をログに残す。対象は DeepSeek と OpenAI バッチAPIの2経路に限定する。
Day 11-12自分の処理での検証自分が運用しているバッチ処理へ適用し、7日間走らせる。実際の請求額と精算ログの予測額を突き合わせ、誤差を記録する。誤差が説明できない水準なら、対象を単一モデル・キャッシュ無効の構成へ狭める。
Day 13-14公開と検証無償のCLIとして公開し、Day 1-2 で接触した相手へ試用を依頼する。成功指標はインストール数ではなく、「精算ログを見てジョブの投入時刻を実際に変更した人の割合」に置く。変更が起きないなら、削減額を見せても行動は変わらないということであり、有償化へ進まない。

課金設計は、精算ログの単発出力を無償、複数プロバイダのレート表の継続更新と実行ゲートを月額とする二層構成を想定します。 無償側で配るのは1回分の計算であり、有償側で売るのは価格改定に追随し続けることです。 1回の計算はいずれ誰でも作れますが、改定のたびに表を直し続ける手間は、払っている側にしか価値が分かりません。

6. スクリーニング結果と提案候補 (参考情報)

AIエージェントによる評価・分析結果

  • token-clock（総合18点、Tier 2）を最有力候補として選定しました。価格が時刻の関数になったのに、ゲートウェイもSDKもレート表に時間軸を持っていません。空白は現に存在し、日本の開発者は業務時間の3分の2がピーク帯に当たるという地理的な不利をそのまま需要にできます。Tier 1 に届かなかった理由は二点です。第一に、時間帯課金の導入が現時点で1社にとどまり、市場の広がりが仮説であること。第二に、レート表に時間帯の列を足すのはOSSゲートウェイなら数週間の作業であり、空白が浅いことです。着手の条件は Day 1-2 の実測であり、キャッシュ最適化のほうが常に効くと確定した場合は、製品を精算ログへ組み替えます。
  • shohizei-switch（総合17点、Tier 2）は、買い手の支払い習慣が最も確かな案です。すでに消費税を納めており、金額が変わることも期限も確定しています。しかし需要が単発かつ季節的であり、さらに判断がサービス業では自明であるという反証を抱えています。着手するなら、業種別に判断が割れる範囲を先に計算し、対象が十分に残るかを確認してからです。
  • pubcred-watch（総合16点、Tier 2）は、期限の確度が最も高い一方、参入余地が最も薄い案です。一括設定という最大の不便は npm trust で既に解消されており、残る空白は「設定とワークフローの不一致」と「移行先が存在しない構成」に限られます。複数レジストリを跨ぐ視点に賭けるなら成立しますが、npm 単体では推奨しません。
  • 今回の探索で候補から落とした案が3件あります。
    • OpenAI の Prompt Objects 移行支援: 2026年8月26日に Assistants API がハードシャットダウンし、移行先である Prompt Objects 自体も2026年11月30日に停止します。公式の移行ガイドは "prompts, can only be created in the dashboard" と書き、Threads から Conversations への自動移行ツールは提供されないと明記しています（OpenAI Migration Guide）。フォーラムには "It is NOT at feature parity, because you can only use the platform UI to build such a prompt." という当事者の指摘も残っています（OpenAI Developer Community）。痛みは濃いものの、エクスポートAPIが存在しないため取得経路がブラウザ操作の自動化に依存し、しかも移行先を訴求する製品（Promptary、Langfuse、PromptLayer）が既に複数あります。総合13点で却下しました。
    • ベンダー保持状態のエスクロー: Assistants の停止で「保存していたIDの分しか取り出せない」ことが実証されました。しかし「自分のDBに保存すればいい」で終わる話であり、差別化が立ちません。加えて保険型の製品は平時に売れません。総合14点で却下しました。
    • YouTube Shorts の収益下限監視: 2027年2月1日から、直近90日で1,000万の有効視聴を割ったチャンネルは Shorts の収益分配を受け取れなくなります（PPC Land）。"This is blatantly stealing money from creators!" という反発も出ています（Kotaku）。しかし当該指標は YouTube Studio の Engaged Views として既に閲覧でき、進捗表示が追加された日に価値が消えます。総合14点で却下しました。
  • 4回連続で Tier 1 に到達していません。 ただし今回、収益性の軸は3案とも3点で揃い、前回まで2点が混ざっていた状態からは改善しました。「買い手が既に金を払っている領域」という探索軸は、収益性の底上げには効いたということです。代わりに、今回は競合優位性が全案で3点以下に落ちました。支払い習慣のある領域はすでに誰かが商売をしている領域でもあり、空白が浅くなるという交換が起きています。次回は探索軸に「買い手に支払い習慣がある」を残したうえで、空白の深さを、機能の有無ではなく構造で説明できるかを条件に加えます。具体的には、大手が真似できない理由が「まだ手を付けていない」ではなく「立場上できない」と書ける案を優先します。
