1. 調査の背景と市場の変曲点

2026年10月1日の前後に、性質の異なる3つの期限が重なります。

1つ目は、TLS証明書の有効期間短縮です。 2026年3月15日に公的に信頼される証明書の上限が398日から200日へ下がりました。 この日に発行された証明書は、ちょうど2026年10月1日に期限を迎えます。

2つ目は、日本の化学物質規制です。 令和7年厚生労働省告示第269号により濃度基準値設定物質が78物質追加され、2026年10月1日から適用されます。 同日、確認測定の実施方法の決定に、講習を修了した作業環境測定士の関与が求められるようになります。

3つ目は、Microsoft Project Online の退役です。 2026年9月30日にサービスが停止し、スケジュールデータベースは復旧手段のないまま到達不能になります。

この3件に共通するのは、期限を課した側が「一覧」は配るが、「自分の環境への当てはめ」は配らないという構造です。 CA/Browser Forum は上限日数を決めますが、どの証明書がどの経路で更新されているかは各組織にしか分かりません。 厚生労働省は物質の一覧を告示しますが、その物質が自社のどのSDSに含まれるかは事業者にしか分かりません。 Microsoft は退役日を告げますが、どの列が移行先に入らないかは各テナントの構成にしか書かれていません。

前回（2026-08-30）は「立場上できないから空いている空白」を探索軸に置き、3案とも競合優位性が3点に留まりました。 今回はその反省を受け、現場を通さないと集まらないデータを製品の中核に置けるかを追加の条件として各案に当てています。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: bakuro-scope (SDS台帳と告示の版を突き合わせ、確認測定の対象範囲を先に確定するローカルツール)

  • ターゲット: 化学物質を取り扱う国内の中小製造業・印刷業・食品工場・建設業の事業場、およびその安全衛生を請け負う社会保険労務士・作業環境測定機関の営業窓口。化学物質管理者を選任済みだが、専任の産業衛生スタッフを置いていない規模を想定する。
  • 解決する課題: 確認測定は物質単位で発生し、1物質1名あたりの実費が積み上がる。したがって「測るか測らないか」の前に「何が対象か」を確定できるかどうかが、そのまま費用になる。ところがこの突き合わせは、SDS台帳（自社固有）と告示（版が年単位で動く）という2つの動く対象の照合であり、公開されているのは後者の一覧だけである。2026年10月1日の78物質追加は、既存の台帳に対する差分としてしか意味を持たないが、その差分を出す工程はどこにも用意されていない。

パターン判定 & Why Now

references/market-analysis-patterns.md の 5. 規制・プラットフォーム変更対応型 と 3. 価格破壊・ローカルファースト型 の複合です。

いま参入できる理由は、対象物質の一覧が2026年10月1日に一段跳ねることにあります。 既存物質に78物質が加わるため、2024年や2025年に一度作った台帳は、この日を境に古くなります。 そして測定1物質あたりの実費が3万円から8万円の帯にあるため、対象を1件絞り込めた時点でツール代を上回るという説明が成立します。 費用対効果を金額で言い切れる規制対応ツールは多くありません。

既存プレイヤーが解決済みの範囲と、未解決の範囲

解決済みなのは両端です。 一方の端では、SDS管理SaaSが台帳の保管と検索を提供しています。 他方の端では、作業環境測定機関がサンプリングと分析、報告書作成を提供しています。 厚生労働省の CREATE-SIMPLE は、物質を1件ずつ入力して見積もる無償ツールとして中間に位置します。

未解決なのは、台帳の全体を告示の版に対して一括で当て、差分として出す工程です。 CREATE-SIMPLE は1物質ずつの見積もりであり、数百件のSDSを持つ事業場が「今年の告示で新たに対象化した物質」を洗い出す用途には向きません。 測定機関は見積もり依頼が来てから動くため、依頼の前段にある絞り込みには関与しません。 SDS管理SaaSは台帳の管理が本業であり、告示の版差分の追随は年1回の単発イベントにすぎません。

アイデア 2: certserve (更新した証明書が実際に配信面へ届いているかを、外側から常時確かめる検査)

  • ターゲット: 公的に信頼される証明書を数十枚から数百枚運用している事業会社の情報システム部門、および複数顧客のサーバーを預かる受託運用会社。ACMEを一部導入しているが、機器やアプライアンスが残っていて完全自動化に至っていない層。
  • 解決する課題: 証明書の失効事故の主因は、期限を忘れることから、更新は成功しているのに配信面が古いままという形へ移りつつある。更新ジョブは正常終了し、ログも緑になるが、リロードが走らずプロセスが古い証明書をメモリから配り続ける。期限監視はディスク上またはCA側の証明書を見るため、この状態を検知しない。有効期間が200日へ短縮されたことで、この潜在的な破綻が2倍の頻度で表面化する。

パターン判定 & Why Now

6. マイクロDevExツール型 に 5. 規制・プラットフォーム変更対応型 が重なった形です。

いま参入できる理由は、日付が算術で確定していることにあります。 2026年3月15日に切り替わった以上、その日に発行された証明書は10月1日に一斉に切れます。 さらに2027年3月15日に100日、2029年3月15日に47日と、更新頻度は減る方向に一度も動きません。 需要が単調増加する期限は珍しく、買い手が「今年だけの話ではない」と自分で理解できる点が、稟議の通りやすさに直結します。

既存プレイヤーが解決済みの範囲と、未解決の範囲

解決済みなのは、証明書の発見と期限の監視です。 無償・有償を問わず、この機能を持つ製品は飽和しています。 CA各社も、ACMEによる発行と更新の自動化を整備済みです。

未解決なのは、発行の成功と配信の成功のあいだにある断絶です。 CertKit が自ら書いているとおり、Certbot のログには「いま実際に配られている証明書」の情報がありません。 期限監視はCA側やディスク上を見るため、リロード漏れを緑と判定します。 この断絶を埋めるには、TLSハンドシェイクを張って実際に配信されている証明書の指紋を取り、更新後の値と突き合わせる必要があります。 技術的には難しくありませんが、既存の監視製品はこの観点で作られていません。

アイデア 3: pwa-tomb (Project Online から吸い出したダンプを、退役後も読める静的アーカイブへ組み直すローカルツール)

  • ターゲット: 2026年9月30日までに Project Online のデータを吸い出したものの、移行先へ入らない列を大量に抱えたPMO。および、監査・係争・原価計算のために数年後に過去のプロジェクト実績を参照する必要がある組織。
  • 解決する課題: 移行ベンダーが提供するのは Planner Premium への移行であり、移行先の器に入る分しか運ばれない。入らなかったデータはCSVやJSONのダンプとして手元に残るが、元の関係（タスクと担当、ベースラインと実績、カスタムフィールドの定義と値）は失われた状態であり、そのままでは読めない。そして退役後は、元のサービスに問い合わせて構造を確認する手段が存在しない。

パターン判定 & Why Now

5. 規制・プラットフォーム変更対応型 と 4. ワークフロー糊付け・連携型 の複合です。

いま参入できる理由は、退役日を境に問題の性質が入れ替わることにあります。 9月30日までの問題は「どう吸い出すか」であり、これは移行ベンダーが売っています。 10月1日からの問題は「吸い出したものをどう読むか」であり、これを売っている相手がいません。 移行ベンダーの商品は移行先への着地であって、移行先に入らなかった残余は彼らの成果物の外にあります。

この空白は、退役によって上流が消えることで初めて固定される。 サービスが生きているあいだは「必要なら元を見に行けばよい」で済むため、残余を読む製品には価値がありません。 上流が消えた瞬間、手元のダンプが唯一の正本になります。

既存プレイヤーが解決済みの範囲と、未解決の範囲

解決済みなのは、Project Online から Planner Premium への移行です。 FluentPro と Onplana がツールとサービスの両方を提供しており、この領域に隙間はありません。

未解決なのは、移行しない側のデータを、元のサービスなしで意味のある形に戻すことです。 カスタムフィールドは値がIDで格納され、定義は別のエンティティにあります。 両方をダンプしていても、結合の仕方を知らなければ列名すら復元できません。 タイムシートは承認履歴と期間の入れ子構造を持ち、平坦なCSVにすると誰がいつ何時間付けたかが読めなくなります。 この復元は、テナントごとに異なるスキーマを実物で見ないと書けない部分を含みます。

配点理由

Idea 1: bakuro-scope — 16点 (Tier 2)

  • タイミング 4: 施行が1か月後の2026年10月1日に確定しており、78物質の追加という具体的な差分がある。買い手は事業者であり、測定費用という形で金額の物差しを既に持っている。減点材料: 市場が国内の化学物質取扱事業場に閉じており、海外展開の余地が構造的にない。加えて買い手の多くは規制対応をITで解くという発想を持たず、測定機関へ丸投げする経路が既に確立している。5点の条件である「明確な課金動機が既に立っている」に、購買行動として届いていない。
  • 技術的実現可能性 3: 告示の物質表は公開されており、突き合わせのロジック自体は単純な照合である。減点材料: 入力側が難しい。SDSのPDFは書式が統一されておらず、CAS番号が記載されない混合物、別名・慣用名での表記、成分の含有率が範囲で書かれる例が日常的にある。ここでの取りこぼしがそのまま法令上の見落としになるため、精度が製品の生死を決める。2週間で「自社のSDSでは動く」までは行けるが、他社のSDSで同じ精度が出る保証がない。
  • 収益性 3: 測定1物質あたり3万円から8万円という物差しがあるため、買い切り3万円から5万円は説明できる。減点材料: 購入が施行前後に集中し、翌年に払い直す理由がない。告示は毎年改正されるが、事業者の台帳が毎年変わるわけではないため、年額での更新動機が立たない。月額$10〜$30の継続課金という4点以上の条件には届かない。
  • 競合優位性 3: SDS管理SaaSは台帳を持つが、告示の版差分を当てる機能は主力ではない。測定機関は依頼前の絞り込みに関与しない。空白は現に存在する。減点材料: その空白は難所ではなく、優先順位の問題である。大手のSDS管理SaaSが3か月で真似したら、台帳を既に握っている側が圧倒的に有利であり、こちらに残るものがない。参入障壁は「告示の過去の版を遡って保持していること」だけで、これは時間さえかければ誰でも作れる。
  • 個人開発適性 3: SDSを外部へ送らないローカル実行として設計でき、データ預かりの責任を負わずに済む。減点材料: 告示改正のたびにデータ更新が必要であり、これは恒常的な固定費になる。さらに法令の該当性を示す出力を出す以上、「このツールで対象外と出たが監督署に指摘された」という種類の問い合わせが構造的に発生する。個人が抱えるにはサポートの質が重い。

Idea 2: certserve — 17点 (Tier 2)

  • タイミング 5: 2026年3月15日に200日上限が発効し、その日に発行された証明書が2026年10月1日に一斉に期限を迎える。日付が算術で確定しており、推測の余地がない。加えて2027年3月に100日、2029年3月に47日と、更新頻度は減る方向に一度も動かない。需要が単調増加であることを買い手自身が理解できるため、この軸で減点する材料が見つからない。
  • 技術的実現可能性 4: 中核は、対象ホストへTLSハンドシェイクを張り、実際に配信されている証明書の指紋を取って、更新側の値と突き合わせることである。標準ライブラリで書け、1〜2週間でコア機能に届く。減点材料: 網羅性が難しい。SNIで複数証明書を出し分けるホスト、443以外のポートで待つサービス（SMTP の STARTTLS、LDAPS、内部API）、ロードバランサ配下で一部のノードだけ古い証明書を配る構成が、実際の事故の中心にある。「全部を見た」と言える状態にするのが工数の本体になる。
  • 収益性 3: 買い手は情報システム部門であり、失効事故の損失で説明できる。減点材料: 証明書監視は無償のサービスと機能が厚く、価格の天井が低い。「更新済みだが配信面が古い」という差分は本物だが、それだけを理由に既存の監視契約へ上乗せさせるのは難しく、月$5〜$15の帯に落ちやすい。100人で月10〜20万円という5点の条件は、単価側で成立しない。
  • 競合優位性 3: 期限監視は飽和しているが、配信面の実測との突き合わせは既存製品の観点に入っていない。CertKit が自ら「Certbot のログには分からない」と書いているとおり、空白は当事者に認識されている。減点材料: 認識されている空白は埋められやすい。TLSハンドシェイクを張って指紋を比べる処理は、既存の監視SaaSにとって数日の追加である。参入障壁がほぼない領域であり、4点は付けられない。
  • 個人開発適性 2: 最大の弱点である。常時監視を売る以上、通知の遅延と誤検知がそのまま製品の評価になる。減点材料: 監視対象が本番の公開サービスであるため、こちらの障害が「通知が来なかったせいで落ちた」という申立てに直結する。ゼロインフラでは終わらず、監視基盤の可用性を個人が背負うことになる。除外フィルタの「24/7運用」に接近しており、この軸を3点へ上げる設計変更なしに着手すべきではない。

Idea 3: pwa-tomb — 18点 (Tier 2)

  • タイミング 3: 2026年9月30日という期限が確定しており、その直後に「吸い出したが読めないダンプを抱えた組織」が一斉に発生する。買い手は監査要件を持つ法人であり、支払意思はある。減点材料: 母数が減り続ける一方である。Project Online の利用組織は退役に向けて縮小しており、新規に発生することはない。さらに、9月30日までに吸い出さなかった組織は永久に顧客にならないため、市場の上限が退役日に固定される。
  • 技術的実現可能性 4: 入力は顧客が既に持つCSV・Excel・OData JSON であり、テナントへの接続も認証も要らない。関係を復元して静的HTMLへ焼くだけで成立するため、1〜2週間でコアに届く。減点材料: スキーマがテナントごとに違う。カスタムフィールドの定義と値の結合、ルックアップテーブルの参照、タイムシートの期間の入れ子は、実物を数件見ないと正しい形が決められない。汎用の変換器として書き切るには、想定より多くの実データが要る。
  • 収益性 3: 買い切り$79〜$149、あるいは1万円台後半の帯は、監査要件を理由に経費で通る。減点材料: 需要が完全に単発である。1テナントにつき1回で終わり、リピートも社内での横展開も起きない。加えて買い手の発見が難しく、Project Online 利用組織を外から特定する手段がない。月額の根拠が立たないため、4点以上には届かない。
  • 競合優位性 3: 移行ベンダーは移行先への着地を売っており、移行先に入らなかった残余は成果物の外にある。空白は商品設計に由来する構造的なものである。減点材料: 構造的であることと、埋めにくいことは別である。FluentPro や Onplana が「移行しなかった分のアーカイブ出力」を1機能として足せば、既に顧客を握っている側が勝つ。彼らがそれをしない理由は動機の弱さだけであり、参入障壁ではない。
  • 個人開発適性 5: 3案で唯一、この軸が例外的である。上流のサービスが既に消えているため、追随すべき仕様変更が存在しない。API変更で壊れることも、規約変更で止められることもない。入力はローカルのファイル、出力は静的HTML、預かるデータはゼロである。他の2案が「相手が動き続けること」を恒常コストとして抱えるのに対し、本案だけがそのコストを構造的に持たない。

4. リスク・反証分析 (Fail-safe Analysis)

1. bakuro-scope のリスクと対策

最大のリスクは、SDSからの物質同定が実用精度に届かないことです。 CAS番号が記載されない混合物、慣用名での表記、含有率が範囲で書かれる例は日常的であり、ここでの取りこぼしは法令上の見落としと同義になります。 対策は、Day 1 で自社以外のSDSを20件集め、CAS番号が機械的に取れる割合を実測することです。 取得率が低いなら、PDFの自動解析を製品の中核から外し、物質名とCAS番号を利用者が貼り付ける入力形式へ切り替えます。 突き合わせと差分表示だけでも、告示の版を跨いだ棚卸しという主目的は残ります。

第二のリスクは、法令判断の責任を負う立場に立ってしまうことです。 対策は、出力を「該当」「非該当」の断定にせず、該当の可能性がある物質の候補列挙と、根拠となる告示の条文・番号への直リンクに留めることです。 最終判断は化学物質管理者と作業環境測定士が行うという前提を、出力の各行に明示します。

第三のリスクは、買い手が測定機関へ丸投げする経路を既に持っていることです。 対策は、販路を事業者ではなく測定機関と社会保険労務士の側へ向けることです。 彼らは見積もり前の絞り込みを自分の工数で行っており、そこを短縮する道具としてなら、支払う側と使う側が一致します。

2. certserve のリスクと対策

最大のリスクは、常時監視の運用負荷が個人の許容量を超えることです。 通知の遅延と誤検知が製品評価に直結し、こちらの障害が顧客の障害の説明に使われます。 対策は、製品の初期形態を常時監視にしないことです。 利用者のCIやcronの中で走る単発の検査コマンドとして配り、結果の保存も通知も利用者側の仕組みに任せます。 監視基盤を持たなければ、可用性の責任も持ちません。 常時監視は、有償の要望が実際に積み上がってから検討します。

第二のリスクは、差分が小さすぎて金を取れないことです。 「更新済みだが配信面が古い」の検知は本物ですが、それ単体では既存の監視契約に上乗せさせる理由になりません。 対策は、Day 1 で自分が管理する全ホストに対して検査を実際に走らせ、不一致が何件出るかを数えることです。 不一致がゼロなら、この製品が解く問題は自分の環境には存在せず、他人の環境にあるという確証もありません。 その場合は、訴求を検知から「配信面まで含めた更新経路の棚卸し」へ移し、10月1日の第一波に向けた一回限りの点検として売ります。

第三のリスクは、網羅できない構成が事故の中心にあることです。 SNIによる出し分け、443以外のポート、ロードバランサ配下の一部ノードは、いずれも「全部見た」と言えない原因になります。 対策は、検査結果に見られなかった対象の一覧を必ず併記することです。 沈黙を「問題なし」に丸めない設計を、最初の版から入れます。

3. pwa-tomb のリスクと対策

最大のリスクは、顧客が9月30日までに正しく吸い出していないことです。 吸い出しが不完全なら、こちらの復元も不完全にしかなりません。 そして退役後は、足りない部分を取りに戻る手段がありません。 対策は、Day 1 に製品の順序を入れ替え、退役前は「抽出の完全性チェック」を無償で配ることです。 手元のダンプに対して、参照されているのに存在しないID、定義のないカスタムフィールド、期間の欠けたタイムシートを列挙します。 9月中にこれを配れば、顧客は不足を退役前に取りに戻れます。 そして10月以降、同じ顧客に対して復元とアーカイブ生成を有償で売ります。

第二のリスクは、市場の上限が退役日に固定されることです。 9月30日までに吸い出さなかった組織は、永久に顧客になりません。 対策は、9月の無償チェックを顧客名簿の獲得工程として設計することです。 10月1日以降に新規の見込み客は増えないため、退役前の1か月が唯一の集客期間になります。 無償配布を宣伝と割り切り、有償化の判断は名簿の規模を見てから行います。

第三のリスクは、スキーマのばらつきで汎用化できないことです。 カスタムフィールドの結合やルックアップの参照は、テナントごとに異なります。 対策は、Day 1 の無償チェックで実際のダンプを見せてもらう関係を作ることです。 この過程で集まるスキーマの実例は、公開情報からは得られず、後から集め直すこともできません。 上流が消えたあとでは、このデータを持つ者だけが復元器を書けます。

5. 参考ロードマップ (14日間MVPの想定仕様)

最有力候補である pwa-tomb について、14日間の想定を置きます。 退役日が2026年9月30日であるため、Day 1 は9月1日からの起算とします。

期間工程内容
Day 1-2事前検証リスク分析の前提を潰す工程。実装には入らない。(a) Project Online を運用している国内組織またはPMO支援ベンダーに5〜10件接触し、9月30日までの吸い出し計画の有無と、どの形式で保存する予定かを聞く。(b) 実際のエクスポート（OData JSON / CSV / Excel）を1件以上、匿名化した状態で見せてもらえるか交渉する。(c) 「移行ベンダーに任せてあるので全部運ばれる」という回答が大半なら、残余を読む需要が存在しないということであり、着手しない。
Day 3-5完全性チェッカ手元のダンプに対する検査だけを書く。参照されているのに存在しないID、定義の見つからないカスタムフィールド、期間が欠けたタイムシート、担当者が解決できない割当を列挙する。判定は出さず、不足の一覧だけを返す。退役前に取りに戻る余地を残すため、この工程を最優先で仕上げる。
Day 6-8無償配布と名簿獲得完全性チェッカを無償のCLIとして公開し、Day 1-2 の接触先へ配る。同時に、検査結果のスキーマ情報（列名と型の構成、匿名化済み）を任意で送ってもらう導線を用意する。9月中しか集められないデータであることを、この時点で明示する。
Day 9-11関係の復元集まったスキーマ実例をもとに、カスタムフィールドの定義と値の結合、ルックアップの参照解決、タイムシートの期間構造の復元を書く。テナントごとの差異は設定ファイルとして外に出し、実例が増えるたびに追加できる形にする。
Day 12-13静的アーカイブ生成復元した関係を、依存ライブラリなしの静的HTMLへ焼く。プロジェクト一覧、タスクとベースラインの対比、資源割当、タイムシート履歴を、検索可能な形で1ファイルに収める。ネットワークを使わず、10年後のブラウザでも開けることを設計条件とする。
Day 14有償化の判断9月30日を過ぎた時点で、名簿の規模と、完全性チェッカで実際に不足が見つかった件数を数える。成功指標はダウンロード数ではなく、「検査の結果、退役前に追加の吸い出しを実施した組織の数」に置く。全社が「不足なし」で終わるなら、復元の需要も無いということであり、有償化へ進みません。

課金設計は、完全性チェッカを恒久的に無償、復元とアーカイブ生成を買い切りとする二層構成を想定します。 無償側で配るのは9月30日までしか意味を持たない道具であり、有償側で売るのは退役後にしか発生しない読み直しの手段です。 この順序は逆にできません。 退役前に復元器を売っても、顧客は「元を見に行けばよい」と考えるためです。

6. スクリーニング結果と提案候補 (参考情報)

AIエージェントによる評価・分析結果

  • pwa-tomb（総合18点、Tier 2）を最有力候補として選定しました。選定理由は市場の大きさではなく、個人開発適性が5点であることです。上流のサービスが2026年9月30日に消えるため、追随すべき仕様変更が存在しません。API変更で壊れず、規約変更で止められず、預かるデータもありません。3案のうち本案だけが、「相手が動き続けること」を恒常コストとして抱えません。Tier 1 に届かなかった理由は二点です。第一に、市場の上限が退役日に固定され、9月30日を過ぎると新規の見込み客が一切増えないこと。第二に、移行ベンダーが1機能として足せば終わる位置にあり、参入障壁が動機の弱さにしか依存していないことです。着手の条件は Day 1-2 の接触であり、「移行ベンダーに全部任せてある」という回答が大半なら着手しません。
  • certserve（総合17点、Tier 2）は、タイミングが3案で最も強い案です。2026年3月15日＋200日＝10月1日という算術は反証の余地がなく、更新頻度が2027年・2029年と減る方向に一度も動かない点で、需要の持続性が説明できます。それでも17点に留まったのは、個人開発適性が2点であることによります。常時監視の可用性を個人が背負う構造は、除外フィルタの「24/7運用」に接近します。着手するなら、初期形態を単発の検査コマンドに固定し、監視基盤を持たない設計から始めるべきです。
  • bakuro-scope（総合16点、Tier 2）は、費用対効果を金額で言い切れる唯一の案です。測定1物質あたり3万円から8万円という物差しがあるため、対象を1件絞り込めばツール代を上回るという説明が成立します。しかしSDSからの物質同定の精度が製品の生死を握っており、そこが未検証のまま16点に留まりました。着手するなら、実装より先に他社のSDSを20件集め、CAS番号の機械的な取得率を実測してからです。販路は事業者ではなく測定機関と社会保険労務士の側へ向けるべきです。
  • 今回の探索で候補から落とした案が4件あります。
    • GitHub Copilot の AI Credits 消費の可視化: 2026年6月1日に Copilot が使用量課金へ移行し、Premium Request Units が GitHub AI Credits へ置き換わりました。移行直後には想定外の請求に関する不満が出ています（The GitHub Blog、community Discussion #197089）。しかし GitHub 自身が使用量ダッシュボード、支出上限、ユーザー単位の予算管理を既に提供しており、除外フィルタの「Big Tech 正面衝突」に該当します。総合11点で却下しました。
    • Chrome Manifest V2 のストア掲載削除（2026年8月31日）: 本日をもって MV2 拡張機能の掲載が削除され、URL・レビュー・インストール数・item ID による企業配布が同時に失われます（Chrome for Developers）。期限としては鋭いものの、2026-08-27 の ext-chat-audit が拡張機能の棚卸しを、2026-08-28 の forum-lifeboat が閉鎖前の資産保全を既に扱っており、重複判定フィルタに触れます。加えて本日が期限であり、事前判定を売る時間が残っていません。総合12点で却下しました。
    • .NET 8 / .NET 9 のサポート終了（2026年11月10日）: 両バージョンが同日にサポート終了を迎え、NuGet エコシステムも順次追随します（.NET Blog）。しかし課題の形が「依存の束の期限を棚卸しする」であり、2026-08-30 の mcp-sunset と実質的に同一です。総合13点で却下しました。
    • OpenAI Assistants API 移行支援: 2026年8月26日に sunset 済みで、/v1/assistants などは既にエラーを返します。移行需要そのものが消滅しており、かつ mcp-sunset と重複します。総合10点で却下しました。
  • 6回連続で Tier 1 に到達していません。 前回設定した追加条件「現場を通さないと集まらないデータを製品の中核に置けるか」は、3案のうち1案でのみ満たされました。pwa-tomb のテナントごとに異なるスキーマの実例は、9月30日までにしか集まらず、退役後は誰も集め直せません。これは時間で消えない参入条件です。一方 certserve の指紋照合と bakuro-scope の告示突き合わせは、いずれも公開情報の実装であり、この条件を満たしません。今回得られた知見は、「立場上できない空白」より「時間で閉じる収集窓」のほうが個人にとって強いということです。前者は誰にでも開いていますが、後者は窓が閉じた時点で他者の参入を止めます。次回の探索軸には、期限そのものではなく、その期限までにしか観測できないデータが何であるかを明示的に置きます。
