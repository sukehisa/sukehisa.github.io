1. 調査の背景と市場の変曲点

前回（2026-09-03）の終わりに、探索軸へ条件をひとつ足すと宣言しました。 先客が利益相反で作らず、かつ判定に必要な資産が公開情報として既に揃っている位置を探す、という条件です。

前回の失敗を先に書きます。 利益相反だけで絞ると、先客が長年かけて溜めた資産を個人が独力で揃え直す羽目になりました。 eol-cliff は EOL データベースを、rp-declare は仕様追随体制を、それぞれ自前で抱える必要がありました。 作りたくない者と作れない者の差が、そのまま個人開発者の工数として現れたわけです。

そこで今回は、判定に要する材料が既に無償で公開されているかを先に確認し、揃っていない領域を最初から捨てました。 残った変曲点は3つです。

1つ目は、Exchange Web Services の自動遮断です。 2026年10月1日、つまり27日後に、Microsoft がテナント単位の自動遮断を開始します。 公開されている資産は3つあります。 テナント管理者が無償で取得できるEWS 使用状況レポート、EWS 操作と Graph API の対応表、そして Microsoft 自身が公式ドキュメントに列挙したパリティギャップの一覧です。 判定に必要な材料が、全て Microsoft の側から公開されています。 そして、この判定を最も作らないのはバックアップ・移行ツールのベンダーです。 彼らの製品が使う EWS 操作こそ Graph に代替が無い筆頭であり、中立な判定を出せば自社製品が「移行先なし」と表示されます。

2つ目は、地域別最低賃金の発効日の分散です。 2026年度は、発効日が10月1日から12月1日まで散らばりました。 月の途中に発効する県が複数あり、その月は同一の賃金計算期間の中に新旧2つの下限が同居します。 公開されている資産は、都道府県ごとの答申額と発効日、そして派遣労働者には派遣先の最低賃金が適用されるという法解釈です。 どちらも無償で読めます。 そして、この検査を作らないのは給与計算 SaaS のベンダーです。 自社の出力を監査する道具は、自社の対応漏れを可視化する道具でもあります。

3つ目は、ホスト型 AI モデルの退役日の不一致です。 同一のモデルに対して、提供元の公式ページ、クラウドのポータル、提供元の別の公式発表が、それぞれ異なる退役日を表示しています。 公開されている資産は、各プロバイダの退役日一覧ページと、自テナントのデプロイ情報を返す API です。 両方とも認証さえあれば無償で読めます。 そして、この突き合わせを作らないのはモデルの提供元です。 複数プロバイダを横断して「どのモデルがいつ死ぬか」を一枚に並べる道具は、そのまま乗り換え支援の道具になります。

この3件は、公開情報の完備度が異なります。 1つ目はベンダーが判定材料を全て公開済み、2つ目は法令と行政公表で完備、3つ目は公開されてはいるが記述同士が矛盾しているという状態です。 以下では、それぞれについて「公開されているのに誰も突き合わせていない理由」を明示したうえで、個人が入れる位置を探しました。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: ews-verdict (使用状況レポートの SOAP 操作を Graph の到達可否へ翻訳し、アプリごとに「移行できる / 許可リストで延命するしかない / 移行先が存在しない」を判定する検査)

Microsoft 365 テナント管理者が管理センターから落とせる EWS 使用状況レポートの CSV を入力に取り、アプリケーションごとに三値の判定を返すローカル CLI です。 出力は使用量の一覧ではありません。 アプリごとの進退です。

この道具が答えるのは、既存のツールが答えない問いです。 Microsoft の使用状況レポートは「誰が、どの SOAP 操作を、何回呼んだか」を答えます。 ews-verdict は「その操作は Graph でできるのか」を答えます。

検知した生の声（リンク付きエビデンス）

第一に、遮断の起動条件が「設定していないこと」である点です。

October 1, 2026: Microsoft begins tenant-by-tenant automatic blocking - any tenant still set to EWSEnabled = $null gets switched to $false — Artic6 Blog, Preparing: Exchange Web Services Retirement: The AppID Allowlist Challenge

何もしなかったテナントが遮断されます。 明示的に有効化し、かつ許可するアプリケーションの GUID を列挙したテナントだけが除外されます。 そして恒久的な猶予ではありません。

Phased blocking begins on 1 October 2026, according to the Microsoft Learn deprecation page and Message Center notice MC1227454. EWS is then disabled permanently on 1 April 2027 with no re-enablement. — ecorpit, EWS is blocked from 1 October 2026: set the allow list now

第二に、許可リストへ何を書くべきかを、レポートが教えてくれない点です。

The report shows raw GUIDs like 5d661950-3475-41cd-a2c3-d671a3162bc1 instead of friendly names. — Artic6 Blog

この不便に対しては、既に無償の解が出ています。 GUID をアプリ名へ解決する PowerShell モジュールが公開されており、その README は解決すべき問題をこう書いています。

the EWS Usage report gives you App IDs, not app names — peterschmidtdk/EWS-App-Identifier (GitHub)

名前解決は、既に埋まった穴です。 そしてこのモジュール自身が、解決できないものを残しています。 データベースにも Entra ID にも存在しない GUID は、INVESTIGATE - high volume, unidentified という札を付けて手作業へ差し戻されます。

第三に、名前が分かっても進退が決まらないという、より根本的な空白です。 Microsoft 自身が、Graph に代替が無い機能領域を公式ドキュメントで列挙しています。

There are a few major EWS feature areas that the Microsoft Graph API doesn't fully support. — Microsoft Learn, Deprecation of Exchange Web Services in Exchange Online

列挙されているのは、パブリックフォルダーのインポート/エクスポート、Microsoft 365 グループのインポート/エクスポート、インプレースアーカイブ、定期イベントの差分取得、Sticky Notes の CRUD などです。 このうち一部は「今後も対応しない」と明言されています。

Create calendar event without inviting attendees will not be supported in Microsoft Graph API. — Microsoft Learn, 同上

パブリックフォルダーについても、CRUD API は提供されないと公式に告知済みです。 つまり移行先が存在しないまま遮断される用途が、公式に確定しているわけです。

第四に、許可リストが解ではないという、実務家自身の認識です。

Microsoft 365 architect Tiago Carvalho describes it as a stopgap rather than a strategy, and every allow-listed application still needs a delivered migration plan. — ecorpit, 同上

許可リストへ入れても、2027年4月1日に同じ問題が再来します。 そのとき再有効化はできません。

第五に、既存の代替制御が効かないことです。

Application Access Policy...has a fatal flaw for my use case: it restricts which mailboxes an app can access, not whether the app can use EWS at all. — Artic6 Blog, 同上

パターン判定 & Why Now

market-analysis-patterns.md のマイクロDevEx型と海外タイムラグ型の重なりに該当します。 判定ロジックそのものは軽量ですが、判定に使う知識（どの SOAP 操作がどの Graph API へ写るか、どれが写らないか）が英語の公式ドキュメントに分散しており、日本語圏ではほとんど束ねられていません。

なぜ今、個人が入れるのか。 理由は3つあります。

第一に、判定材料が全て Microsoft 側から公開済みである点です。 使用状況レポートは管理センターから CSV で落ちます。 その列は、アプリケーション ID、SOAP アクション、呼び出し回数、最終アクティビティ日です。 EWS 操作と Graph API の対応表も、パリティギャップの一覧も、公式ページに載っています。 個人が独力で溜めるべき資産がありません。 前回のレポートで工数の主因になった「資産の揃え直し」が、この案には存在しません。

第二に、誰も突き合わせていない点です。 Microsoft は使用状況レポートを出し、対応表を出し、パリティギャップの一覧を出していますが、この3つを結合して「あなたのアプリ X は移行できない」と言い切る出力は提供していません。 コードアナライザーはソースコードを要求するため、自社開発アプリにしか当たりません。 テナントで動いている第三者製アプリのソースは手元にありません。

第三に、バックアップ・移行ツールのベンダーが構造的に作れない点です。 Graph に代替が無い筆頭がインポート/エクスポートとパブリックフォルダーであり、これはまさにバックアップ・移行ツールが叩いている領域です。 中立な判定を出せば、自社製品に「移行先なし」の札が付きます。 彼らが出すのは「当社は Graph 対応済みです」という自社限定の告知であり、テナント全体の棚卸しではありません。

リスク・反証分析

最大のリスクは、Microsoft が使用状況レポートに「Graph 対応可否」の列を足すことです。 Microsoft には、この列を足す動機があります。 移行を促進したいからです。 利益相反が無いどころか、利害が一致しています。 前回の eol-cliff では「延命ベンダーは否定の答えを作れない」という構造がありましたが、この案にその構造はありません。 Microsoft は作れるし、作りたい。作っていないのは優先度の問題にすぎません。 これがこの案の最も弱い点です。

対策は、Microsoft が足せない部分に製品の重心を置くことです。 Microsoft が出せるのは「この操作は Graph にある/ない」までです。 出せないのは、「このアプリを許可リストから外したら、誰の何が止まるか」という影響範囲の推定です。 それには、SOAP 操作の呼び出し回数と最終アクティビティ日から、そのアプリの用途（バックアップか、署名挿入か、会議室予約か、CRM 連携か）を推定する必要があります。 用途の推定は、Microsoft が公式に断定できない種類の出力です。 誤ればテナントの業務を止めるからです。 第三者だからこそ「推定です」と書いて出せます。

第二のリスクは、市場の寿命です。 2027年4月1日に EWS は完全停止し、この道具の需要は消えます。 残り19か月の市場です。 対策は、判定エンジンを EWS 専用にしないことです。 「使用状況ログ × 後継 API の対応表 × 公式のパリティギャップ一覧 → アプリごとの進退」という構造は、EWS に固有ではありません。 Microsoft Advertising の SOAP API も2026年10月1日に機能凍結し、2027年1月31日に停止します。 同じ器が次の退役にも使えるかを、最初の設計で確認しておきます。

第三のリスクは、レポートのデータ制約です。

Because data aggregates weekly and stops at 90 days, add the Unified Audit Log, Entra sign-in logs, and app registration grants. — ecorpit, 同上

週次集計かつ90日で切れるため、四半期に1度しか動かないバッチ処理がレポートに現れません。 年次の監査エクスポートや、決算期だけ動くアーカイブ処理が該当します。 これらは許可リストから漏れ、遮断後に静かに失敗します。 対策は、出力に「レポートに現れなかった＝安全」と書かないことです。 「観測窓は90日であり、それより低頻度の処理は検出できない」という限界を、出力の先頭に固定文言として置きます。

検知した生の声（リンク付きエビデンス）

第一に、発効日が県ごとに大きくずれた事実です。

⚠ 発効日は都道府県によって大きく異なります — taxlabor, 2026年度 都道府県別最低賃金一覧

2026年度の答申では、最も早い発効日が10月1日、最も遅い発効日が12月1日でした。 その間に、10月14日（秋田）、10月29日（青森）、10月30日（山形）、11月15日（佐賀）、11月16日（京都）といった月の途中の発効日が並びます。 月末締めの給与計算では、これらの県の10月分・11月分の賃金計算期間の中に、旧額と新額が同居します。

第二に、判定の基準が支払日ではない点です。

最低賃金の適用は「いつ払ったか」ではなく「いつ働いたか」が基準です。 — taxlabor, 同上

月をまたぐ場合は日ごとに新旧賃金を計算して合算する必要があります — taxlabor, 同上

つまり、月単位の平均時給が新額を上回っていても、発効日以降の労働日だけを取り出すと下回っている、という状態が成立します。 月次の集計では見えません。

第三に、派遣における適用先のずれです。

派遣労働者には、派遣元の事業場の所在地にかかわらず、派遣先の最低賃金が適用されます。 — 日本労働組合総連合会, 最低賃金Q&A

派遣元が東京で、派遣先が岩手なら、適用されるのは岩手の額と岩手の発効日（12月1日）です。 派遣元の給与システムは自社の事業所所在地を持っており、派遣先の所在地を賃金判定に使っている保証がありません。 複数県へ派遣している事業者では、同じ賃金計算期間の中で、労働者ごとに発効日が異なります。

パターン判定 & Why Now

マイクロDevEx型ではなく、コミュニティ特化型に該当します。 対象は「複数県に事業所を持つ、または複数県へ派遣している、かつ給与計算を自社の表計算または自作システムで行っている事業者」です。

なぜ今か。 2026年度は、発効日の散らばりが例年より大きく、月の途中の発効が複数県で発生しました。 散らばりが大きいほど、県別マスタの更新漏れと、日割り計算の失念が起きます。

公開情報の完備度は3案で最も高いと言えます。 都道府県ごとの答申額と発効日は行政と各種一覧サイトが公表しており、派遣先適用の法解釈も無償で読めます。 揃え直す資産がありません。

リスク・反証分析

最大のリスクは、除外フィルタの「大手との正面衝突」に近接していることです。 freee・マネーフォワード・弥生は、いずれも都道府県別の最低賃金マスタを持ち、発効日での自動切り替えを実装しています。 2026-09-03 のレポートでは、年末調整の様式変更対応案をまさにこの理由で総合13点として却下しました。 同じ理由でこの案も落とすべきかを、正面から検討する必要があります。

落とさなかった理由は、大手が扱っていない2点があるからです。 第一が、派遣先ベースの判定です。給与計算 SaaS が持つのは雇用主側の事業所であり、就業場所ではありません。 第二が、日単位の分割です。月の途中で発効する県について、その月の賃金を発効日で二分して別々に判定する処理は、月次締めを前提としたシステムの構造と噛み合いません。

しかし、この2点だけでは製品として細すぎます。 対策は、給与計算の代替ではなく「出力の監査」として位置づけることです。 既存の SaaS が出した賃金台帳の CSV を入力に取り、判定だけを行います。 競合しない位置に立てば、正面衝突は避けられます。 それでも軸4に4点を付けられないのは、大手が同じ監査機能を自社の警告として実装できるからです。

第二のリスクは、誤判定の責任です。 最低賃金法違反は、罰則と遡及是正を伴います。 この道具が「問題なし」と出したせいで見逃しが起きた場合、責任の所在が問われます。 対策は、出力を「違反である」ではなく「発効日をまたぐ計算期間があり、日単位の再計算が必要な労働者」の列挙に限定することです。 判定ではなく、要確認対象の抽出に出力を絞ります。

第三のリスクは、需要が年1回である点です。 発効期を過ぎれば動機が消えます。 対策は、対象を最低賃金に限定せず、発効日をまたぐ賃金改定一般へ広げることです。 特定（産業別）最低賃金は地域別と別の発効日を持ち、しかも地域別より高い場合はそちらが適用されます。 この二重判定を含めれば、年内に複数回の利用機会が生じます。

アイデア 3: pin-drift (コードに固定したモデル文字列と、自テナントのデプロイ実態を突き合わせ、静かに差し替わる箇所と確実に落ちる箇所を分けて示す検査)

ところが、別の質問には正反対の回答が付いています。

一方は公式ドキュメントが権威だと言い、他方はポータルの表示が権威だと言っています。 同一ベンダーの公式回答が、権威の所在について食い違っています。

第二に、質問者がその説明に納得していない点です。

リスク・反証分析

最大のリスクは、退役日そのものが解決済みの情報だと見なされることです。 既に無償の横断カレンダーが個人ブログとして公開されています。 「日付を並べるだけ」なら、この道具は不要です。

第二のリスクは、静的抽出の取りこぼしです。 モデル識別子は、ソースコードの定数だけでなく、環境変数、IaC のテンプレート、データベースの設定行、プロンプトテンプレートの内部に散在します。 取りこぼしは「該当なし＝安全」という誤った答えに直結します。 この案で最も価値の高い部分が、最も難しい部分と一致しています。 対策は、静的抽出に加えて、実行時のリクエストログからモデル文字列を回収する経路を用意することです。 静的抽出だけを信頼しない設計にします。

第三のリスクは、認証情報の扱いです。 デプロイ情報の照会には、各プロバイダの認証情報が要ります。 開発者は、素性の分からない CLI に本番の API キーを渡しません。 対策は、既定で読み取り専用スコープのみを要求し、認証情報をディスクへ書かず、照会結果をローカルへ保存する構成にすることです。 それでも初回の信頼獲得は重く、この摩擦は消えません。

4. リスク・反証分析 (Fail-safe Analysis)

1. ews-verdict のリスクと対策

この案が失敗する最も蓋然性の高い筋書きは、10月1日を過ぎてから道具ができあがることです。 27日後に自動遮断が始まります。 遮断された組織は、その場で許可リストを設定するか、業務を止めるかの二択に追い込まれます。 そのとき必要なのは棚卸しの道具ではなく、今すぐ書くべき GUID のリストです。 14日で作っても、残る猶予は13日です。

対策は、出力の順序を逆転させることです。 「移行計画の作成支援」ではなく、「今日、許可リストへ入れるべき GUID の一覧」を最初の画面に置きます。 その下に、それぞれの進退（移行できる／延命するしかない／移行先が無い）を添えます。 緊急の需要へ先に答え、計画の需要へ後から答える構成にします。

第二の筋書きは、Microsoft が10月中に対応可否の列を足すことです。 この案には利益相反による防壁がありません。 そうなった場合、残る差別化は影響範囲の推定だけです。 着手前に、この一点だけで製品が成立するかを判断します。 成立しないなら、着手しないのが正しい判断です。

2. chingin-split のリスクと対策

この案が失敗する最も蓋然性の高い筋書きは、対象者が存在しないことです。 複数県に跨り、かつ表計算で給与計算をしている事業者が、実在するのか。 実在しても、その事業者が有償の道具を探しているのか。 表計算で給与計算を続けている組織は、そもそも道具に金を払わない選択をした組織である可能性があります。

対策は、着手前に対象者の実在を確認することです。 確認できないなら着手しません。

第二の筋書きは、大手が派遣先の就業場所を1列足すことです。 そうなれば残る空白は月の途中の日割りだけになり、製品として細すぎます。 この案は、着手する場合でも「最低賃金の検査」としてではなく、賃金台帳の列マッピングを起点とした汎用の突合器として設計すべきです。 最低賃金は最初の適用例にすぎない、という位置づけにします。

3. pin-drift のリスクと対策

この案が失敗する最も蓋然性の高い筋書きは、自動昇格が実際には起きていないことです。 この案の価値は「静かに差し替わる箇所がある」という前提に全て乗っています。 もし調査対象のデプロイが全て手動更新に設定されており、退役日に例外を投げるだけなら、既存の監視で足ります。 その場合、この道具の存在理由が消えます。

対策は、着手前にこの前提を実測することです。 手元とチームのデプロイを列挙し、自動昇格が設定されているものが1件でもあるかを確認します。 1件も無いなら着手しません。

第二の筋書きは、プロバイダの SDK が警告を出すことです。 実装は数十行であり、いつ来てもおかしくありません。 対策は、SDK が出せない出力を製品の中心に置くことです。 SDK が出せるのは「このデプロイは昇格します」までです。 出せないのは、「昇格後に出力がどう変わるか」という差分の実測です。 昇格前後の両バージョンへ同じプロンプトを流し、差分を記録する工程を製品へ含めます。 これはプロバイダが自社の SDK に組み込めない種類の機能です。 自社モデルの世代間差分を、自ら定量化して見せることになるからです。

Day 8-9名前解決の統合既存の無償モジュールが持つ AppID → アプリ名の対応を取り込み、GUID に名前を添える。解決できない GUID を隠さず、「未解決・呼び出し量 N 回」として最上位へ出す。 未解決かつ高頻度のものが、最も危険な取りこぼしである。
Day 10-11観測窓の明示出力の先頭に、レポートの観測窓（週次集計・最大90日）と、そこから導かれる限界を固定文言として置く。「レポートに現れなかったこと」を「使っていないこと」として出力しない。 四半期バッチや年次エクスポートは原理的に検出できないため、その旨を明記する。
Day 12-13影響範囲の推定SOAP アクションの構成と呼び出し量から、各アプリの用途（バックアップ／署名挿入／会議室予約／CRM 連携）を推定し、「許可リストから外した場合に止まる業務」を推定として添える。これが Microsoft には出せない出力であり、この案の唯一の防壁である。 断定せず、根拠となった SOAP アクションを必ず併記する。
Day 14有償化の判断成功指標はダウンロード数ではなく、「検査の結果、許可リストへ GUID を追加した、または移行の発注を行った件数」に置く。判定が行動を引き起こさないなら、それは知って終わりの情報であり、有償化へ進まない。

課金設計は、単一テナントの検査を無償、MSP 向けの複数テナント横断と影響範囲の推定を有償とする二層構成を想定します。 無償側は Microsoft が模倣可能です。 有償側が持つのは用途の推定であり、これは Microsoft が公式には断定できません。 誤ればテナントの業務を止めるからです。 第三者だから「推定です」と書いて出せる、という一点にこの製品の存在理由があります。

6. スクリーニング結果と提案候補 (参考情報)

AIエージェントによる評価・分析結果

  • ews-verdict（総合19点、Tier 2）を最有力候補として選定しました。選定理由は、今回の探索軸「判定材料が公開情報として既に揃っている」に、3案で最も明快に当てはまるからです。使用状況レポートも、EWS-to-Graph の対応表も、パリティギャップの一覧も、全て Microsoft が無償で公開しています。個人が独力で溜めるべき資産がありません。前回のレポートで工数の主因となった「資産の揃え直し」が、この案には存在しません。加えて、期限が27日後に確定しており、遮断の起動条件が「何もしなかったこと」であるため、無自覚な組織ほど当たります。Tier 1 に届かなかった理由は二点です。第一に、この案には利益相反が存在しないこと。 Microsoft は対応可否の列を足せるし、足す動機もあります。前回まで探索軸の中核だった「作りたくない先客」が、ここには居ません。第二に、市場の寿命が19か月で切れること。2027年4月1日に EWS が完全停止すれば、需要も消えます。
  • pin-drift（総合18点、Tier 2）は、課題の反復性で3案の最上位です。モデルの退役は一度きりの事件ではなく、四半期ごとに来る保守作業へ変わりました。Idea 1 が19か月で終わるのに対し、この案の需要は終わりません。それでも18点に留まったのは、収益性と競合優位性が同時に3点であることによります。無償の横断カレンダーが既に存在し、差別化は自動昇格の検出という一点に依存します。その一点も、プロバイダの SDK が数十行の警告を足せば消えます。着手するなら、日付の可視化からではなく、昇格前後の出力差分の実測から入るべきです。差分の記録だけは、プロバイダが自社の SDK に組み込めません。自社モデルの世代間差分を自ら定量化して見せることになるからです。
  • chingin-split（総合17点、Tier 2）は、公開情報の完備度が3案で最も高い案でした。都道府県別の発効日も、派遣先適用の法解釈も、全て無償で読めます。しかしタイミング3点・収益性3点・競合優位性3点が重なり、17点に留まりました。除外フィルタの「大手との正面衝突」に近接していることが最大の理由です。2026-09-03 で同型の年末調整案を同じ理由で却下しており、判断の一貫性を保つ以上、この案だけを高く採点することはできません。着手するなら、最低賃金の検査としてではなく、賃金台帳の列マッピングを起点とした汎用の突合器として設計する場合に限ります。最低賃金は最初の適用例にすぎない、という位置づけであれば、大手の1列追加で消える構造から抜けられます。
  • 今回の探索で候補から落とした案が4件あります。
    • Python 3.10 のサポート終了対応: 2026年10月31日に上流の保守が止まり、Azure App Service の拡張サポートも10月1日に終わります。期日として鋭く母数も大きいのですが、課題の形が「どのコンポーネントを誰がいつまでパッチするか」であり、2026-09-03 の eol-cliff と実質的に同一です。重複判定フィルタに該当するため、総合13点で却下しました。
    • Microsoft Advertising SOAP API の退役: 2026年10月1日に機能凍結、2027年1月31日に完全停止します。EWS と同型の「SOAP から REST への移行棚卸し」であり、期日も近接しています。単独の案としてではなく、ews-verdict の判定エンジンが次に適用できる領域として扱うのが正しいと判断し、独立案としては総合14点で却下しました。買い手が広告代理店に限られ、母数が EWS より一桁小さい点も理由です。
    • Sora API 終了に伴う生成資産の退避: 2026年9月24日に API が終了し、期限を過ぎるとユーザーデータは削除されます。20日後という切迫度は3案のどれよりも高いのですが、対象が「Sora で生成した資産を本番で参照しているアプリ」に限られ、しかも作業内容がエクスポートと参照書き換えという一度きりの単純作業です。有償化の余地がなく、総合11点で却下しました。
    • npm の Granular トークン90日期限への追随: クラシックトークンの失効後、新規の Granular トークンは有効期限が最大90日となりました。CI の公開パイプラインが四半期ごとに静かに失敗する構造ですが、2026-08-29 の token-clock と同一の課題です。重複判定フィルタに該当するため、総合12点で却下しました。
  • 10回連続で Tier 1 に到達していません。 今回の探索軸は、狙った軸では機能しました。技術的実現可能性の平均が4.0点であり、前回の3.67点から改善しています。「判定材料が公開済みか」で先に絞ったことが、そのまま MVP 工数の低さとして現れました。3案とも、揃え直すべき資産を持ちません。 一方で、今回沈んだのは競合優位性です。 軸4の平均が3.0点であり、前回の3.67点から明確に後退しました。理由は探索軸の交換にあります。公開情報が完備している領域とは、誰でも同じ材料に手が届く領域です。 材料が公開されているということは、先客も同じ材料を持っているということです。前回の軸（利益相反）は差別化を作りましたが工数を膨らませ、今回の軸（公開情報の完備）は工数を削りましたが差別化を溶かしました。2つの軸は交換関係にあります。 この交換関係が、10回 Tier 1 に届かない構造的な理由だと考えます。軸2と軸4を同時に高く保つには、材料は公開されているが、突き合わせた結果を出すことが先客にとって不都合という第三の条件が要ります。今回の3案でこれを満たしていたのは pin-drift だけでした。退役日は各社が公開していますが、それを横断して一枚に並べることは提供元にとって不都合です。ews-verdict は材料も公開・突き合わせも Microsoft に不都合でなく、chingin-split は材料も公開・突き合わせも大手に不都合ではありません。 次回の探索軸は、「材料が公開されている」かつ「突き合わせた結果が先客に不都合」の積で絞ります。材料の公開だけでも、不都合だけでも足りません。両方が同時に成立する位置だけを候補に残します。
