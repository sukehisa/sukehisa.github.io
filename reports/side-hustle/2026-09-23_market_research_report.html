1. 調査の背景と市場の変曲点

前回（2026-09-21）は、値上げではなく数え方の新設を軸に置きました。 請求が立つ前に、新しい単位での消費量を自分の持ち物だけで再構成できるかどうかが道具の成立境界でした。

今回は、障害の原因を見ます。 ただし「自分が何を変更したか」ではありません。 何も変更していないのに、なぜ壊れるのか、です。

通常の障害はコミットが引き起こします。 コードを書き換え、PRをマージし、デプロイした瞬間にテストが落ちます。 原因は自分の手元にあり、Git の差分が犯人を指します。

上流の停止時計（Deprecation Clock）は、そう動きません。 ワークフロー定義もアプリケーションコードも何ヶ月も触っていません。 ただカレンダーの日付が進んだという理由だけで、昨夜までグリーンだったパイプラインが朝一番に突然死します。 原因は自社のリポジトリの外にあり、差分を見ても何も変わっていません。

2026年9月下旬から10月中旬にかけて、この形の「サイレントな停止時計」が集中して期日を迎えます。

  • GitHub Actions runners の Node.js 20 完全撤去（2026年9月23日本日、GitHub-hosted runner から Node 20 が消滅）
  • GitHub Actions 自己ホストランナーの最小バージョン強制執行（2026年9月25日、最新版から30日以上遅れたランナーのジョブ実行を完全遮断）
  • Cloudflare Workers KV レガシー名前空間ルートの完全停止（2026年10月15日、/accounts/{account_id}/workers/namespaces/* が完全停止）

3つとも、上流が一方的に定めた時計です。 違いは、期日が到来したとき、その時計の進捗を利用者が自前で観測・予見できる仕組みがあるかでした。 提供元が「APIを公開したから各自で定期的に叩いて監視せよ」と運用を放任した場所に、個人開発者が入り込める隙間が生まれます。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: runner-clock (自己ホストランナーのバージョンと新設 deprecations API を照合し、30日ルールと強制執行によるジョブ遮断日を逆算して事前警告する監視)

対象は、GitHub Actions の自己ホストランナー（Self-hosted runner）を自前で運用しているインフラエンジニア・SRE・プラットフォームチームです。 GPUインスタンス、オンプレミスサーバー、Kubernetes（Actions Runner Controller）で専用ランナーを動かしているチームが該当します。

入力は2つです。 1. GitHub API のランナー一覧（GET /orgs/{org}/actions/runners で取得できる各ランナーのバージョン情報） 2. 2026年9月3日に新設された退役API（GET /actions/runners/deprecations/{version}）

出力は次の3点です。 1. 組織内に点在する全ランナーの退役予定日一覧（runtime_deprecates_at および registration_deprecates_at） 2. 最新リリースから30日経過による強制遮断までの残り日数カウントダウン 3. 遮断の14日前・7日前・3日前に Slack / GitHub Issue へ届く事前アラート通知

本体は3番目です。 APIを叩いて期日を知るだけなら難しくありません。 難しいのは、組織内の複数リポジトリ・ランナーグループに散らばった数百台のランナーを定期走査し、パイプラインが止まる前に更新作業を計画メンテナンスへ落とし込むことです。

検知した生の声（リンク付きエビデンス）

最も価値の高いエビデンスは、GitHub 自身が「自己ホストランナーは自動更新されないため、APIを定期的に叩くワークフローを自作せよ」と利用者に丸投げしている一文です。

A new REST API returns when registration and runtime support end for a given runner version, so you can plan runner upgrades before a version is deprecated. Call GET /actions/runners/deprecations/{version} at the repository, organization, or enterprise level. The response includes runner_version, runtime_deprecates_at, and registration_deprecates_at. — GitHub Actions: Early September 2026 updates（The GitHub Blog）

GitHub-hosted runner は提供元が勝手に更新します。 しかし自己ホストランナーは利用者が更新しない限り古くなり続けます。 GitHub は 2026年9月25日に強制執行（Full Enforcement）を開始し、古いランナーを容赦なく弾きます。

Once enforcement is active, self-hosted runners below the minimum required version are unable to register, re-register, or execute workflow jobs. — GitHub Changelog: Minimum self-hosted runner version enforcement

さらに、GitHub の標準運用規則では、最新リリースから30日遅れたランナーは退役対象になります。 自前で監視を組まない限り、「週明けに出社したら社内GPUランナーが全滅していた」という事態が構造的に発生します。

パターン判定 & Why Now

パターンはマイクロDevEx型と規制・プラットフォーム変更対応型の複合です。

Why Now は2026年9月3日の新API公開と、9月25日の強制執行開始です。 GitHub が公式の判定口（GET /actions/runners/deprecations/{version}）を配ったことで、推測に頼らず確定した期日を取得できるようになりました。 提供元が「APIは渡したからあとは自分でやれ」と引いた境界線が、そのままツールの設置場所になります。

既存プレイヤーが解決済みの範囲と未解決の範囲の境界線は次のとおりです。

  • 解決済み: 各ランナーの現在のバージョン番号の表示。GitHub の Settings 画面に出ます。
  • 解決済み: 指定した1つのバージョンがいつ退役するか。新設 API が即座に返します。
  • 未解決: 組織内の全ランナーを突き合わせ、最短であと何日でジョブが拒否されるかの統合警告。 GitHub は単一画面で期日一覧を出さず、アラートも飛ばしません。

アイデア 2: action-node-audit (リポジトリ内のワークフローが依存する第三者 Action を走査し、本日撤去された Node 20 依存と偽の非推奨警告を切り分ける静的検査)

対象は、GitHub Actions でビルドやデプロイを行っている開発チーム全般です。

2026年9月23日（本日）、GitHub-hosted runner から Node.js 20 が完全に撤去されました。 利用している第三者 Action の action.yml が runs.using: node20 のまま放置されていると、本日以降ワークフローが実行時エラーでクラッシュします。

さらに現場を混乱させているのが、GitHub Actions runner の実装バグによる「偽警告」です。

検知した生の声（リンク付きエビデンス）

GitHub の公式 Issue に、回避設定を入れても誤った警告が出続ける不満が報告されています。

When FORCE_JAVASCRIPT_ACTIONS_TO_NODE24=true is set in a workflow's env: section, JavaScript actions with using: node20 are correctly upgraded to run on Node 24 at runtime — but the end-of-job deprecation annotation still fires with the misleading message: "The following actions are running on Node.js 20 and may not work as expected". — Misleading Node 20 deprecation warning when FORCE_JAVASCRIPT_ACTIONS_TO_NODE24=true is set（actions/runner #4295）

The action is added to DeprecatedNode20Actions based on its declared version (node20) before DetermineActionsNodeVersion has a chance to check the FORCE_JAVASCRIPT_ACTIONS_TO_NODE24 env var and upgrade the runtime to node24. The end-of-job warning then iterates over that list and claims the actions "are running on Node.js 20", even though they ran on Node 24. — 同 Issue

この不具合により、「本当に壊れる Action」と「設定により Node 24 で動いているが警告だけ出ている Action」が画面上で見分けられません。

このアイデアは、.github/workflows/*.yml を解析し、各 Action の宣言とランタイム強制フラグを照合して、真の即死対象だけを浮き彫りにする CLI です。 しかし、このツールは本日以降に駆け込みで使われた後、各 Action が node24 対応版をリリースすれば役目を終えます。 寿命が短すぎるため、恒久的なプロダクトとしては成立しません。

アイデア 3: cf-path-scan (リポジトリ内のコード・CI・Terraform を走査し、10月15日に停止する Cloudflare Workers KV 旧ルートの呼び出しを検知して一括置換するツール)

対象は、Cloudflare Workers や Terraform でインフラを管理する開発者です。

2026年10月15日に、Workers KV のレガシールートが完全に停止します。

検知した生の声（リンク付きエビデンス）

The legacy Workers KV API routes under /accounts/{account_id}/workers/namespaces/ are deprecated in favor of the Workers KV API routes under /accounts/{account_id}/storage/kv/namespaces/. The legacy and replacement routes are interchangeable...After October 15, 2026, requests to the legacy /accounts/{account_id}/workers/namespaces/* routes will no longer be supported. — API deprecations（Cloudflare Fundamentals docs）

パスを /workers/namespaces/ から /storage/kv/namespaces/ へ変えるだけの単純な置換です。 リポジトリ内のスクリプトや Terraform を走査して置換パッチを出すツールは技術的に容易に作れます。

しかし、この変更は置換ルールが単純すぎます。 公式ドキュメントに書かれた対応表を見れば開発者が sed やエディタの一括置換で数分で修正できます。 独立した有料ツールとして対価を請求できるだけの価値がありません。

4. 最有力アイデアの深掘りと検証計画 (runner-clock)

リスク・反証分析

runner-clock を推進する上での最大のリスクと反証は以下の3点です。

1. GitHub 公式によるダッシュボード統合リスク（最大リスク）

  • GitHub が GET /actions/runners/deprecations/{version} を新設したのは、管理画面に将来組み込むための布石である可能性があります。GitHub が Organization の Settings 画面に「退役まであと○日のランナーがあります」という警告バナーと通知を標準実装した場合、外部ツールの存在意義が消失します。

2. 大手オートスケールソリューションへの内包リスク

  • 多くの企業はランナーを素の VM ではなく、Actions Runner Controller (ARC) や Kubernetes、WarpBuild、Runs-on などのオーケストレーター経由で動かしています。これら上流のコントローラーが「退役期日前の自動ローリングアップデート」を標準機能として取り込んだ場合、単体監視ツールの出番がなくなります。

3. 退役サイクルの頻度と関心の低下

  • ランナーのバージョン退役は毎日発生するわけではなく、数ヶ月に一度のイベントです。定常的にログインするダッシュボードとしての定着が難しく、通知が届かない期間の解約（チャーン）リスクが高くなります。
