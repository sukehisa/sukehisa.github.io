1. 調査の背景と市場の変曲点

前回（2026-09-16）は「数える者」を軸に置きました。 数えた結果がそのまま自分への請求額になり、誰も検算しない構造です。 結論として出た条件は、数えるための材料が一部だけ手元にあること、でした。

今回は問いを、義務の側から通知の側へ移します。 非推奨の警告は、誰の画面に出ているかを見ます。

この軸を選んだ理由は、前回までの探索が「まだ誰も知らない締切」を探し続けていたことにあります。 しかし実際の壊れ方を追うと、締切が知られていない例はほとんどありません。 警告は出ています。 多くの場合、1年前から出ています。

痛みが残るのは、その警告が表示される場所と、それを直せる者の手元が、別々のときだけです。

この構造では、警告の量を増やしても何も改善しません。 受け取っている人は直せず、直せる人は受け取っていないからです。 受け取った側にできることは、直せる側へ「あなたのところが壊れます」と伝えることだけになります。 そして伝達は人力なので、届かないまま期限が来ます。

今回はこの軸で3つの構造を拾いました。

  • Chrome の XSLT 撤去（警告は訪問者の DevTools と Lighthouse に出る。配信者は自分の XML を DevTools で開かない）
  • apt が拒否する署名鍵（警告は利用者の apt update に1年前から出る。配信元は自分のリポジトリを apt で叩かない）
  • 送られない Sunset ヘッダ（警告が出る場所そのものが存在しない）

3つとも「警告と修正権限が同じ手元にない」点は同じです。 違いは、警告が別のどこかには出ているのか、それとも最初から出ていないのかでした。 結論から書くと、道具の置き場になったのは1つだけです。 警告が別のどこかに出ているなら、それを回収して配信者へ運ぶ仕事が成立します。 警告が最初から出ていないなら、回収すべきものがなく、仕事は人力の追跡に戻ります。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: served-lint (公開中の XML・フィード・エンドポイントを利用者側の目で走査し、日付の決まった廃止ポリシーに照らして「いつ壊れるか」を資源1件ずつ確定させる外形検査)

対象は、自分のサイトの HTML ではなく 配布物としての XML を公開している運営者です。 具体的には、機関リポジトリ（DSpace の OAI-PMH）、官公庁・規制当局の公開データ、自前で RSS / Podcast フィードを配信している事業者が射程になります。

入力は、公開 URL の一覧またはサイトマップです。 出力は、資源1件ずつに次の3つを付けた検査台帳です。

1. 廃止対象の記法を使っているか（<?xml-stylesheet ?> 処理命令か、JavaScript の XSLTProcessor 呼び出しか） 2. 撤去日に見た目が実際に壊れるか（ヘッドレスブラウザで撤去後の挙動を再現し、現状と比較する） 3. 救済措置が実際に届いているか（Origin Trial のトークンが、その XML のレスポンスヘッダに本当に載っているか）

3番目が本体です。 XSLT を検出すること自体は難しくありません。 難しいのは、救済を申し込んだ後に「効いている」と確認することです。 Origin Trial のトークンは HTTP ヘッダか <meta> タグで配られますが、XML 文書に <meta> は置けません。 つまり静的ホスティングで XML を配っている運営者は、配信基盤のヘッダ設定を触れなければ救済を受け取れません。 そして効いていないことは、エラーではなく「ただ壊れる」という形で現れます。

検知した生の声（リンク付きエビデンス）

最も価値の高いエビデンスは、Chrome 自身が「使用カウンタでは該当を判定できない」と書いている一文です。

about 75% of sites that hit the use counter don't appear to be visibly broken — Intent to Deprecate and Remove: Deprecate and remove XSLT（blink-dev）

カウンタに載っても4分の3は壊れません。 裏を返すと、カウンタに載ったかどうかを知っても、自分が壊れるかは分からないということです。

同じ Intent は、撤去の日程を明示しています。

M155 (Nov 17, 2026): XSLT stops functioning on Stable releases, for all users other than Origin Trial and Enterprise Policy participants — 同スレッド

M164 (Aug 17, 2027): Origin Trial and Enterprise Policy stop functioning. XSLT is disabled for all users — 同スレッド

日付は動いていませんが、マイルストーン番号は動いています。 現行の公式ドキュメントでは、同じ2つの日付が Chrome 158 と Chrome 176 として記載されています（Removing XSLT for a more secure browser）。 影響判定を Chrome のバージョン番号で組んだ運営者は、この時点で一度ずれています。

Chrome が案内する検出手段は2つですが、どちらも配信者の手元では動きません。

The Reporting API is a generic reporting mechanism for web applications to use report on various platform features and conditions, including feature deprecations. — Removing XSLT for a more secure browser（Chrome for Developers）

Reporting API は、レスポンスにヘッダを仕込んだうえで、実際の利用者がその URL を Chrome で開かないと何も返しません。 もう一方の Enterprise Legacy Technology Report は、管理下の Chrome にしか効きません。 RSS フィードや OAI-PMH エンドポイントは、管理下の Chrome で開かれることも、Reporting API を仕込まれることも、まずありません。

影響の広さは、当事者が数えています。

My estimate is that this affects more than 500,000 feeds and millions of people viewing them on the web. — Don't kill my pretty RSS feed (XSLT)（Justin Jackson）

官公庁側の該当例は、WHATWG の Issue で列挙されました。 米国議会、国立気象局、欧州議会、豪州 TGA、カナダ森林局、E-PRTR が挙がっています。 提起者は、探せば見つかることを指摘しています。

If I, and others, could easily find such examples, I believe browser vendors could easily find these, too. — XSLT removal will break multiple government and regulatory sites across the world（whatwg/html #11582）

0.0001% still results in someone being frustrated every 3 seconds. — 同 Issue

機関リポジトリでは、用途が特定されています。

Client-side XSLT in JavaScript (e.g. saxonjs)? — Address removal of XSLT in Chrome based browsers（DSpace/DSpace #11648）

DSpace の OAI-PMH は、ブラウザで開いたときの可読表示を <?xml-stylesheet … ?> に依存しています。 該当するのは DSpace 8.x / 9.x / main であり、世界中の大学図書館の設置インスタンスがそのまま対象になります。

パターン判定 & Why Now

market-analysis-patterns.md の分類では マイクロ DevEx 型に該当します。 既存の開発者向けツールが取りこぼしている検査工程を、専用の小さな道具で埋める形です。

Why Now は3点あります。

第一に、撤去日（2026年11月17日）が2か月後に迫っています。 第二に、救済措置（Origin Trial）は2026年8月25日に既に稼働しており、申し込めるが効いているか確認できないという状態が今まさに発生しています。 第三に、影響判定に使える公式手段が、配信物としての XML に対しては構造的に機能しません。

既出アイデアとの切り分け

2026-09-14 の regen-watch は、AIビルダー製アプリの外形をベースライン化してセキュリティ退行を差分検査する案でした。 外形を見る点は共通しますが、入力も買い手も異なります。 regen-watch の入力は自分のアプリの再生成であり、買い手は AI ビルダーの利用者です。 served-lint の入力は外部の廃止ポリシー日程であり、買い手は XML を配布している運営者です。 両方を同時に入れる理由は説明できます。 一方は自分の変更を、もう一方は他人の変更を見ているためです。

アイデア 2: sign-drift (公開している apt / rpm リポジトリと配布鍵を外から検査し、どのディストリビューションのポリシーで今日拒否され、次にいつ拒否されるかを日付で返すツール)

対象は、自前の Linux パッケージリポジトリを配っているソフトウェアベンダーと OSS プロジェクトです。

入力はリポジトリの URL だけです。 出力は、配布鍵と Release 署名に使われているアルゴリズムと、各ディストリビューションの暗号ポリシーに照らした拒否日です。

検知した生の声（リンク付きエビデンス）

この構造で最も強いエビデンスは、警告を受け取った利用者が「自分にできることはない」と書いている一文です。

There's nothing you can do besides raising awareness for this issue. — Debian repo: signing must not use SHA1（openresty/openresty #1072）

この Issue は2025年8月30日に、利用者から提起されています。 警告そのものは1年前から apt update に出ていました。

Warning: http://openresty.org/package/debian/dists/bookworm/InRelease: Policy will reject signature within a year — 同 Issue

同じ警告は Kubernetes の公式 APT リポジトリにも出ていました。

Warning: https://pkgs.k8s.io/core:/stable:/v1.33/deb/InRelease: Policy will reject signature within a year — Debian now deprecates public key file used for K8s APT repo（kubernetes/kubernetes #133532）

Signature Packet v3 is not considered secure since 2026-02-01T00:00:00Z — 同 Issue

猶予が切れると、警告は失敗に変わります。

Signing key on 98F5A7CC1ABE72AC3852A007D33A1BD725ED047D is not bound: No binding signature at time 2026-01-18T18:02:18Z because: Policy rejected non-revocation signature (PositiveCertification) requiring second pre-image resistance because: SHA1 is not considered secure since 2026-02-01T00:00:00Z — APT Repository signature verification failed due to SHA-1 deprecation（dbeaver/dbeaver #40250）

同じ現象は、配信基盤の側にも及んでいます。

APT fails to update repositories hosted on OBS (like GPXSee) because the signatures or key bindings still use SHA-1. — APT signature verification fails（openSUSE/open-build-service #19221）

期限を前にした警鐘も出ていました。

If you ignored this for the last year, I would like to tell you that 2026-02-01 is not that far away. — apt, SHA-1 keys + 2026-02-01（Michael Prokop）

ここで注意すべきは、壊れているのが鍵であってビルド設定ではないことです。 問題は数年前に生成された公開鍵の自己署名パケットにあり、リポジトリのソースを見ても分かりません。 ベンダーは自分のリポジトリを apt で叩かないので、警告を1年間見ていません。

パターン判定 & Why Now

マイクロ DevEx 型です。 ただし後述のとおり、この案は検査能力そのものが既に無料で配られている点で崩れます。

Why Now は弱いと判断しました。 断崖は2026年2月1日に既に過ぎており、新しい事象ではありません。 apt の既定ポリシーに記載された次の日付は Brainpool の2028年2月1日、RSA 2048 の2030年2月1日であり、いずれも遠すぎます。

アイデア 3: sunset-radar (依存している外部 API のレスポンスから廃止予告を収集し、期限が近づいた依存を通知するサービス)

対象は、外部 API に依存してサービスを組んでいる小規模事業者です。

RFC 9745 の Deprecation ヘッダと RFC 8594 の Sunset ヘッダは、まさにこの用途のために定義されています。 仕様上は、廃止予告が機械可読な形でレスポンスに載ります。

検知した生の声（リンク付きエビデンス）

実装率の実測値があります。

only one vendor sends the RFC headers — Third-Party API Deprecation and Sunset Header Watch（Apify）

この数字は、2026年9月11日に201社のエンドポイントを走査した結果として掲載されています。 出所は同種ツールの提供者自身のページであり、第三者による監査ではありません。 その点を割り引いても、規格が定めた警告の経路が事実上使われていないことは、示された手法（本文の 410 応答を読む）からも裏づけられます。

HTTP 410 Gone with a notice in the error body — 同ページ

つまり廃止予告は、ヘッダではなくエラー本文の散文として届きます。 散文は仕様ではないので、書式はベンダーごとに違います。

パターン判定 & Why Now

パターンは 新API ラッパー型の変種ですが、Why Now が立ちません。 ヘッダの未実装は数年来の慢性状態であり、今年に何かが変わったわけではありません。 そして上記のとおり、同じ設計の実装が既に公開されています。

4. リスク・反証分析 (Fail-safe Analysis)

Idea 1 が失敗する最大の理由

最大のリスクは、壊れる母数が小さすぎることです。

Chrome 自身の計測では、宣言的な XSL 処理命令の出現率はページロードの約0.001%です。 JavaScript の XSLTProcessor を含めても約0.05%にとどまります。 Justin Jackson の見積もりは50万フィードですが、これはフィードの本数であって、それを検査するために金を払う組織の数ではありません。 podcast ホスティング事業者は自社基盤側で一括して直すため、個別の検査を買いません。 残るのは自前でフィードを配信している層と機関リポジトリですが、前者は払わず、後者は払えても遅いという構造です。

対策は2つあります。

第一に、買い手を「フィードの持ち主」ではなく「説明責任のある組織」に絞ることです。 機関リポジトリと官公庁が欲しいのは修正そのものではなく、「公開している47件のうちどれが11月17日に壊れるか」を一覧で示した文書です。 成果物を検査レポートに置けば、単発でも金額が付きます。

第二に、製品の本体を XSLT から切り離すことです。 XSLT は最初の検査項目にすぎません。 ブラウザの廃止は今後も同じ形（非推奨 → Origin Trial による救済 → 全廃）で流れ続けます。 検査対象を差し替えられる構造にしておけば、11月17日を過ぎても製品は死にません。 逆に「XSLT チェッカー」として作れば、2026年11月18日に価値がゼロになります。

Idea 1 が失敗する2番目の理由

救済措置の確認という中核機能が、プラットフォーム側に取り込まれる可能性があります。

Origin Trial のトークンが正しく配られているかは、Chrome が最もよく知っています。 chrome://origin-trials のような確認画面や、トークン発行時の検証機能が追加されれば、この機能は不要になります。 ただしこれは XSLT に限らずすべての Origin Trial に効く改善であり、数年前から追加されていません。 先行期間は取れますが、堀にはなりません。

Idea 2 が失敗する理由

検査が無料のコマンド1行で終わるためです。

Sequoia の sq cert lint --fix --cert-file <鍵> が、まさにこの検査と修正を行います。 問題は検査手段の不在ではなく、検査すべきだと知らないことです。 知らない相手に道具を届ける仕事は、技術ではなく流通の問題であり、個人開発の射程から外れます。 無料スキャンで流入を作る設計も考えられますが、流入した先に売るものがありません。

Idea 3 が失敗する理由

読み取るべき信号が存在しないためです。

201社中1社という実装率は、規格に沿った検出が成立しないことを意味します。 残りはエラー本文の散文であり、これを読む仕事は解析ではなく翻訳です。 翻訳の精度はベンダーの書きぶりに左右され、誤りは利用者の移行判断を狂わせます。 加えて、同じ設計の実装が既に公開されています。

5. 参考ロードマップ (14日間MVPの想定仕様)

対象は Idea 1 (served-lint) です。

日程作業内容
Day 1前提の事前検証（実装前）。 ①DSpace を公開運用している機関リポジトリ20件の OAI-PMH エンドポイントを手作業で開き、<?xml-stylesheet ?> が実際に何件で使われているかを数える。②そのうち Origin Trial のトークンをレスポンスヘッダで配れている件数を数える。③既存の SEO クローラ（Screaming Frog 等）のカスタム抽出で同じ検出ができるかを試す。①が5件未満なら母数の仮説が崩れているので中止する。③が容易に成功し、かつ②がほぼ全件で対応済みなら、検査の価値がないので中止する。
Day 2救済の確認可能性を確かめる。 手元の静的ホスティング（Cloudflare Pages / GitHub Pages / S3）で XML に Origin-Trial ヘッダを付けられるかを実際に試す。付けられない環境が過半なら、製品の売り文句を「検査」から「代替経路の提示」へ寄せる判断をする。
Day 3-5走査の実装。サイトマップとフィード探索から XML 資源を列挙し、<?xml-stylesheet ?> と XSLTProcessor 呼び出しを検出する。検出根拠（どのバイト位置の何か）を1件ずつ記録する。
Day 6-8破損判定の実装。ヘッドレス Chrome を XSLT 無効の設定で起動し、現状の描画と撤去後の描画を比較する。「生の XML が表示される」「ダウンロードが促される」「見た目が変わらない」の3分類に落とす。Chrome 自身が言う「4分の3は壊れない」を、自分の側で再現できる形にする。
Day 9-10救済検証の実装。各 XML のレスポンスヘッダから Origin-Trial を読み、トークンの対象オリジン・機能名・有効期限を照合する。期限切れと対象違いを別々に報告する。
Day 11-12レポート出力。資源1件ごとに「検出記法 / 破損分類 / 救済状態 / 推奨対処」を並べた PDF と CSV を出す。ポリシーカレンダー（撤去日と全廃日）を先頭に置く。
Day 13-14機関リポジトリと官公庁サイトの運用担当5件へ、実際の検査結果を添えて連絡する。確認するのは「この一覧を自分で作れていたか」の1点のみ。作れていたなら仮説は死んでおり、作れていなかったなら生きている。

今回却下した候補と理由

サブスクリプション終了時の据置停止への対応（Microsoft CSP の無償猶予期間廃止、2026年5月4日以降）。 何もしないことが「月額＋3%、月額プランがなければ＋23%」という支払いに変わる構造は、今回の軸に近い形をしています。 落としたのは軸1です。 施行が既に4か月前であり、かつ判断の主体がパートナー企業とテナント管理者という、個人開発者がリーチできない層に閉じています。

移行先が存在しないエクスポート（Relay.app の終了に伴うワークフロー JSON）。 出口の義務は果たされているのに入口が存在しない、という非対称は構造として面白い題材でした。 落としたのは軸5です。 単一の終了する製品に紐づく変換器は、その製品の終了とともに需要が消えます。 14日でなく14か月かけても、寿命が延びません。

今回の探索から得られた条件

3案を並べて分かったのは、「警告と修正権限がずれている」構造それ自体は、道具の置き場を保証しないことです。

条件はもう一段細かく、次の形になります。

警告が、直せない誰かの画面には既に出ていること。

served-lint が通ったのは、警告が訪問者の DevTools と Lighthouse に実際に出ているからです。 出ているものは回収できます。 回収して配信者へ運ぶ経路が、そのまま製品になります。

sign-drift も警告は出ていました。 落ちたのは軸3と軸4であり、軸そのものは満たしています。 回収する道具が既に無料で存在したため、運ぶ仕事に値段が付きませんでした。

sunset-radar は、警告が最初から出ていません。 回収するものがないので、仕事は人力の追跡に戻ります。

前回の条件は「材料が部分的に手元にあること」でした。 今回はそこへ、警告がどこかに物として存在していることという条件が加わります。 存在していれば運べます。 存在していなければ、作るところから始めることになり、それはプラットフォームの仕事です。
