1. 調査の背景と市場の変曲点

前回（2026-09-17）は、非推奨の警告が誰の画面に出ているかを軸に置きました。 警告が別のどこかに出ているなら、それを回収して修正権限のある側へ運ぶ仕事が成立する、という結論でした。

今回は、変更そのものの形を見ます。 その変更は撤去として来るのか、それとも既定値の反転として来るのか、という区別です。

撤去は痕跡を残します。 呼び出しが 404 を返し、ビルドが失敗し、バージョン番号が上がります。 壊れたことが、壊れたという形で現れます。

既定値の反転は、そうなりません。 名前も、エンドポイントも、バージョンも変わらないまま、書いていない設定の意味だけが裏返ります。 自分が何も書かなかった箇所が、書かなかったという理由で振る舞いを変えます。

2026年10月には、この形の変更が3つ集中します。

  • Supabase の Data API 既定（2026年10月30日、全既存プロジェクトへ適用）
  • NTLMv1 SSO の BlockNTLMv1SSO（2026年10月、Audit から Enforce へ）
  • Entra ID Protection の旧リスクポリシー（2026年10月1日、退役）

3つとも、反転の日付は公表済みです。 違いは、反転したあとに旧既定の痕跡が状態として残るか、ログとしてしか残らないかでした。 先に結論を書くと、道具の置き場になったのは1つだけです。 痕跡が状態として残るなら、反転後でも差分を取る仕事が成立します。 ログとしてしか残らないなら、保持期間が切れた時点で入力そのものが消え、仕事は反転前の駆け込み作業に戻ります。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: acl-drift (Postgres の生きたカタログへ定期的に問い直し、プラットフォームが本人に代わって与えたテーブル権限と RLS の組合せを、時系列の差分として棚卸しする検査)

対象は、Supabase をはじめとするマネージド Postgres の上に本番アプリを載せている個人開発者・小規模チームです。

入力は、本番データベースへの読み取り接続1本です。 出力は、テーブル1件ずつに次の3つを付けた台帳になります。

1. anon / authenticated がそのテーブルに対して直接保持している権限（SELECT だけか、INSERT / UPDATE / DELETE / TRUNCATE まで含むか） 2. RLS が有効か、有効ならポリシーが1本でも存在するか 3. その権限が前回の観測から増えたのか、最初から在ったのか

3番目が本体です。 権限を一覧するだけなら難しくありません。 難しいのは、その権限を自分が書いたのか、プラットフォームの既定が入れたのかを区別することです。 SQL ファイルを読む静的解析は、本人が書いた宣言しか見られません。 書いていないものは、書いていないという理由で解析の視野の外にあります。

検知した生の声（リンク付きエビデンス）

最も価値の高いエビデンスは、Supabase 自身が「既存テーブルは対象外」と明言している一文です。

Existing tables are not affected in your project, they keep their current grants and stay reachable. — Breaking Change: Tables not exposed to Data and GraphQL API automatically（supabase/discussions #45329）

同じスレッドは、適用日と適用範囲を明示しています。

On October 30, 2026 the setting will be applied it to all existing projects. — 同スレッド

From this point on, new tables you create in the public schema need explicit GRANT statements before the Data API can see them. — 同スレッド

この3文の関係が、そのまま市場の形です。 10月30日に反転するのは新規テーブルの扱いだけで、それまでに作られたテーブルは旧既定の権限を保持したまま到達可能に留まります。 つまり、この変更は既存の露出を1件も直しません。 それでも「Supabase が既定を締めた」という見出しだけが流通するため、反転が済んだことを自分の安全と取り違える利用者が生まれます。

次に、当事者が実際に何を見つけたかの記録です。

anon holding TRUNCATE on 96 tables, authenticated on 109 — Supabase had granted anon TRUNCATE on 96 tables. I never wrote that line, and every check I own was green.（DEV Community）

同じ記事は、自分の検査がなぜ通り抜けたのかを書いています。

A checker reads your declarations. The nastiest defects live in what you never declared — platform defaults, upstream package behaviour, the difference between your laptop and production. — 同記事

Reading your declarations cannot, in principle, see past their edge. — 同記事

そして、著者は救済のタイミングを2つに限定しています。

only two moments catch it — the moment you adopt a platform, when you enumerate the decisions it made on your behalf, and a scheduled question asked of the live system rather than of your files — 同記事

最後に、既存ツールが埋めていない範囲を、別の当事者が名指ししています。

The public app had seventeen tables with RLS disabled and anon CRUD grants. — I scanned my own Supabase project and found 17 tables anyone could read with the anon key（DEV Community）

I never had a way to _see_ this. The Supabase Dashboard advisor warns about RLS being off. — 同記事

It does not surface the combination of 'RLS off and anon has direct grants.' — 同記事

公式ダッシュボードの助言機能は、RLS が切れていることを警告します。 警告しないのは、RLS が切れていることと直接権限が在ることの組合せです。 片方だけなら無害な構成がいくらでもあるため、単独の警告は読み飛ばされます。 組合せになった瞬間に露出が確定するのに、その組合せを名指しする画面が無い、というのがこの市場の正確な形です。

パターン判定 & Why Now

market-analysis-patterns.md の分類では 6. マイクロDevExツール型 に 5. 規制・プラットフォーム変更対応型 が重なります。

Why Now は、10月30日という日付そのものではありません。 日付が作るのは注目であって、課題ではないからです。

参入できる理由は、Supabase が「既存テーブルは対象外」と公式に書いたことで、未解決の範囲が公式文書の上で確定したことにあります。 反転を境に、プロジェクトの中は2つの世代に割れます。 10月30日以降に作られたテーブルは明示的な GRANT を必要とし、それ以前のテーブルは旧既定の権限を保持します。 同じスキーマの中に、同じ見た目で、違う規則で動く2群が同居することになります。 この分裂を一覧できる画面は、反転を実施した側が作らないと明言しています。

既存プレイヤーが解決済みの範囲と、解決していない範囲

境界線は、次のとおりです。

解決済み未解決
Supabase Dashboard AdvisorRLS が無効なテーブルの列挙RLS 無効と直接権限の組合せ（当事者が明記）
pgrls 等の静的解析SQL に書かれた RLS ポリシーの欠陥検出宣言に書かれていないプラットフォーム既定（当事者が「宣言の縁の先は原理的に見えない」と明記）
個人が公開した単発スキャナある時点のスナップショット前回観測との差分と、反転後に生まれる2世代の区別

残っているのは、生きたカタログへ定期的に同じ問いを投げ、前回との差分を出すことの1点です。 静的解析は入力が違うため届かず、ダッシュボードは組合せを出さず、単発スキャナは時系列を持ちません。

アイデア 2: ntlm-window (NTLMv1 SSO の監査イベントを強制切替の前に収集し、Enforce 後に単一サインオンが壊れる資産を事前に列挙する調査ツール)

対象は、Windows 11 24H2 / Windows Server 2025 を運用する組織の IT 部門です。

Microsoft は、監査モードと強制モードの切替日を明示しています。

In October 2026, Microsoft will set the default value of BlockNTLMv1SSO registry key to 1 (Enforce) instead of 0 (Audit). — Upcoming changes to NTLMv1 in Windows 11, version 24H2 and Windows Server 2025（Microsoft Support）

監査モードの間は、認証が通ったうえで記録だけが残ります。

The request to generate NTLMv1-credentials for a logged-on user is audited but allowed to succeed. Warning events are generated. — 同ページ

強制モードでは、生成そのものが拒否されます。

The request to generate NTLMv1-credentials for a logged-on user is blocked. Error events are generated. — 同ページ

壊れ方は部分的です。

Single Sign-On flows for these protocols would not work but manually entering credentials will continue to work even in Enforce mode. — 同ページ

軸としては正確に合致します。 監査イベントが出ているのは反転の前だけで、反転後は「誰が旧既定に依存していたか」を新たに数える手段が無くなります。

落としたのは、痕跡がログにしか無いことです。 イベントログは保持期間で消えます。 反転後に残るのは状態ではなく、消えたログの跡地です。 差分を取り続ける仕事が成立せず、10月までの駆け込み調査という一度きりの作業になります。

加えて、買い手が企業の IT 部門であり、個人開発者が到達できる販売経路を持ちません。 Microsoft 自身が Event Viewer と PowerShell の手順を公開しており、集約の仕組みは既存の SIEM が標準機能として持っています。

アイデア 3: lapse-proof (Entra ID Protection の旧リスクポリシー退役にあたり、退役後に保護が実効として失われた状態を検知し続ける監視)

対象は、Microsoft Entra ID P2 を保有し、ID Protection の旧リスクポリシーを有効にしたまま運用している組織です。

退役日は、公式ドキュメントに警告として書かれています。

The legacy risk policies configured in Microsoft Entra ID Protection will be retired on October 1, 2026. — Risk policies - Microsoft Entra ID Protection（Microsoft Learn）

移行は手作業です。 条件付きアクセスで同等のポリシーをレポート専用モードで作り、確認後に有効化し、旧ポリシーを無効化する、という3工程が案内されています。

この案件が軸に合うのは、反転の結果が「何も起きないこと」として現れる点です。 撤去されるのは保護であり、保護が無くなってもエラーは出ません。 高リスクと判定された利用者が、追加の確認を求められずにそのまま通ります。 壊れたことが、壊れていないように見えます。

落としたのは、軸4です。 Microsoft 自身が移行手順を書き、レポート専用モードという検証手段を用意し、さらに移行専用のサポート要求の起票フローまで文書化しています。 空白を埋める道具の置き場を、提供元が先に塞いでいます。 加えて、テナント管理者権限の委譲を前提とする監視であり、個人が負える責任の水準を超えます。

4. リスク・反証分析 (Fail-safe Analysis)

Idea 1 が失敗する最大の理由

最大のリスクは、露出が実際には稀であることです。

根拠になっている記録は2件で、どちらも個人が自分のプロジェクトを調べた結果です。 96テーブルや17テーブルという数字は具体的ですが、母集団を代表していません。 本人が GRANT を書いた記憶が無いだけで、テンプレートや生成ツールが書いた可能性も残ります。 「プラットフォームが勝手に入れた権限が広く残っている」という前提が崩れれば、この道具は解くべき課題を失います。

対策は、前提の確認を実装より前に置くことです。 自分と協力者の既存プロジェクトを10件ほど読み、RLS 無効と直接権限が同時に成立しているテーブルの比率を先に数えます。 比率が一桁パーセントに留まるなら、市場は無いと判断して撤退します。

次点のリスク

2つ目は、提供元が1行で塞げることです。

Dashboard advisor は既に RLS 無効を警告しています。 そこへ「かつ anon に直接権限がある」という条件を足すのは、Supabase にとって小さな変更です。 当事者が公開の場でこの欠落を指摘している以上、実装される確率は低くありません。

対策は、価値の重心をスナップショットから時系列へ移すことです。 「今どうなっているか」は塞がれますが、「前回の観測からどう変わったか」「その変更を誰のマイグレーションが入れたか」は、提供元の advisor が持たない情報です。 反転後は新旧2世代のテーブルが混在するため、この区別の需要はむしろ増えます。

3つ目は、接続情報の預かりです。

本番データベースへ読み取り接続する道具である以上、SaaS 形態は顧客の心理的障壁が高くなります。 ローカル CLI と CI 実行を既定にし、結果だけを持ち出せる形にすることで、この障壁を回避します。 軸5で3点に留めた理由もここにあります。

5. 参考ロードマップ (14日間MVPの想定仕様)

期間作業内容
Day 1-2前提の事前検証。自分と協力者の既存 Supabase プロジェクトを10件以上集め、pg_class / pg_default_acl / information_schema.role_table_grants を読み取る手書きクエリだけで、(a) RLS 無効かつ anon に直接権限があるテーブル数、(b) そのうち本人が書いた記憶の無い権限の比率、を数える。比率が低ければここで撤退する。
Day 3-4読み取りクエリの確定。テーブル権限・デフォルト権限・RLS 有効フラグ・ポリシー本数を1回のセッションで取り切る SQL を固める。ビューと関数の SECURITY DEFINER も同時に拾う。
Day 5-6台帳の出力。テーブル1件ごとに権限・RLS・ポリシー有無を並べ、露出が確定する組合せだけを先頭に寄せた一覧を出す。単一の HTML ファイルとして書き出し、外部送信を持たない。
Day 7-8差分の保存。観測結果をローカルのスナップショットとして保存し、前回との差分（増えた権限・消えたポリシー）を出す。ここがスナップショット型の既存ツールとの分岐点になる。
Day 9-10世代の区別。10月30日を境界として、反転前に作られたテーブルと以後のテーブルを分けて集計する。同じスキーマ内に異なる規則の2群が同居している状態を、そのまま画面に出す。
Day 11-12CI への組み込み。GitHub Actions から読み取り専用接続で実行し、新たな露出が生まれた時だけ失敗させる。接続情報をサービス側へ渡さない構成を既定にする。
Day 13-14個人開発者5名へのヒアリング。確認するのは「Day 1-2 で数えた露出を、あなたは自分で見つけられるか」の1点のみ。ダッシュボードで足りると答えるなら仮説は死んでおり、見つけられないと答えるなら生きている。

今回却下した候補と理由

Zendesk の旧 CC 自動移行（2026年10月28日）。

If you take no action, on October 28, 2026, all accounts still using legacy CCs will automatically undergo the migration process and move to CCs and followers. — Announcing the required migration of Support accounts to the CCs and followers experience（Zendesk）

何もしなければ移行が実施される点は、今回の軸に正確に合致します。 落としたのは、移行後にトリガ・自動化・API フィールドの意味がどう変わるかを、公式文書が明示していないことです。 変わると書かれていない以上、壊れる範囲を先に言語化できません。 境界線が引けない候補は、差別化の根拠が無いものとして落とします。

GitHub Actions の可変タグから SHA への移行。 2026年のセキュリティロードマップが依存ロックと不変リリースを掲げており、可変参照が既定である現状は反転の前段にあります。 落としたのは軸4です。 SHA へのピン留めは Dependabot と複数の OSS ツールが既に担い、GitHub 自身がワークフローのロックファイルを実装予定と公表しています。 提供元が実装を予告している領域は、個人の置き場になりません。

今回の探索から得られた条件

3案を並べて分かったのは、「既定値が反転する」という構造それ自体は、道具の置き場を保証しないことです。

条件はもう一段細かく、次の形になります。

反転したあと、旧既定の痕跡が状態として残ること。ログとしてしか残らないなら、道具ではなく作業になる。

acl-drift が通ったのは、テーブルの権限が反転後も生きたカタログに残るからです。 残るから、いつでも問い直せます。 いつでも問い直せるから、定期的に問い直す道具に月額を払う根拠が立ちます。

ntlm-window が落ちたのは、痕跡がイベントログにしか無いからです。 保持期間が切れれば入力が消え、反転後は新たに数える手段もありません。 残るのは10月までの駆け込み作業で、繰り返し使う道具にはなりません。

lapse-proof が落ちたのは、痕跡がポリシーオブジェクトの存在そのもので、退役と同時に消えるからです。 消えたことを検知しようにも、比較対象が先に無くなります。

前回の条件は「警告が別のどこかに出ていること」でした。 今回はそこへ、痕跡の置き場が状態か、ログかという条件が加わります。 状態なら何度でも問えて、ログなら保持期間の分しか問えません。
