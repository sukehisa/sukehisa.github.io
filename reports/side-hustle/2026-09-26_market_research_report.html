1. 調査の背景と市場の変曲点

前回（2026-09-25）は、Snowflake のパスワード遮断や Cloudflare Tunnel のフィールド削除など、インフラ層の強制切断時計を検証しました。 手元のコードを変更していなくても、外部プラットフォームの締め切り到来によって非対話型バッチが突然死する現象を扱いました。

今回は、AI アプリケーションと API 連携における「プラットフォーム側の提供撤退」と「実行境界の権限破綻」を検証します。 クラウドベンダーが手厚く用意していた便利機能が突然打ち切られる現象と、プロトコルの普及によって新たに生じたセキュリティの死角です。

生成 AI 領域では、ベンダーが一度提供した機能であっても、戦略の転換やインフラ負荷によって突然非推奨・閉鎖される事例が頻発しています。 管理画面上でプロンプトや評価を完結させていたチームは、ベンダーの都合でコードベースへの退避を余儀なくされます。 同時に、Agentic AI の普及に伴い標準となった Model Context Protocol（MCP）では、複数のツールを接続した途端にツール間の境界線が崩壊し、権限昇格（Confused Deputy）の脆弱性が急増しています。

2026年9月下旬現在、以下の3つの切断と摩擦が開発現場で顕在化しています。

  • OpenAI による Reusable Prompts（v1/prompts）および Hosted Evals の完全シャットダウン（2026年10月31日に新規編集が禁止され、11月30日に API ごと消滅する）
  • MCP マルチサーバー運用における Cross-Tool Confused Deputy 脆弱性の多発（Web 検索等の低権限ツールの出力に仕込まれたインジェクションにより、エージェントが高権限ツールを無断実行する）
  • Google Ads API v22 の完全停止（2026年10月7日に全リクエストが失敗し、コード内の旧 GAQL クエリが沈黙する）

3者とも、公式からは「新しいバージョンへ移行せよ」「ベストプラクティスに従え」という抽象的な指針しか与えられていません。 移行作業を泥臭く自動化し、あるいは実行時の安全境界をローカルで担保するツールの需要が急拡大しています。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: prompt-evac (OpenAI Reusable Prompts & Hosted Evals 終了に伴う全アセット一括エクスポート & Git/Promptfoo 変換 CLI)

対象は、OpenAI プラットフォーム上の Reusable Prompts（プロンプトオブジェクト）や Hosted Evals、Agent Builder を本番・検証運用してきた AI アプリ開発チームです。

入力は2つです。 1. OpenAI API キー（Organization 管理者権限） 2. 移行先のプロジェクトリポジトリパス

出力は次の3点です。 1. プラットフォーム上に保存された全プロンプト、バージョン履歴、Hosted Evals データセットの一括ダウンロード 2. OpenAI 推奨形式に準拠した TypeScript / Python 型安全プロンプトモジュールの自動コード生成 3. Evals データセットの Promptfoo 互換 YAML テストスイートへの自動変換、およびコード内の prompt: { id: "..." } 参照箇所の書き換えパッチ

本体は2番目と3番目です。 単に JSON を落とすだけなら curl でも可能です。 本質的な価値は、OpenAI がダッシュボードで行っていた変数バインディングやバージョン追跡を、開発チームの Git ワークフロー（PR、型チェック、CI での Promptfoo 評価）へシームレスに移植し直すことです。

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、OpenAI 公式ドキュメント自身が v1/prompts の廃止と 2026年11月30日のシャットダウンを明記している事実です。

Treat prompts as application code. Store prompt content in named modules, build dynamic sections with typed function arguments, and review prompt changes in the same pull requests as the product behavior they support. OpenAI is deprecating reusable prompt objects in the API. Prompt creation will be de-emphasized beginning June 3, 2026, and v1/prompts is scheduled to shut down on November 30, 2026. — Prompting | OpenAI API（Prompt deprecation and application migration）

さらに、開発者コミュニティ（r/OpenAI、OpenAI Developer Community）では、これまでダッシュボードでプロンプトを非エンジニアがホットフィックスしていた運用の崩壊と移行負荷に対する困惑が広がっています。

API support for "Prompt Objects" is scheduled to be shut down on November 30, 2026...This will require developers to move prompt management directly into their application code, potentially reducing the speed of iteration and hotfixing capabilities... — Community discussions on OpenAI Prompt Objects & Evals shutdown

画面上で管理していたチームは、10月31日までに全プロンプトを退避させなければ、11月30日以降に本番リクエストが物理的に破綻します。 しかし、過去の全バージョンと評価ケースを手作業でコードへ書き起こす工数は膨大です。

パターン判定 & Why Now

パターンは規制・プラットフォーム変更対応型とワークフロー糊付け・連携型の複合です。

Why Now は、2026年10月31日の Read-only 化と 11月30日のサービス停止期限です。 あと約1ヶ月で編集不能になり、約2ヶ月で API エンドポイントが削除されます。 プラットフォーム依存から Git 管理への移行を余儀なくされるため、今すぐ実行しなければならない切実な締切が存在します。

境界線は以下のとおりです。

  • 解決済み: OpenAI ドキュメントに記載された「コードでプロンプトを管理すべき」という抽象的なベストプラクティス。
  • 未解決: OpenAI 上に点在するプロンプトオブジェクトと評価データセットをワンコマンドで抽出し、型安全な関数モジュールと Promptfoo テストスイートへ変換・置換する移行自動化パイプライン。

アイデア 2: mcp-deputy-shield (MCP マルチサーバー環境における Cross-Tool 権限昇格・Confused Deputy 遮断用ゼロインフラ軽量ローカルプロキシ)

対象は、Claude Code、Cursor、Windsurf、または自作の LangChain / LlamaIndex スクリプトにおいて、複数の MCP サーバー（Web 検索、GitHub、ローカルファイル、DB等）を接続して自律エージェントを運用しているエンジニアです。

入力は2つです。 1. MCP クライアントと各 MCP サーバー間の通信ストリーム（stdio または SSE） 2. ツールの信頼度定義ポリシー（例: Web 検索＝Untrusted, ファイル書き込み＝Privileged）

出力は次の3点です。 1. 未信頼ツールの出力が後続の特権ツール呼び出しに波及する「動的汚染（Taint）」のリアルタイム追跡 2. Confused Deputy 兆候（低権限ツールの直後に予期せぬファイル走査やシステムコマンドが要求された場合）の即時インターセプトと対話的 JIT 承認 3. パス走査（/proc/self/environ や ~/.ssh へのアクセス）や不正引数の決定論的フィルタリング

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、Cloud Security Alliance（CSA）が発行した MCP セキュリティ指針において、Confused Deputy が最も警戒すべき脅威として名指しされている事実です。

The Confused Deputy problem is specific case of privilege escalation which occurs when an agent unintentionally misuses its elevated privileges to act on behalf of another agent or user. For example, an agent with broad write permissions might be prompted to modify or delete critical resources while following a seemingly legitimate request from a less-privileged agent. In MCP systems, this threat is particularly concerning because agents can interact autonomously across tools and services, making it difficult to detect misuse. — MCP Risks CISOs Should Prepare For | CSA（Cloud Security Alliance）

さらに、2026年には MCP エコシステムで CVE-2026-77255 をはじめとする脆弱性が公表され、低特権のツール経由で環境変数や機密トークンが読み出される事例が相次いでいます。

エージェント自身は「ユーザーの目的を達成するための推論」としてツールを連鎖させているため、自分がプロンプトインジェクションに操られていることに気づけません。 外部の決定論的なプロキシが、ツール呼び出しの遷移グラフを監視して遮断する必要があります。

パターン判定 & Why Now

パターンはマイクロDevExツール型と価格破壊・ローカルファースト型の複合です。

Why Now は、2026年秋の MCP ツールチェーンの爆発的普及と、それに伴うセキュリティ事件の表面化です。 開発者が手元のコーディングエージェントに 5〜10 個の MCP サーバーを接続するのが日常化した結果、単一ツールでは安全でも組み合わせることで危険が生じる「複合脆弱性」が現実の脅威になっています。

境界線は以下のとおりです。

  • 解決済み: FastMCP 等による個々の MCP サーバーエンドポイントでの OAuth 認証。
  • 未解決: 手元のエージェント環境（Claude Code や Cursor）にワンコマンドで挟み、複数サーバーを跨ぐツール呼び出しの連鎖から動的汚染を検知して遮断する軽量ローカルプロキシ。

アイデア 3: gads-sunset-audit (Google Ads API v22 の 2026年10月7日完全停止に向けたコードベース静的監査 & 廃止フィールド・クエリ構文の自動パッチ CLI)

対象は、Google Ads API を利用して自社の自動入札、予算管理、レポーティングバッチを運用しているマーケティングエンジニアや広告代理店の開発者です。

入力は2つです。 1. 社内の広告スクリプト・バッチ処理のリポジトリ群（Python, Node, PHP 等） 2. Google Ads API の廃止・非互換変更定義データベース

出力は次の3点です。 1. コードベース内に残存する Google Ads API v22 呼び出しおよび SDK 初期化箇所の静的検出 2. GAQL（Google Ads Query Language）内の廃止・改名フィールド（Performance Max 関連の指標変更等）の静的特定 3. v24/v25 互換の構文への自動書き換えパッチ（Unified Diff）の生成

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、Google Ads 公式デベロッパーブログが 2026年10月7日の完全停止を最終警告している事実です。

Google Ads API v22 will sunset on October 7, 2026. Starting on this date, all v22 API requests will begin to fail. Migrate to a newer version prior to October 7, 2026 to ensure your API access is unaffected. — Google Ads API v22 sunset reminder（Google Ads Developer Blog）

公式の Google Cloud Console では、プロジェクト全体で「v22 のリクエストが月間何件発生しているか」という aggregate なグラフしか提供されません。 「どのリポジトリのどのファイルのどのクエリが壊れるか」は現場のエンジニアが自力でコードを探す必要があります。

パターン判定 & Why Now

パターンは規制・プラットフォーム変更対応型とマイクロDevExツール型の複合です。

Why Now は、2026年10月7日という目前の停止期限（あと11日）です。 広告運用のバッチが停止すると、広告配信の停止や過剰出稿による直接的な金銭的損失が発生するため、緊急度が極めて高い状態にあります。

境界線は以下のとおりです。

  • 解決済み: Google Cloud Console によるプロジェクト単位での API バージョン別コール数グラフ。
  • 未解決: マルチリポジトリのコードベースに散らばった v22 依存箇所と、GAQL クエリ内の廃止フィールドの静的検知および自動互換パッチ。

4. 各アイデアの詳細分析 & 参考ロードマップ

最有力候補: prompt-evac (総合 21/25 点, Tier 1)

リスク・反証分析

  • 失敗する理由・最大のリスク: 1. 一過性需要（One-off Utility）のリスク: 2026年11月30日のシャットダウンを過ぎると、移行需要そのものが急減する。 2. 大手移行先の公式スクリプト提供: Promptfoo や LangSmith、Braintrust 等が自社への囲い込みとして「OpenAI からのワンクリックインポートツール」を公式に無料配布するリスク。
  • 対策: 1. 単なるエクスポートで終わらせず、移行後の「プロンプト変更 PR に対する自動回帰テスト CI GitHub Action」として継続価値を提供する。 プロンプトをコードに移したことで生じる「非エンジニアが直せなくなった課題」を、GitHub PR 上でプレビュー・評価できる仕組みに拡張する。 2. 競合が「自社 SaaS へのインポート」に閉じるのに対し、本ツールは「ローカルの標準 TypeScript / Python コードとオープンソースの Promptfoo 設定」へ中立に出力することで、ベンダーロックインを嫌う開発者の支持を獲得する。

参考ロードマップ (14日間 MVP)

  • Day 1: 【前提の事前検証】OpenAI の v1/prompts および v1/evals API から、バージョン履歴やメタデータが完全な形で取得可能か、権限の境界（Admin キーの要件）をテストスクリプトで検証する。
  • Day 2-4: OpenAI API からプロンプト一覧・履歴を全件取得し、ローカルに JSON/YAML 形式で保存するバックアップ CLI コアの実装。
  • Day 5-7: 取得したプロンプト定義から、型安全な TypeScript 関数モジュール（引数を埋め込んで messages 配列を返す関数）を自動生成するコードジェネレータの実装。
  • Day 8-10: Evals データセットを Promptfoo 互換のテスト設定（promptfooconfig.yaml）へ変換するマッパーの実装。
  • Day 11-12: コードベース内をスキャンし、旧 v1/prompts 呼び出し箇所を新関数インポートへ置換する codemod サブコマンドの実装。
  • Day 13: ドキュメント作成、テスト自動化、GitHub リポジトリ公開、Product Hunt / Hacker News へのローンチ告知。
  • Day 14: 初期ユーザーからのフィードバック収集と、未対応のプロンプト構文（複雑な構造化パラメータ等）のエッジケース改修。

第二候補: mcp-deputy-shield (総合 20/25 点, Tier 2)

リスク・反証分析

  • 失敗する理由・最大のリスク:
    • Claude Desktop や Cursor などのクライアント側、あるいは FastMCP などの基盤フレームワーク側が、将来のアップデートで標準の権限管理・サンドボックス機能を組み込んでくる「プラットフォーム標準化」のリスク。
  • 対策:
    • クライアントの特定実装に依存しない stdio / SSE レベルの透過プロキシに徹する。プロキシならではの「複数クライアント間での共通ポリシー共有」や「ローカル完結の監査ログ可視化 WebUI」を差別化要素とする。

参考ロードマップ (14日間 MVP)

  • Day 1: 【前提の事前検証】Claude Code および Cursor の MCP 設定（claude.json / settings.json）において、既存の MCP サーバーコマンドの先頭にプロキシバイナリを挟んでもレイテンシやハンドシェイクに問題が生じないかを検証する。
  • Day 2-5: MCP の JSON-RPC 通信を透過的に中継し、ツール定義と呼び出し引数をログ出力するプロキシコアの実装。
  • Day 6-8: ツールの信頼度（Untrusted vs Privileged）に基づく動的汚染（Taint）トラッカーと、未信頼入力後の特権ツール呼び出しを一時停止する JIT 承認機構の実装。
  • Day 9-11: パストラバーサル（危険なシステムパスの読み書き）を即時遮断するルールエンジンの実装。
  • Day 12-14: CLI 設定ウィザードの作成（既存の claude.json からワンクリックでプロキシを自動挿入）とドッグフーディング。

第三候補: gads-sunset-audit (総合 19/25 点, Tier 2)

リスク・反証分析

  • 失敗する理由・最大のリスク:
    • 2026年10月7日という期日があと11日に迫っており、ツールの認知を獲得して購入・実行してもらうまでのマーケティングリードタイムが極端に短い。
  • 対策:
    • 広告代理店やアドテクコミュニティ（Twitter/X, LinkedIn）のインフルエンサーに直接アプローチし、無料スキャンレポートを提供して即時拡散を図る。

5. まとめと推奨ネクストアクション

本リサーチでは、直近で生じた「プラットフォームの撤退」「マルチサーバー境界の権限昇格」「広告APIの完全停止」という3つの変曲点を検証しました。

最も推奨されるアイデアは、総合スコア 21点（Tier 1）を獲得した prompt-evac です。 OpenAI 公式による Reusable Prompts の廃止期限（2026年10月31日 Read-only、11月30日 完全シャットダウン）が間近に迫っており、世界中の AI プロダクトチームにおいて「放置すれば本番が死ぬ」切実な作業が発生しています。

OpenAI が推奨する「コード管理への移行」と「Promptfoo への移行」をワンコマンドで完了させるマイグレーションツールとして、即時の需要獲得と Git 管理プロンプトのテスト支援への継続展開が見込めます。 まずは Day 1 の事前検証（OpenAI API からのメタデータ・バージョン履歴取得仕様の確認）に着手することを推奨します。
