1. 調査の背景と市場の変曲点

前回（2026-09-28）は、Kubernetes Ingress-NGINX のコミュニティ版 EOL に伴う Gateway API 移行時のアノテーション脱落や、AWS Proton の完全遮断など、基盤層の標準移行で生じるカスタム設定の切り捨てを検証しました。 公式移行ツールが最小共通仕様しか面倒を見ず、現場の独自ルールがこぼれ落ちる構造を扱いました。

今回は、「長年固定化されていたフォーマットや暗号規格が突然変更・終了し、現場の通信や資産が孤立する」変曲点を検証します。 何十年も動いてきたレガシー仕様の打ち切りと、次世代セキュリティ標準の強制適用という、一見正反対に見える事象が同時に現場へもたらす互換性の断絶です。

提供元はセキュリティや保守効率を理由に、古いプロトコルの遮断や新規格の既定有効化を断行します。 しかし、現場のネットワーク機器や過去のファイル資産は、その急激な変化に対応できません。 その結果、パケットのサイレントドロップや、過去文書へのアクセス遮断といった障害が表面化します。

2026年9月末現在、以下の3つの断絶が現場を直撃しています。

  • Microsoft Publisher の Microsoft 365 からの完全退役（2026年10月1日に M365 サブスクライバーのアプリ起動権限が喪失し、学校・自治体・中小企業に眠る数百万本の .pub ファイルが閲覧・編集不能になる）
  • Google Cloud Load Balancing における耐量子暗号（X25519MLKEM768）の既定許可（2026年10月に既定動作が反転し、肥大化した TLS ClientHello が企業のファイアウォールや Middlebox で断片化・サイレントドロップされる）
  • AWS FinSpace / Managed kdb Insights の完全終了（2026年10月7日にコンソールと API が完全遮断され、クオンツ・市場分析の時系列データと q スクリプトがアクセス不能になる）

3者とも、公式からは「別ツールへ手動移行せよ」「次世代規格をテストせよ」という指針しか示されていません。 失われる資産を吸い上げて現代的なオープン標準へ着地させるツール、および通信経路の断裂を事前に検知するツールの需要が急浮上しています。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: pub-to-open (Microsoft Publisher 2026年10月1日完全遮断に伴う .pub ファイル一括抽出・レイアウト完全保持 SVG/HTML/Canva/InDesign 互換変換 CLI & マイグレーションスイート)

対象は、小中学校・高校、自治体、非営利団体、中小企業、印刷会社などで、過去数十年にわたり Microsoft Publisher で広報誌、チラシ、会報、賞状、名刺テンプレートを蓄積してきた現場担当者・IT管理者です。

入力は2つです。 1. ローカルまたはファイルサーバー内の .pub ファイル群（単一ファイルまたはフォルダ再帰指定） 2. 出力ターゲット形式の指定（表示専用 PDF/SVG/HTML5 Canvas、または再編集用 InDesign IDML / Canva 互換 JSON / Word docx）

出力は次の3点です。 1. テキストボックスの配置、二段組、画像アスペクト比、ワードアート、回転角を1ピクセル単位で保持した高忠実度レンダリング（SVG / PDF / HTML） 2. 再編集可能なベクター・レイヤ構造を維持したモダンフォーマット（InDesign IDML、Canva 互換 JSON）への変換出力 3. フォルダ内の一括スキャン、埋め込み画像の個別抽出、フォント欠落警告、および変換忠実度スコアをまとめた移行診断 HTML レポート

本体は1番目と2番目です。 単にテキストを抜き出すだけなら、既存のオープンソースライブラリ（libmspub）でも可能です。 本質的な価値は、Microsoft 公式すら「レイアウトが変わる」と匙を投げた複雑な多段レイアウトや図形配置を解析し、Canva や InDesign、Web 上で即座に再利用できる構造化データへ無劣化でトランスパイルすることです。

パターン判定 & Why Now

パターンは価格破壊・ローカルファースト型とコミュニティ特化型、および規制・プラットフォーム変更対応型の複合です。

Why Now は、2026年10月1日という Microsoft 365 サブスクライバー向け完全遮断期限（あと2日）です。 10月1日を迎えると Office アプリ一覧から Publisher が消滅し、二度と自力でファイルを開くことができなくなるため、緊急の救済需要が爆発します。

境界線は以下のとおりです。

  • 解決済み: 公式 PowerShell スクリプトによる、Publisher 起動環境下での機械的な一括 PDF 印刷（Publisher が動いている Windows 環境が必須）。
  • 未解決: Publisher が起動しなくなった後の環境でも、バイナリから直接レイアウト座標・フォント・図形を抽出し、Canva や InDesign 等の現役ツールで崩れずに再編集できる形式へトランスパイルする独立ツール。

アイデア 2: pqc-frag-guard (耐量子暗号 PQC / ML-KEM-768 展開に伴う TLS ClientHello 断片化・Middlebox 遮断静的解析 & 検証プローブ CLI)

対象は、外部向け Web サービスや API を運用し、企業内 LAN、学校、公的機関からのアクセス遮断・タイムアウト苦情に直面するインフラエンジニア、SRE、ネットワークセキュリティ担当者です。

入力は2つです。 1. 自社サービスのエンドポイント URL（またはホスト名一覧） 2. クラウドプロバイダ（Google Cloud, AWS, Cloudflare）のロードバランサ / SSL 設定

出力は次の3点です。 1. ML-KEM-768（FIPS 203）公開鍵（1,184バイト）を含む実寸大 TLS ClientHello（1,400〜1,600バイト）を生成し、対象ネットワーク経路における TCP MTU 境界パケット断片化および Middlebox（ファイアウォール、DPI、WAF）によるサイレントドロップの有無を判定する自動プローブ結果 2. Google Cloud Load Balancing などの SSL ポリシー設定（DEFAULT / DEFERRED / ENABLED）の監査と、2026年10月の既定変更で影響を受けるエンドポイントの可視化 3. インシデント回避のための処方箋（SSL ポリシーの DEFERRED 指定、ロードバランサでの ClientHello 分割対応、MTU 最適化設定）の自動生成

本体は1番目と2番目です。 単に耐量子暗号が有効かどうかを調べるだけなら、ブラウザのセキュリティ設定でも確認できます。 本質的な価値は、手元のローカル環境（MTU 9000 等のクリーンな回線）では絶対に再現しない「途中の古いエンタープライズファイアウォールが断片化された ClientHello を破棄する現象」をシミュレートし、本番障害が起きる前に危険なエンドポイントを炙り出すことです。

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、Google Cloud 公式ドキュメント自身が 2026年10月に既定の動作を変更し、X25519MLKEM768 を既定で有効化することを明記している事実です。

Post-quantum key exchange modes The post-quantum key exchange setting lets you specify one of the following: ENABLED. The load balancer uses X25519MLKEM768 key exchange with clients that advertise support for it. DEFAULT. The load balancer disallows X25519MLKEM768 key exchange until October 2026. This is the default behavior if no SSL policy is attached. DEFERRED. The load balancer disallows X25519MLKEM768 key exchange until October 2027. Timeline: Now: Disabled by default, enabled only when set to ENABLED After October 2026: Enabled by default, disabled when set to DEFERRED After October 2027: Enabled always — SSL policies overview | Cloud Load Balancing | Google Cloud Documentation

さらに、技術者コミュニティ（Hacker News）でも、ML-KEM 導入における最大の実装課題として Middlebox の干渉が議論されています。

It should be noted that if indeed there has not remained much time until a usable quantum computer will become available, the priority is the deployment of FIPS 203 (ML-KEM) for the establishment of the secret session keys that are used in protocols like TLS or SSH... Middlebox Interference: A common concern in the transition to new TLS features—including those involving PQ key exchanges—is the behavior of 'middleboxes'. These network devices sometimes mishandle unexpected packets or extensions in the ClientHello, leading to dropped connections or 'blackholing' of traffic. — Discussion on FIPS 203 (ML-KEM) and TLS Deployment Challenges | Hacker News

従来の楕円曲線暗号では公開鍵共有はわずか 32 バイトでしたが、ML-KEM-768 では 1,184 バイトに跳ね上がります。 ClientHello が一般的なインターネットの MTU（1,400〜1,500バイト）を超過するため、TCP レベルでパケットが2つに分割されます。 古い DPI アプライアンスやファイアウォールは、分割された ClientHello の SNI（Server Name Indication）をパースできずに破棄し、利用者の画面には原因不明の「接続がリセットされました」が表示されます。

パターン判定 & Why Now

パターンはマイクロDevExツール型と規制・プラットフォーム変更対応型の複合です。

Why Now は、2026年10月の Google Cloud Load Balancing における既定動作反転（Phase 2 ロールアウト）です。 これまでオプトインだった耐量子暗号が、SSL ポリシーを明示していない全ロードバランサで一斉に有効化されるため、10月から社内ネットワークや特定の顧客環境で突発的な通信障害が多発します。

境界線は以下のとおりです。

  • 解決済み: 各クラウドや CDN が提供する「PQC を有効化・無効化するスイッチ」。
  • 未解決: 自社のサービスエンドポイントが、実際のインターネット経路上の Middlebox（断片化非対応ルータや古いファイアウォール）によってサイレントドロップされるリスクを事前に外形検査するテストツール。

アイデア 3: finspace-kdb-bridge (AWS FinSpace / Managed kdb Insights 2026年10月7日完全終了に伴うクオンツ時系列データ・q スクリプト抽出 & ローカル kdb+/DuckDB 移行 CLI)

対象は、AWS FinSpace を利用して市場データ（株価、板情報、ティックデータ）のカタログ管理を行い、Managed kdb Insights 上でバックテストやオプション価格計算の q スクリプトを実行してきたヘッジファンド、アセットマネジメント、クオンツエンジニアです。

入力は2つです。 1. AWS FinSpace アカウント情報（Managed kdb Insights クラスタ設定、S3 データセット ARN） 2. 移行先の実行環境指定（自前 EC2 上の kdb+ インスタンス、または DuckDB / Polars ベースのローカル分析環境）

出力は次の3点です。 1. FinSpace HDB（Historical Database）内のパーティション化された時系列バイナリデータを、AWS 推奨の「CSV 中間ファイル」を介さずに直接 S3 / ローカルストレージへゼロロス抽出するパイプライン 2. 自前 kdb+ クラスタを AWS EC2 / EBS 上に自動プロビジョニングする Terraform / OpenTofu コード 3. 既存の q 言語クエリを、最新の DuckDB / Polars（Python）SQL へ変換する構文マッピングガイドおよび検証スクリプト

本体は1番目と2番目です。 単に S3 からオブジェクトをダウンロードするだけなら AWS CLI でも可能です。 本質的な価値は、AWS 公式ドキュメントが推奨する「CSV に一度エクスポートして手動インポートする」という高頻度取引データでは破綻する手順を回避し、kdb+ のネイティブバイナリ構造を保ったまま自前の安価な環境へ安全にスライドさせることです。

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、AWS 公式ドキュメント自身が 2026年10月7日の完全終了とリソース削除を明記し、かつデータ抽出手順として CSV 経由という非効率な方法を案内している事実です。

After careful consideration, we decided to end support for Amazon FinSpace, effective October 7, 2026. Amazon FinSpace will no longer accept new customers beginning October 7, 2025. As an existing customer with an Amazon FinSpace environment created before October 7, 2025, you can continue to use the service as normal...After October 7, 2026, you will no longer be able to use Amazon FinSpace...After October 7, 2026, you will no longer be able to access the Amazon FinSpace Dataset Browser or Amazon FinSpace Managed kdb Insights features... To extract your data from Amazon FinSpace, you can leverage python, along with kdb's pyKX feature, to connect to your Amazon FinSpace HDBs and then extract database table contents, store in CSV format, and then import into your new self-managed kdb Insights environment. — Amazon FinSpace end of support | AWS Documentation

数億行・数テラバイトに及ぶティックデータを CSV に変換すれば、ファイルサイズは数倍に膨れ上がり、日時型やシンボル型のメタデータが欠落し、再インポートに数日を要します。 FinSpace を利用していた金融現場は、10月7日までに安全に自前クラスタへ移行する自動パイプラインを強く求めています。

パターン判定 & Why Now

パターンは規制・プラットフォーム変更対応型とワークフロー糊付け・連携型の複合です。

Why Now は、2026年10月7日の完全終了期限（あと8日）です。 期限を過ぎると Managed kdb Insights のクラスタもコンソールも完全消滅するため、データを退避できる物理的猶予が今しか残されていません。

境界線は以下のとおりです。

  • 解決済み: AWS re:Post に掲載された、pyKX を使って小規模テーブルを CSV に吐き出す単体サンプルスクリプト。
  • 未解決: ペタバイト級の HDB パーティション構造を崩さず、S3 間コピーと自前 EC2 kdb+ / DuckDB クラスタへの自動再配線をワンストップで完走させる移行 CLI。

4. 最有力アイデアの深掘りと検証計画 (MVP: pub-to-open)

アイデア概要

pub-to-open は、Microsoft Publisher の退役によってアクセス不能となる .pub ファイルを、レイアウト崩れを起こさずに SVG、HTML5 Canvas、InDesign IDML、Canva 互換 JSON へ一括変換する特化型ローカル CLI / マイグレーションツールです。

リスク・反証分析

最大の前提崩壊リスクは、「ユーザーが過去の .pub ファイルを再編集することを諦め、Microsoft 公式の案内どおり単なる閲覧用 PDF に変換して済ませてしまうこと」です。

この反証に対する検証と対策は以下のとおりです。

  • 反証検証: 学校、PTA、自治体、中小企業において、Publisher の最大の価値は「毎年・毎月使い回すテンプレート（広報誌の枠組み、賞状、会報）」にあります。単なる PDF 化では文字の差し替えや日付変更ができず、ゼロから Canva や Word でデザインを作り直す手間が発生します。
  • 対策: 単なる「PDF / 画像へのレンダリング」にとどまらず、テキストボックスを編集可能なオブジェクトとして保持したまま出力する「再編集用フォーマット（Canva 互換 JSON、InDesign IDML、HTML 編集可能ブロック）」を主軸として訴求します。

参考ロードマップ（14日間MVP）

ロードマップの初日には、前提の「事前検証」を必ず配置します。

  • Day 1: 前提検証（仮説の生死判定）
    • 公開されている学校・自治体・官公庁の .pub テンプレート（Web 上にインデックスされている実ファイル）を 50 件収集。
    • 公式推奨の「PDF 経由 Word 変換」および LibreOffice Draw の変換を実行し、レイアウト崩れ（枠の重なり、文字あふれ、画像位置ズレ）の発生率を定量測定。崩れ発生率が 70% を超えることを確認して変換需要を確定させる。
  • Day 2〜4: コア変換エンジンの開発
    • libmspub および C++ / Python バインディングを利用し、.pub バイナリからテキストフレーム、ベクターシェイプ、埋め込みラスター画像を抽出。
    • 各要素の絶対座標（バウンディングボックス）とフォントサイズ、カラー情報を JSON AST として正規化。
  • Day 5〜7: ターゲットフォーマット出力の実装
    • 高忠実度 SVG レンダラの実装（Web ブラウザで完全再現可能なベクター出力）。
    • Canva 互換 JSON および InDesign IDML（XML アーカイブ）へのトランスパイルロジック構築。
  • Day 8〜10: CLI インターフェース & 一括診断機能
    • pub-to-open convert --dir ./templates --format svg,canva --out ./converted コマンドの実装。

  • Day 11〜12: パッケージング & 配布準備
    • Windows および macOS 向けスタンドアロンバイナリ（PyInstaller / Rust ラッパー）のビルド。
