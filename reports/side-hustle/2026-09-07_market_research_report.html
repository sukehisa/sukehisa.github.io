1. 調査の背景と市場の変曲点

前回（2026-09-06）の終わりに、次の探索軸を宣言しました。 結果が金額として確定する、かつその金額の元になる数字が買い手の内部ではなく公開領域にあり、買い手側の入力が識別子だけで済む、という条件です。

今回、この軸で探索した結果を先に書きます。 入力を識別子まで縮める条件は満たせましたが、出力を金額として確定させる条件は満たせませんでした。

見つかったのは、金額ではなく権限を出力する構造でした。 買い手が差し出す入力は lockfile や名簿といった識別子の集合であり、突き合わせる相手はレジストリの公開物や法文です。 入力の軽さという点で軸2と軸5は取り戻せます。 一方で出力が「いくら消えるか」ではなく「いま何が許されているか」であるため、軸3（収益性）は前回の水準へ届きません。

この交換を承知したうえで、今回は一つの構造に絞って探索しました。 一度与えた許可が、許可された実体が変わった後も効き続けるという構造です。 以下の3つの変曲点は、いずれもこの構造が2026年後半に一斉に表面化したことを示しています。

変曲点 1: npm 12 が「暗黙の実行」を終わらせ、承認という工程を全チームへ配った

GitHub は2026年6月9日、npm v12 の破壊的変更を予告しました。

allowScripts defaults to off: npm install will no longer execute preinstall, install, or postinstall scripts from dependencies unless they are explicitly allowed in your project. — GitHub Changelog, 2026-06-09

同じ告知には、依存の取得元に関する2つの既定変更も並んでいます。 --allow-git の既定が none となり、Git 依存が解決されなくなります。 --allow-remote の既定も none となり、HTTPS の tarball 依存が解決されなくなります。

ユーザーに求められる作業は、告知に明記されています。

approve the ones you trust, and commit the updated package.json — GitHub Changelog, 2026-06-09

npm 12 は2026年8月にリリースされました。 つまりいま、npm を使うすべてのチームが「どれを信頼するか」を一度だけ決めて、その決定をリポジトリへ commit している最中です。

この工程はライブラリの保守側にも波及しています。 Microsoft の vscode-eslint には、告知の4日後に issue が立ちました。

npm v12 will block scripts by default (affecting this extension's postinstall script) — Gabriel Boehme, 2026-06-13, microsoft/vscode-eslint Issue #2190

変曲点 2: 承認の中身が空であることを、推進側と観測側の双方が認めている

承認という工程が配られた一方で、承認の判断材料は配られていません。

第一に、承認が反射になるという指摘があります。

by the third time a build breaks at 5pm because some transitive dependency needs its postinstall hook, the approval becomes a reflex — OpenSourceMalware, 2026-06-10, The Pros and Cons of NPM v12's Security Improvements

同じ記事は、規制が攻撃を消すのではなく移動させるとも書いています。

if install scripts are off by default, some package authors...will move the work somewhere NPM can't turn it off — OpenSourceMalware, 2026-06-10, 同上

第二に、承認の前段にある「出所の証明」が、この種の攻撃に対して機能しないことが実証されています。 2026年8月4日に keyv のメンテナが侵害され、CHAINDROP と呼ばれるワームが自己増殖しました。

The worm did not forge that signature. It earned it, the way a legitimate release would. — Louis Columbus, 2026-08-05, VentureBeat

Provenance attestation answers whether a package came from the pipeline it claims. It does not answer whether the human or token that triggered that pipeline was supposed to. — Louis Columbus, 2026-08-05, 同上

署名は「正規の経路から来たか」に答え、許可リストは「正規の名前か」に答えます。 どちらも「そのスクリプトが何をするか」には答えません。

第三に、許可リストの意味論がパッケージマネージャごとに違います。 npm はバージョンで固定しますが、pnpm は名前のみで許可します。 その帰結を、pnpm の issue が名指ししています。

Currently, pnpm silently ignores unused entries in onlyBuiltDependencies. — martinfrancois, pnpm/pnpm Issue #10253

If a package is listed in onlyBuiltDependencies but doesn't currently have scripts, it is effectively a "dormant" privilege. — martinfrancois, 同上

If that package is later compromised...and the attacker re-introduces a malicious preinstall script, pnpm will execute it immediately because the package is already whitelisted. — martinfrancois, 同上

エコシステム全体の状況は、Andrew Nesbitt が整理しています。 npm 11 系の挙動は助言に止まると書かれています。

Behaviour in 11.x is advisory: scripts still execute, an end-of-install summary names anything unreviewed — Andrew Nesbitt, 2026-06-05, Install-script allowlists

Bun の挙動は、許可リストの追加が既定を壊す形になっています。

opting a single package in drops the default-trusted set entirely — Andrew Nesbitt, 2026-06-05, 同上

変曲点 3: 2026年12月1日、日本の内部通報が「誰が読めるか」を刑事罰の射程に入れる

改正公益通報者保護法が2026年12月1日に施行されます。 改正の中身は、通報の入口ではなく通報の取扱いに踏み込んでいます。

通報者を探索する行為を禁止し、これに違反してされた合意等の法律行為を無効 — 東京弁護士会

罰則も新設されています。

６月以下の拘禁刑又は30万円以下の罰金、両罰規定あり — 東京弁護士会

3,000万円以下の罰金刑 — 東京弁護士会

体制整備義務と従事者指定義務の対象は、規模で切られています。

常時使用する従業員が301人以上 — 東京弁護士会

BUSINESS LAWYERS は、行政側の権限強化も併記しています。

立入検査権 — BUSINESS LAWYERS

ここで起きているのは、変曲点2と同じ構造です。 従事者の指定は名簿という台帳に書かれ、実際に通報を読める範囲は共有メールボックスや共有ドライブの権限設定に書かれています。 名簿は法務が持ち、権限設定は情報システムが持ちます。 両者を突き合わせる工程は、どちらの職務にも属していません。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: script-jury (npm 12 の承認待ちパッケージについて、スクリプト本文・挙動の分類・前回承認バージョンとの差分・名前のみ許可リストの休眠特権を出し、承認の判断材料そのものを供給するローカル CLI)

package.json の allowScripts、pnpm の allowBuilds、yarn / bun の許可設定、および lockfile を入力に取るローカル CLI です。 出力はリスクスコアではありません。 この承認が何を許すのかを、承認の直前に文章と差分で出します。

行は4種類です。

第一に、承認待ちの各パッケージについて、レジストリの tarball から取り出した preinstall / install / postinstall の本文そのものを出します。 第二に、その本文を挙動で分類します。node-gyp rebuild のようなネイティブビルド、prebuilt バイナリの取得、ネットワークアクセス、シェル経由の実行、エンコードされた文字列の実行を区別します。 第三に、同一パッケージの前回承認バージョンとのスクリプト差分を出します。差分が空なら、承認の更新は形式だけで済みます。 第四に、pnpm / yarn / bun の名前のみ許可リストについて、現在スクリプトを持たない承認済みパッケージを休眠特権として名指しします。

加えて、npm 12 の残り2つの既定変更（--allow-git と --allow-remote）で解決不能になる依存を、同じ走査のついでに列挙します。

検知した生の声（リンク付きエビデンス）

第一に、承認という工程が判断材料なしで配られている点です。 推進側ではなく批判側の記述が、この空白を最も明確に述べています。

by the third time a build breaks at 5pm because some transitive dependency needs its postinstall hook, the approval becomes a reflex — OpenSourceMalware, 2026-06-10, The Pros and Cons of NPM v12's Security Improvements

第二に、承認の前段にある証明が、実際の攻撃を止めなかった点です。

Provenance attestation answers whether a package came from the pipeline it claims. It does not answer whether the human or token that triggered that pipeline was supposed to. — Louis Columbus, 2026-08-05, VentureBeat

同じ記事は、npm 12 が守った範囲も正確に限定しています。

JFrog confirmed that on npm 12 or newer, where preinstall hooks are off by default, the malware does not run at install time. Every organization still on an older npm, and most enterprises upgrade slowly, remained exposed. — Louis Columbus, 2026-08-05, 同上

第三に、名前のみ許可リストが休眠特権を作るという指摘が、パッケージマネージャの issue として当事者から出ている点です。

If a package is listed in onlyBuiltDependencies but doesn't currently have scripts, it is effectively a "dormant" privilege. — martinfrancois, pnpm/pnpm Issue #10253

第四に、承認の列挙自体が完全ではないという一次報告がある点です。 npm 本体の issue に、承認コマンドと強制コマンドの結果が食い違うという報告が立っています。

One command tells me it does not need to be whitelisted, another command tells me I cannot install dependencies unless it is whitelisted. — 報告者, npm/cli Issue #9562

この食い違いは、fsevents のようなプラットフォーム限定の optional 依存で起きています。 macOS で作った許可リストは、Linux の CI で正しいとは限りません。

パターン判定 & Why Now

パターンはマイクロ DevEx 型です。 毎日発生する作業ではありませんが、npm 12 への移行という一度の作業で全チームが必ず通る地点にあります。

Why Now は3点です。 第一に、npm 12 が2026年8月にリリースされ、移行作業がいま進行中である点です。 第二に、CHAINDROP が2026年8月4日に発生し、「正規の資格情報で publish された悪意あるバージョン」が現実の事象として観測された点です。 第三に、許可リストの意味論がパッケージマネージャごとに分かれたまま固まりつつある点です。npm はバージョン固定、pnpm と yarn と bun は名前のみで、移行の判断は各チームが個別に行っています。

既存プレイヤーが解決済みの範囲と、解決していない範囲

解決済みは、どのパッケージがスクリプトを持つかの列挙と、その承認の記録です。 npm approve-scripts が列挙し、package.json が記録します。pnpm の approve-builds も同じ役割を持ちます。 @lavamoat/allow-scripts は、この仕組みを持たない旧環境へ許可リスト運用を後付けします。 Socket.dev はパッケージ全体のリスクを採点し、ホスト型で提供します。

解決していないのは、承認の対象となるスクリプトが何をするかです。 列挙は名前を出し、記録は名前を残しますが、本文はどこにも出てきません。 そして採点型の製品は、スコアという抽象へ畳んだ結果を返すため、「この行が curl でバイナリを取ってくる」という具体を承認画面の隣に置きません。

境界線は明確です。 先客は「承認すべきか」を答えようとし、本案は「承認すると何が起きるか」を見せます。 前者は判断を代替し、後者は判断を可能にします。

アイデア 2: koeki-reach (従事者名簿と、通報が実際に届く場所の権限設定を突き合わせ、2026年12月1日時点で通報を読める非従事者を名指しするローカル検査)

従事者名簿（CSV）と、通報の受け口の識別子（共有メールボックスのアドレス、フォーム回答スプレッドシートの ID、共有ドライブのフォルダ ID）を入力に取るローカル検査です。 Google Workspace の Admin SDK / Drive API、または Microsoft Graph をサービスアカウントで読み、いま実際に通報へ到達できる主体の一覧を作ります。

出力は3種類です。

第一に、従事者名簿に無いのに通報を読める主体です。転送設定、代理アクセス、グループのネスト、リンク共有、退職者の残存アカウントを含みます。 第二に、名簿にあるのに到達できない主体です。指定はされたが権限が付いていない、という逆方向の乖離です。 第三に、通報の閲覧履歴が記録される構成になっているかどうかです。記録されない構成では、「探索していない」ことを事業者側が示せません。

検知した生の声（リンク付きエビデンス）

第一に、法が禁じる対象が「探索」という行為そのものである点です。

通報者を探索する行為を禁止し、これに違反してされた合意等の法律行為を無効 — 東京弁護士会

第二に、違反の帰結が刑事罰である点です。

６月以下の拘禁刑又は30万円以下の罰金、両罰規定あり — 東京弁護士会

3,000万円以下の罰金刑 — 東京弁護士会

第三に、行政が現場を見に来る権限を得た点です。

立入検査権 — BUSINESS LAWYERS

第四に、義務の対象が規模で明確に切られている点です。

常時使用する従業員が301人以上 — 東京弁護士会

買い手の母数は、この一行で確定します。

パターン判定 & Why Now

パターンは規制・プラットフォーム変更対応型です。

Why Now は2点です。 第一に、施行日が2026年12月1日であり、85日後である点です。 第二に、改正が「窓口を作ったか」から「取扱いが適切か」へ検査の焦点を移した点です。窓口の有無は既存の内部通報 SaaS が売っており、既に埋まっています。取扱いの実態は、SaaS を導入した企業でも、旧来の共有メールボックスが並行して生きていれば穴が残ります。

既存プレイヤーが解決済みの範囲と、解決していない範囲

解決済みは、新しい窓口の提供です。 内部通報 SaaS は匿名受付と案件管理を提供し、その中では権限が設計されています。 規程の雛形は士業が提供し、従事者名簿の作り方も解説されています。

解決していないのは、既に動いている受け口の実態です。 多くの組織は、SaaS を入れた後も総務宛の共有メールボックスとフォームを残します。 そこに誰が到達できるかは Workspace の設定に書かれており、名簿の側からは見えません。

境界線はこうです。 先客は「正しい窓口」を売り、本案は「残っている窓口」を数えます。 SaaS 事業者は、自社へ移行しない限り解けない問題として顧客の既存環境を扱うため、既存環境の穴を独立に数える製品を自社の主張の中へ置けません。ここに利益相反があります。

アイデア 3: release-path (自分が公開権限を持つパッケージについて、次のリリースが成立するかを公開経路と資格情報の観点から事前判定する検査)

リポジトリのワークフロー定義と、npm 側の公開設定を入力に取る検査です。 出力は、次にタグを打ったとき、そのパッケージが実際に公開されるかどうかの判定です。

npm の公開経路は2026年に3つの変更を同時に受けています。 第一に、trusted publishing の対応 CI が限定されています。

Trusted publishing currently supports: GitHub Actions (GitHub-hosted runners), GitLab CI/CD Pipelines (GitLab.com shared runners), CircleCI (CircleCI cloud). — npm/documentation

Self-hosted runners are not currently supported but are planned for future releases. — 同上

第二に、設定を作った日付によって既定の挙動が変わります。

Configurations created after Sep 03, 2026 are automatically set to allow npm stage publish, and you can choose whether to also permit direct publishing with npm publish. — npm Docs

4日前を境に、新しく作った設定は既定で staging へ入ります。 CI は成功し、しかしパッケージは installable になりません。

第三に、トークン側の締め付けが進んでいます。

検知した生の声（リンク付きエビデンス）

self-hosted runner の除外について、当事者の反応が公式ディスカッションに並んでいます。

enterprises use self hosted runners...should still be capable of publishing packages safely without having to manually update a token every 7 days — MarshallOfSound, GitHub community Discussion #174507

トークンの再発行についても、粒度の再現が問題として挙がっています。

if a token of mine expires, I probably need one with the same granularity to replace it — ericcornelissen, 同上

推進側の設計そのものへの異議も出ています。

they are not actually addressing the ask for native 2FA workflows and even making one secure workflow even harder — wesleytodd, 同上

パターン判定 & Why Now

パターンはマイクロ DevEx 型です。 Why Now は、Sep 3 の既定変更が4日前である点と、classic token の廃止が進行中である点です。

既存プレイヤーが解決済みの範囲と、解決していない範囲

解決済みは、個々の事実の公開です。 対応 CI、設定日ごとの既定、トークンの期限は、いずれも npm の文書に書かれています。

解決していないのは、自分の資産への当てはめです。 30個のパッケージを持つメンテナが、どれが次のリリースで失敗するかを一覧で見る手段はありません。

境界線は引けますが、幅が狭いというのが今回の判定です。 理由は第3節で述べます。

配点理由

Idea 1: script-jury — 18点 (Tier 2)

  • タイミング 4: npm 12 が2026年8月にリリースされ、承認という工程が全チームへ一斉に配られました。CHAINDROP という具体的な事故が2026年8月4日に起きており、動機の説明に仮定を要しません。母数は npm を使う全チームで、3案で最大です。減点材料: 全員に共通する期日がありません。npm 11 系の挙動は助言に止まるため、アップグレードを遅らせれば作業も遅れます。「今月中に決めろ」という一斉のトリガーが立たないため、5点は付けられません。
  • 技術的実現可能性 4: lockfile を読み、レジストリから tarball を取り、package.json の scripts を読むという経路は確立しています。差分の計算も平易です。2週間で本文表示と差分までは確実に届きます。減点材料: 価値の中心は「分類」にあり、そこは網羅性の勝負です。node-gyp rebuild の判定は容易ですが、ビルドスクリプトが shell 経由で分岐する実装、prebuilt バイナリの取得をラッパーへ隠す実装は個別対応になります。分類の質が低いと、出力が本文の再掲に落ちます。5点は付けられません。
  • 収益性 3: 個人開発者は無料版で足ります。払うのは複数リポジトリを CI で回すチームであり、月額15ドル前後のライセンスが現実的な水準です。減点材料: 上に Socket.dev のような採点型 SaaS がおり、価格の天井を作っています。買い手から見れば「スクリプトの本文だけを見せる道具」は、パッケージ全体を採点する製品の部分機能に見えます。加えて、承認は移行時の一度で終わる作業であり、継続課金の根拠は「依存を更新するたびに差分を見る」という運用が定着した後にしか立ちません。4点は付けられません。
  • 競合優位性 3: 境界線は明確です。列挙と記録は npm 自身が持ち、採点は SaaS が持ちますが、承認画面の隣に本文と差分を置く製品はありません。休眠特権の検出は pnpm の issue が未実装として残っており、実装されるまでは空白です。減点材料: 大手が3か月で真似したら、というより、npm 本体が approve-scripts の出力へスクリプト本文を1行足せば、価値の半分が消えます。実装は数行であり、しかも issue #9562 のような不整合報告が積まれている以上、本体側に改善の動機があります。参入障壁が製品の構造ではなく本体の優先順位に依存しており、4点は付けられません。
  • 個人開発適性 4: ローカル CLI として完結し、lockfile を外部へ送りません。取得先は公開レジストリのみで、認証も不要です。減点材料: npm / pnpm / yarn / bun の4種について、許可リストの位置と意味論を追随する固定費が発生します。pnpm は v11 で onlyBuiltDependencies を allowBuilds へ統合しており、この種の変更は今後も起きます。追随を止めると、誤った休眠特権を報告し続けます。5点は付けられません。

Idea 2: koeki-reach — 16点 (Tier 2)

  • タイミング 4: 施行日が2026年12月1日と単一で定まり、85日後です。罰則が刑事罰であり、予算確保の動機は3案で最も強い。義務の対象も「常時使用する従業員が301人以上」と一行で確定します。減点材料: その一行が母数の上限も決めます。国内の301人以上の事業者に限られ、Idea 1 より二桁小さい。5点は付けられません。
  • 技術的実現可能性 3: Google Workspace の Admin SDK と Drive API、Microsoft Graph のいずれも、権限の読み取りは文書化された既知の経路です。突き合わせ自体は集合演算です。減点材料: 導入の手前に壁があります。サービスアカウントの作成とドメイン全体の委任には管理者の作業が要り、その作業を依頼する時点で商談になります。「ダウンロードして走らせる」という個人開発の最短経路が使えません。4点は付けられません。
  • 収益性 3: 法務・内部統制の予算が付く領域であり、年額数万円は成立します。減点材料: 出力が診断結果であり、穴を塞げば用が済みます。継続課金の根拠は「権限が再び増えていないか」の定期実行に依存し、それは購買時点では価値として説明しにくい。加えて、この領域の支出は監査法人やコンサルの見積もりと同じ表に並び、数万円の道具は「まず人に見てもらう」に負けます。4点は付けられません。
  • 競合優位性 3: 境界線は引けます。内部通報 SaaS は新しい窓口を売り、既存環境の穴を数えません。利益相反も構造として実在します。減点材料: 大手が3か月で真似したら、SaaS 各社が「移行前診断」を無料で付けるだけで、購買理由が消えます。しかも彼らにとって診断は営業の入口であり、無料で配る動機があります。無料の営業ツールと有料の道具が正面から当たる構図であり、4点は付けられません。
  • 個人開発適性 3: ローカル CLI としてサービスアカウントの鍵を手元で使う設計にすれば、OAuth アプリの審査もホスティングも不要になります。24時間の監視も要りません。減点材料: 扱うのが「誰が通報を読めるか」という情報であり、誤りが刑事罰に隣接します。到達経路を1つ見落とせば「安全」と誤報し、買い手はそれを根拠に対応を止めます。個人名義で売る際の信頼要求と問い合わせ負荷が、Idea 1 より一段重い。4点は付けられません。

Idea 3: release-path — 14点 (Tier 3)

  • タイミング 3: Sep 3 の既定変更は4日前であり、鮮度は3案で最高です。減点材料: 母数が小さすぎます。買い手は npm パッケージの公開権限を持つ人に限られ、そのうち複数パッケージを抱えて一覧を必要とする層はさらに一部です。市場規模の観点で4点は付けられません。
  • 技術的実現可能性 3: ワークフロー定義から runner の種別と publish コマンドを取るのは静的解析であり、平易です。減点材料: 判定の核である「その trusted publisher 設定が直接 publish を許しているか」を、外部から読める保証がありません。読めない場合はユーザーの自己申告で補うことになり、自動判定という価値の半分が崩れます。前提が確認できていない状態で4点は付けられません。
  • 収益性 2: OSS メンテナは無料を前提とする層です。企業のリリース基盤担当は払える立場ですが、その層は同じものを内製します。誰がいくら払うかを具体的に書けません。 基準に従い、3点は付けられません。
  • 競合優位性 2: いま空白であることは確かです。減点材料: 空白の理由が「難しいから」ではなく「小さいから」です。参入障壁が存在せず、npm が公開時に警告を1行出せば、あるいは npm doctor に項目を1つ足せば消えます。3案で最も模倣が容易であり、3点は付けられません。
  • 個人開発適性 4: ローカル完結で、低保守です。減点材料: npm 側の仕様が現在進行形で動いており、設定日ごとの既定という時限的なルールを追い続ける必要があります。5点は付けられません。

Idea 3 は Tier 3 に落ちたため、提案から外します。 第2節に残したのは、「変曲点は鋭いが市場が小さい」という型の失敗例として、次回以降の探索で同じ判断を繰り返さないためです。

4. リスク・反証分析 (Fail-safe Analysis)

3案に共通する最大のリスク

今回の3案は、いずれも出力が「権限の一覧」であり、金額でも期限でもありません。

これは第1節に書いたとおり、前回宣言した第三条件（金額として確定する）を満たせなかったことの直接の帰結です。 結果として、軸3（収益性）の平均は2.67点となり、前回の3.67点から1点下がりました。 軸2と軸5を取り戻す代わりに、軸3を支払っています。

権限の一覧は、買い手にとって「危ないかもしれない」という情報です。 金額の一覧が「戻る」「消える」という確定した結果であるのに対し、権限の一覧は確率の提示に止まります。 確率に対する支払意思は、確定額に対する支払意思より構造的に低くなります。

対策は、3案とも出力を「確定した事実」の側へ寄せることです。 Idea 1 であれば「危険なスクリプト」ではなく「前回承認時と本文が変わったパッケージが3件ある」という事実を主出力に置きます。 Idea 2 であれば「リスクがある」ではなく「名簿にない7名がいま通報を読める」という事実を主出力に置きます。 どちらも、判定ではなく計数です。

Idea 1 が失敗する最大の理由

npm 本体が approve-scripts の出力にスクリプト本文を追加することです。

これは技術的に数行の変更であり、issue #9562 のような不整合報告が積まれている以上、本体側に改善の動機があります。 起きた場合、本案に残るのは「差分」と「休眠特権」と「4種のパッケージマネージャ横断」の3点だけになります。

対策は、最初からその3点を製品の中心に置くことです。 本文表示は入口であって商品ではない、という設計を初日から取ります。

もう一つの反証は、そもそも誰も承認を吟味しないという可能性です。 OpenSourceMalware が書いた「approval becomes a reflex」が正しければ、判断材料の需要そのものが存在しません。 この反証は、ロードマップの初日で検証します。

Idea 2 が失敗する最大の理由

買い手が「診断」ではなく「移行」を選ぶことです。

穴が見つかった組織の自然な反応は、穴を塞ぐことではなく、内部通報 SaaS へ一本化することです。 その場合、本案は SaaS の営業資料になり、売上は SaaS 側へ流れます。

対策は、SaaS へ移行した後も残る問いへ出力を寄せることです。 すなわち「旧窓口を閉じたか」「閉じた後も転送設定が生きていないか」という、移行の完了を確認する用途です。

5. 参考ロードマップ (14日間MVPの想定仕様)

対象は最有力候補の script-jury です。

Day作業完了条件
1前提の事前検証。自分と知人の5リポジトリで npm approve-scripts --allow-scripts-pending を実行し、承認待ちのパッケージ数を数える。同時に、各リポジトリの担当者へ「承認したパッケージのスクリプト本文を見たか」を聞く。5リポジトリの平均承認待ち数が5件以上あり、かつ「本文を見た」と答えた担当者が半数未満であること。満たさなければ全体を破棄する。「reflex になっている」という反証が正しければ、判断材料の需要は存在しない。
2lockfile 走査の実装。npm / pnpm / yarn / bun の4形式から、依存の名前とバージョンを取り出す。4形式すべてで依存一覧が出る。
3-4tarball 取得とスクリプト抽出。レジストリから該当バージョンを取り、preinstall / install / postinstall の本文を出す。取得結果はローカルへキャッシュする。承認待ちの全件について本文が表示される。
5-6差分の実装。許可リストに記録された前回承認バージョンと現在バージョンのスクリプト本文を比較し、変化した件数を出す。「本文が変わったパッケージ N 件」が主出力の先頭に来る。
7-8休眠特権の検出。pnpm / yarn / bun の名前のみ許可リストについて、現在スクリプトを持たない承認済みパッケージを列挙する。pnpm の実リポジトリで休眠特権が検出できる。
9挙動分類の第一版。node-gyp rebuild 相当のネイティブビルドと、それ以外を2分する。細かい分類はまだ作らない。承認待ちの大半が「ネイティブビルド」へ落ち、レビュー対象が絞られる。
10プラットフォーム差の対応。optional 依存と os / cpu 制約を読み、他プラットフォームでのみ必要になるパッケージを別枠で出す。issue #9562 の fsevents のケースが再現・検出できる。
11Day 1 の5リポジトリで再検証。差分と休眠特権の出力を見せ、承認判断が変わるかを聞く。5リポジトリ中3つで「この出力を見て承認を保留した項目がある」こと。
12-13検証結果に基づく修正。分類を増やすか、差分の見せ方を変えるかを、聞いた内容で決める。修正が1点に絞られている。
14公開。README に「npm 本体が本文表示を実装したら、本ツールの価値は差分・休眠特権・横断の3点に縮む」と明記する。反証条件が公開物に書かれている。

Day 1 は実装ではありません。 承認が既に反射になっているなら、判断材料を作っても誰も読みません。 需要の生死を14日のうち1日で判定し、駄目なら残り13日を使わない、という設計です。

6. スクリーニング結果と提案候補 (参考情報)

  • 最優先で検証すべき候補: script-jury (総合18点、Tier 2)。3案で唯一、母数（npm を使う全チーム）と境界線（列挙と採点の間にある「本文と差分」の空白）の両方が説明できています。ただし着手は Day 1 の結果を見てから判断すべきであり、承認が既に反射になっているなら全体を破棄します。
  • 次点: koeki-reach (総合16点、Tier 2)。期日と罰則の鋭さは3案で最高ですが、導入の手前に管理者作業という壁があり、個人開発の最短経路が使えません。着手するなら、知人の情報システム部門を1社確保してからにすべきです。
  • 今回却下した候補と理由:
    • MCP ツールスキーマの無言の変化の検知: 2026年9月3日に、248の公開 MCP サーバを1日に2回巡回した実測が公開されました。説明文が1バイトも変わらないままスキーマまたはアノテーションが変わった例が17件記録されています。「no MCP client re-prompts. Approval happens once. Nothing re-derives it」という記述は、本レポートの探索軸そのものです（mcp-pin）。しかし Vercel AI SDK が2026年7月9日公開の 7.0.19 で fingerprintTools と detectToolDrift を標準搭載しており、Schema Drift Gate（有償ホスト型）、MCP Vitals、driftguard も既に存在します。フレームワーク本体が同じ機能を持った時点で境界線が引けず、軸4を2点として総合18点でも Tier 2 下位、かつ 2026-08-23 レポートの MCP 検査案との重複判定に触れるため却下しました。
    • npm 12 の --allow-git / --allow-remote 既定変更で壊れる依存の検知: 期日も影響も明確ですが、走査対象が Idea 1 と完全に同一であり、重複判定フィルタの「機能追加版にすぎない」に該当します。Idea 1 の副次出力として吸収しました。
    • HubSpot Classic CRM Cards 停止（2026年10月31日）への移行検査: 期日は鋭く、HubSpot 自身が View Swapping Tool と Converter を提供しています。プラットフォーム側が移行支援を出し切っている領域であり、境界線が引けないため却下しました。
    • EU AI Act の適用日変更に伴う義務の再判定: Digital Omnibus により Annex III の高リスク義務が2027年12月2日へ、Annex I が2028年8月2日へ延期される一方、透明性義務の一部は2026年8月2日のまま据え置かれました。「どの義務が動き、どれが動かなかったか」の混乱は実在しますが、2026-08-23 レポートで EU AI Act Article 50 を扱っており、重複判定に触れるため却下しました。
    • Windows 10 消費者向け ESU の期限変更追跡: 2026年10月13日で終わるはずだった消費者向け ESU が、正式な告知ではなく文書の更新により2027年10月12日へ延長されました。ベンダーが期限を静かに動かすという事象は本レポートの構造と一致しますが、2026-09-04 レポートで「公式回答同士が食い違うモデル退役日」を扱っており、重複判定に触れるため却下しました。
  • 13回連続で Tier 1 に到達していません。 今回の交換関係を整理します。 軸2（実現可能性）の平均は3.33点、軸5（個人開発適性）の平均は3.67点であり、いずれも前回（3.33点・2.67点）から維持または改善しました。 狙いどおり、入力を識別子（lockfile・名簿）まで縮めたことで、買い手のデータへ深く入り込む必要がなくなりました。 一方で、軸3（収益性）の平均は2.67点へ落ちました。 前回の3.67点から1点の低下です。原因は第4節に書いたとおりで、出力が金額ではなく権限だからです。 ここまでの4回で、同じ交換が繰り返し現れています。買い手の内部へ深く入るほど出力は金額に近づき、入力を軽くするほど出力は判断材料に留まります。 軸2・軸5と軸3が、入力の深さを媒介にトレードオフの関係にあります。 次回の探索軸は、この媒介を外しにいきます。入力が識別子だけで済み、かつ出力が金額として確定する位置、すなわち金額の元になる料率が公開されていて、買い手が差し出す識別子1つで金額が一意に決まる構造を探します。公示価格、公定料率、法定の補償額、公開された料金表が候補です。買い手のデータ量ではなく、公開された料率の存在が金額を作れるかどうかが、3つの軸を同時に立てられるかの分かれ目になります。
