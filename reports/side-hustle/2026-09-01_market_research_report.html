1. 調査の背景と市場の変曲点

前回（2026-08-31）の探索で得た結論を、そのまま今回の探索軸に据えます。 期限そのものではなく、その期限までにしか観測できないデータが何であるかを先に問う、という軸です。 期限は誰にでも見えており、期限に反応する製品は誰でも作れます。 一方、期限を境に観測できなくなる値は、その日を過ぎた者が後から集め直せません。

この軸で見たとき、2026年9月の変曲点は3つに絞れました。

1つ目は、Chrome のリリース間隔の半減です。 2026年9月8日の Chrome 153 から、安定版が4週ごとではなく2週ごとに出ます。 同時に、Chrome ウェブストアの審査待ち行列は2026年4月から滞留しており、Google 自身が滞留を認めたまま解消の見通しを示していません。 9月8日より前の「4週ケイデンス下での審査待ち時間」は、9月8日を過ぎると二度と観測できません。

2つ目は、パートタイム・有期雇用労働法の改正です。 2026年10月1日から、パート・有期雇用労働者を雇い入れる際に「待遇の相違の内容・理由等に関する説明を求めることができる旨」の明示が義務になります。 明示は書式の問題ですが、その先にある説明は各社の賃金規程と運用を読まなければ書けません。

3つ目は、iOS 27 の一般提供です。 iOS 27 SDK でビルドしたアプリは、UISceneDelegate に対応していないと起動時点で終了します。 起動しないため通知登録も走らず、既存ユーザーのデバイストークンが静かに死にます。

この3件は、期限の性質が異なります。 1つ目は観測の窓が閉じる期限、2つ目は書類の締切、3つ目はビルド構成に紐づく強制です。 以下では、それぞれに対して個人が入れる位置を探しました。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: cws-window (差し戻しを潰す提出前検査と、審査待ち実測にもとづく提出タイミングの決定)

  • ターゲット: Chrome 拡張機能で収入を得ている個人開発者と小規模チーム。インストール数が数万から数十万規模で、修正を出せない期間がそのまま損失になる層を中心に置く。
  • 解決する課題: 拡張機能の開発者にとって、審査待ち行列は制御できない。制御できるのは「差し戻されないこと」と「いつ提出するか」の2つだけである。ところがこの2つはどちらも、判断材料が公開されていない。Google は審査所要時間を公表せず、差し戻しの判定基準も提出後にしか分からない。9月8日以降は安定版が2週ごとに出るため、提出の集中と Chrome 側の破壊的変更の両方が倍の頻度で来る。

検知した生の声（一次ソース）

Chrome ウェブストアの審査滞留について、Google の担当者が2026年4月24日に投稿しています。

We've experienced a surge in new extensions being submitted to the Chrome Web Store causing longer-than-expected wait times.

このスレッドに、月20万インストールを持つ開発者が返信しています。

I get over 200,000 installs a month and right now I'm trying to release a fix for a bug...now there's nothing I can do other than wait 28 days.

別の開発者は、実績のある拡張機能が新規提出に押し出される構造を問題にしています。

It is extremely unfair if a bunch of new users submitting new extensions with no history cause developers with history...to be delayed.

収入との直結を述べた投稿もあります。

Many of us depend on our extensions for income, and delays like this can directly translate into financial loss.

これに対する Google の回答は、次のとおりです。

We're actively discussing and investigating different approaches...but there's nothing concrete yet that we can share.

出所: PSA: Increase in review times for submissions to the Chrome Web Store（chromium-extensions グループ）

この4月の滞留の上に、9月8日のケイデンス変更が重なります。

Starting September 2026, Chrome will move to a two-week release cycle, from the current four-week cycle.

Chrome 153 on September 8th

Google は開発者に対して、ベータでの検証を求めています。

developers test with the beta to keep up to date with any upcoming changes that might impact your sites and applications

出所: Get features faster with Chrome's two-week release cycle（Chrome for Developers）

ケイデンス変更が審査待ち行列に与える影響を、外部の解説はこう書いています。

The queue will see roughly twice the update volume from the developer ecosystem around each stable release date.

Review queue pressure typically spikes in the 48 hours before and after a Chrome stable release. Doubling the releases doubles those spikes, and queue times during those windows may lengthen.

保守モードの拡張機能については、猶予が縮む点を具体的に述べています。

A newly deprecated API method that breaks a feature in Chrome 155 (let's say) now arrives six weeks after the initial Beta warning instead of eight weeks. For a developer who checks in quarterly, that window matters.

出所: Chrome's 2-Week Release Cycle (Sept 2026): What Changes

Web 開発全体への影響として、検証の信頼性が落ちるという指摘もあります。

A two-week release model makes end-stage compatibility testing increasingly unreliable. Tests may pass early in the week, Chrome may update days later, and user-facing issues can surface immediately after deployment.

Teams built for resilience will move with the browser. Teams built around reactive fixes may spend the next year or so trying to catch up.

出所: Google Chrome Faster Release Cycle Reshapes Web Development（DesignRush）

パターン判定 & Why Now

6. マイクロDevExツール型を主とし、5. 規制・プラットフォーム変更対応型が重なります。

Why Now は日付で確定しています。 9月8日を境に、安定版の間隔が4週から2週へ変わります。 審査待ち行列の混雑は安定版リリース日の前後48時間に立つため、混雑の山の数が年13回から年26回へ増えます。 提出日をどこに置くかという問いは、これまで存在しなかった問いです。

そして本案の核心は、ここに置く判断材料が誰の手元にもないことです。 Google は待ち時間を公表せず、開発者は自分の1件しか知りません。 4週ケイデンス下での待ち時間の分布は、9月8日を過ぎれば取り直せません。 この基準値は、今週中に測り始めた者だけが持てます。

既存プレイヤーが解決済みの範囲と、未解決の範囲

解決済みの範囲は3つあります。 第一に、審査ポリシーの文書化である。権限は機能の実装に必要な最小限に絞ること、単一目的の記述と掲載情報を一致させることが、Program Policies に明記されている。 第二に、アップロードの自動化である。chrome-webstore-upload 系の CLI が提出そのものを自動化している。 第三に、拡張機能の統計である。インストール数や評価の推移を追う外部サービスは複数ある。

未解決の範囲は2つです。 1つ目は、提出前に「この提出は差し戻されるか」を判定する工程です。 ポリシーは文章として公開されているが、手元のビルドがそれに適合しているかを機械的に照合する手段は提供されていない。 差し戻しは1回で数週間を失い、異議申立ては1回しか許されない。 それでも判定は提出後にしか得られない。

2つ目は、いつ提出するかの判断です。 混雑の山が安定版リリース日の前後48時間に立つことは外部の解説が指摘しているが、実測値ではない。 Google 自身が「共有できる具体策はまだない」と述べており、この空白は当事者に認識されたまま埋まっていない。

アイデア 2: taiguu-brief (正社員との待遇差の説明資料を、規程の版に紐づけて組み立てるローカルツール)

  • ターゲット: パート・有期雇用労働者を抱える国内の中小企業（小売・飲食・介護・宿泊）と、その労務を請け負う社会保険労務士事務所。顧問先を10社から50社抱える社労士事務所を主たる販路に置く。
  • 解決する課題: 2026年10月1日から、雇い入れ時に「説明を求めることができる旨」を明示する義務が生じる。明示そのものは通知書の1行であり、労務SaaSがひな形を更新すれば終わる。本当の負荷は、実際に説明を求められた後に発生する。事業主は「通常の労働者」を選定したうえで、待遇項目ごとに相違の内容と理由を述べなければならない。この材料は賃金規程・就業規則・実際の運用に散らばっており、求められてから作ると間に合わない。

検知した生の声（一次ソース）

厚生労働省の Web マガジンは、追加される明示事項を次のように書いています。

「待遇の相違の内容・理由等に関する説明を求めることができる」旨を明示することが必要となります

説明の方法についても、選択肢が限定されています。

「資料を活用し、口頭により説明する方法」または「説明すべき事項を全て記載した分かりやすい内容の資料を交付する等の方法」のいずれかにより説明することが必要になります

同時に、同一労働同一賃金ガイドラインが改定され、賞与・退職金・手当・福利厚生について不合理と認められる例が明確化されます。

出所: 2026年10月からパートタイム・有期雇用のルールが変わります―3つの改正ポイント（厚生労働省 Webマガジン）

社会保険労務士による解説は、明示すべき事項の条文上の位置づけを次のように示しています。

法第14条第２項の規定による説明（待遇の相違の内容・理由等に関する説明）を求めることができる旨

比較の基準となる労働者については、「通常の労働者」すなわち「いわゆる正規型の労働者」と定義され、企業が自社の呼称（正社員など）に読み替えてよいとされています。 違反した場合の制裁は、行政指導で是正されない場合に「10万円以下の過料」です。

出所: 【2026年10月改正】パートタイム労働者・有期雇用労働者に対する労働条件の明示事項の追加（京都うえにし社会保険労務士事務所）

パターン判定 & Why Now

5. 規制・プラットフォーム変更対応型に、2. コミュニティ特化型（社労士という職能コミュニティ）が重なります。

Why Now は施行日です。 10月1日以降に締結・更新する契約から、明示が義務になります。 更新時期が集中する事業者では、9月中に通知書の書式を確定する必要があります。

ただし Why Now の本体は明示ではありません。 明示が義務化されると、労働者側に「説明を求める」という選択肢が制度として告知されます。 説明の請求は、明示の義務化によって増えます。 説明の材料を持たない事業者は、請求が来てから慌てることになります。

既存プレイヤーが解決済みの範囲と、未解決の範囲

解決済みの範囲は、労働条件通知書の書式です。 人事労務SaaSは10月1日に合わせて明示事項を追加するはずであり、社労士向けの書式集も更新されます。 ここへ個人が入る余地はありません。

未解決の範囲は、説明資料の中身です。 「基本給の決定要素が正社員と異なる理由」「賞与を支給しない理由」「通勤手当の支給基準の違い」は、各社の規程と運用にしか書かれていません。 ひな形を配っても埋まらず、埋めるには規程を読む工程が要ります。 この工程は、外部のSaaSが持っていないデータの上でしか成立しません。

一方で、この空白は狭いものです。 埋める作業自体は表を作ることであり、技術的な難所がありません。

アイデア 3: scenegate (iOS 27 SDK でのビルドが本番のどの機能を殺すかを、ビルド前に写像する検査)

  • ターゲット: 保守モードの iOS アプリを複数抱える受託開発会社と、自社アプリを外注で運用している事業会社。1本ずつ手で確かめるコストが積み上がる立場を想定する。
  • 解決する課題: iOS 27 SDK でビルドすると、UISceneDelegate に対応していないアプリは起動時に終了する。起動しないため didFinishLaunchingWithOptions が走らず、通知登録も行われない。結果としてデバイストークンが取得できず、プッシュ通知が届かなくなる。この連鎖は Apple の移行ガイドが説明する「シーンへ移行せよ」からは見えない。

パターン判定 & Why Now

6. マイクロDevExツール型です。

Why Now は、強制の到来が確定していながら、まだ来ていない点にあります。 iOS 27 は今月に一般提供され、SDK の強制は2027年4月と見込まれます。 移行の窓は約7か月であり、この間に受託先のアプリを順に確かめる需要が立ちます。

既存プレイヤーが解決済みの範囲と、未解決の範囲

解決済みの範囲は、移行そのものの手順です。 Apple はシーンベースのライフサイクルへの移行を文書化しており、Xcode も警告を出します。 コード変換自体は、LLM を使えば個々のファイル単位では片づきます。

未解決の範囲は、移行漏れが本番のどの機能を殺すかの写像です。 起動、通知登録、トークン取得、配信という連鎖は、コードの1箇所を見ても分かりません。 加えて、依存ライブラリ側がシーンに未対応である場合、自社コードだけを直しても起動しません。

ただしこの空白は、Apple 自身が塞ぐ位置にあります。 Xcode 27 が移行アシスタントを載せた時点で、本案の価値は大きく削られます。

配点理由

Idea 1: cws-window — 19点 (Tier 2)

  • タイミング 4: 9月8日という日付が公式に確定しており、その前後で審査待ち行列の性質が変わることまで外部が指摘している。買い手側には「28日待った」という金額に換算できる実害の記録が既に公開されている。減点材料: 市場の母数が小さい。Chrome 拡張機能で収入を得ている開発者は多く見積もっても数千人規模であり、しかもその多くは無償の拡張機能を副産物として持っているだけである。「明確な課金動機を持つ買い手が十分な数いる」という5点の条件に、人数の側で届かない。
  • 技術的実現可能性 4: 中核は manifest の権限宣言と実コードの API 呼び出しの突き合わせであり、既存のJSパーサで書ける。掲載文・単一目的の記述・権限justificationの整合も、文字列の照合で足りる。減点材料: バンドル済み・難読化済みのコードに対する権限使用の検出精度が落ちる。多くの拡張機能はビルド済みのバンドルを提出するため、この弱点は例外ではなく常態である。ソースマップの提出を前提にすると使える相手が減り、前提にしないと精度が落ちる。この二律背反を2週間では解けない。
  • 収益性 3: 差し戻し1回の損失を日数で語れるため、買い切り$39〜$59は説明できる。減点材料: 開発者向けCLIは無料が既定の領域であり、有償の壁が高い。加えて、提出は毎日起きる作業ではないため、月額の根拠が立たない。月$10〜$30の継続課金という4点以上の条件に、利用頻度の側で届かない。
  • 競合優位性 4: 3案で唯一、時間で閉じる参入条件を持つ。4週ケイデンス下での提出から公開までの実測値は、9月8日を過ぎると誰も集め直せない。 変更前後の比較を語れるのは、変更前に測り始めた者だけである。Google は待ち時間を公表せず、「共有できる具体策はまだない」と述べたまま半年が経っている。減点材料: 静的解析の部分は模倣が容易であり、観測データを持たない期間は差別化が存在しない。5点にしないのは、この障壁が製品の一部にしか掛かっていないためである。大手が3か月で真似したら、静的解析側は即座に並ばれる。守れるのは観測データ側だけである。
  • 個人開発適性 4: 検査はローカルのCLIで完結し、預かるデータがない。観測データの収集も追記のみであり、収集先が落ちても利用者の手元の検査は動き続ける。減点材料: Chrome ウェブストアのポリシーは改定され続けるため、ルールセットの追随が恒常的な固定費になる。加えて「このツールが通ると言ったのに差し戻された」という種類の問い合わせが構造的に発生する。

Idea 2: taiguu-brief — 17点 (Tier 2)

  • タイミング 4: 施行が1か月後に確定しており、対象は企業規模を問わない全事業者である。更新時期の集中する事業者では9月中に着手する必要がある。減点材料: 制裁が弱い。10万円以下の過料であり、しかも行政指導で是正されなければという条件が付く。予算が即座に動く水準ではない。「切実なペインと強い予算確保動機」という5点の条件に、金額の側で届かない。
  • 技術的実現可能性 4: 待遇項目ごとの入力フォームと、通知書の追記文言・説明資料・実施記録を出力する帳票生成で成立する。ローカルで完結し、外部APIを要しない。減点材料: 賃金規程や就業規則のPDFから待遇項目を自動抽出しようとすると、難度が跳ね上がる。手入力を前提にすれば2週間で届くが、その場合の入力負荷は利用者が負う。自動化の範囲を絞ることで実現可能性を買っている。
  • 収益性 3: 社労士事務所は顧問先ごとに繰り返し使うため、年額2万円から3万円の帯は説明できる。減点材料: 市場が国内に閉じており、海外展開の余地が構造的にない。企業への直販は施行前後の単発になり、翌年に払い直す理由がない。100人で月10〜20万円という5点の条件は、継続率の側で成立しない。
  • 競合優位性 2: 3案で最も弱い軸である。減点材料: 明示事項の追加は、人事労務SaaSが10月1日に合わせて確実に対応する範囲である。説明資料の中身が各社固有であることは事実だが、大手も「入力フォーム＋ひな形」で同じ形に到達できる。既に顧問先の従業員データを握っている側が有利であり、こちらに残るものがない。大手が3か月で真似したら、差分はゼロになる。2点にとどめたのは、参入障壁が「まだ誰も作っていない」という一点にしか依存していないためである。
  • 個人開発適性 4: 従業員情報を外部へ送らないローカル実行として設計でき、個人情報を預かる責任を負わずに済む。サポート負荷も低い。減点材料: 同一労働同一賃金ガイドラインの改定に追随する必要があり、法令解釈を含む問い合わせが来る。個人が法令判断の外観を持つ出力を提供することのリスクは、この軸を5点にできない理由である。

Idea 3: scenegate — 16点 (Tier 2)

  • タイミング 4: 強制の内容が明確であり、対応しなければ起動しないという結果も断定できる。移行の必要性を説明する手間がかからない。減点材料: 期限が遠い。Xcode 27 の必須化は2027年4月と見込まれ、現在の提出下限は iOS 26 SDK のままである。「今すぐ払う理由」が7か月先にあるため、購買の先送りが容易である。
  • 技術的実現可能性 4: Info.plist の scene 構成、AppDelegate のライフサイクル実装、非推奨となった UIApplication のアクセサ利用箇所は、いずれも静的解析で列挙できる。Podfile.lock と SPM の解決結果から依存ライブラリの一覧も取れる。減点材料: 依存ライブラリの内部がシーンに対応しているかは、ソースが手に入らない場合に判定できない。この判定こそが受託にとっての難所であり、そこを埋められないまま出すことになる。
  • 収益性 2: 3案で最も弱い軸である。減点材料: iOS 開発者向けの検査ツールは無償が既定であり、有償化の実績が乏しい。移行は1アプリにつき1回で終わるため、継続課金の根拠がない。受託会社に「監査レポート」として売る道はあるが、それは製品ではなく役務の販売であり、個人の時間が原価になる。「API原価率」ではなく「人的原価率」でスケールしない。
  • 競合優位性 2: 減点材料: Apple が正面から重なる。Xcode 27 が移行アシスタントや診断を載せれば、本案の中核は消える。除外フィルタの「Big Tech 正面衝突」に該当するかを検討したが、Apple が現時点で提供しているのは移行手順の文書と警告のみであり、機能の重複としては未成立と判断して却下は見送った。ただしそれは、いつでも重複しうるという意味でもある。加えて LLM によるコード変換が、移行作業そのものを個別に解いてしまう。
  • 個人開発適性 4: ローカルCLIとして完結し、預かるデータがない。CI に組み込む形にすれば運用も不要である。減点材料: iOS SDK は毎年更新され、非推奨APIの一覧も毎年変わる。ルールセットの年次更新が固定費として残る。

4. リスク・反証分析 (Fail-safe Analysis)

1. cws-window のリスクと対策

最大のリスクは、審査待ち時間の実測データが集まらないことです。

本案の競合優位性は、9月8日を境に取り直せなくなる観測データにあります。 しかしその観測は、開発者が自分の提出時刻と公開時刻を提供してくれることが前提です。 提出は毎日起きる作業ではないため、100人が導入しても週に数十件しか集まりません。 統計として意味を持つ量に届く前に、9月8日が過ぎる可能性があります。

対策は、収集を人の善意に依存させないことです。 提出前検査のCLIが実行された時点の時刻と、拡張機能のバージョン番号だけを記録します。 公開の検知は、開発者の手を借りずに Chrome ウェブストアの公開ページからバージョン番号の変化を読むことで成立します。 提出時刻は手元のCLI、公開時刻は公開情報という組み合わせであり、開発者が後から報告する工程を省けます。

第二のリスクは、静的解析の判定が当たらないことです。

差し戻し理由の多くは権限の過剰宣言と掲載情報の不整合ですが、実際の審査には自動判定に載らない要素が含まれます。 「通ると言われたのに差し戻された」という体験は、製品の信頼を一度で失わせます。

対策は、出力を判定ではなく指摘に固定することです。 「通る/通らない」を出さず、「この権限はコード上で使用箇所が見つからない」「掲載文にある機能が manifest の権限と対応しない」という事実だけを列挙します。 判断は開発者が行い、ツールは材料だけを出します。

反証されたときの撤退条件は、Day 1-2 の接触で「差し戻しを経験していない」という回答が大半を占めた場合です。 待ち行列の長さが問題であって差し戻しが問題でないなら、検査には価値がありません。

2. taiguu-brief のリスクと対策

最大のリスクは、説明を求められる件数がそもそも少ないことです。

本案は「明示の義務化によって説明の請求が増える」という仮定の上に立ちます。 しかし労働者が待遇差の説明を求める行為には、職場での立場という抑止が働きます。 明示されても請求が増えなければ、事業者は説明資料を準備する動機を持ちません。 その場合、売れるのは通知書の1行を追記する機能だけになり、それは労務SaaSが無償で配ります。

対策は、製品の入口を説明資料ではなく通知書の追記文言の生成に置き、説明資料を上位の機能として後段に置くことです。 入口を確実に発生する需要に合わせ、不確実な需要は入口の後ろに隠します。

第二のリスクは、法令解釈の責任を負わされることです。

「このツールが出した説明資料で説明したのに、不合理な待遇差と判断された」という申立てが起きうる。 個人が背負える種類の責任ではありません。

対策は、出力を事業者自身の記述としてまとめる形に限定することです。 理由の文面はツールが生成せず、事業者が入力した文を構造化して並べるだけにします。 ツールが提供するのは「どの待遇項目について書くべきか」の網羅リストであり、内容ではありません。

反証されたときの撤退条件は、社労士5名への聞き取りで「顧問先には自作のExcelで足りている」という回答が大半を占めた場合です。

3. scenegate のリスクと対策

最大のリスクは、Apple が同じものを出すことです。

Xcode 27 が移行診断を載せた時点で、本案の中核は無価値になります。 これは対策できるリスクではなく、時期の問題です。

対策は、Apple が出さない部分に製品の重心を移すことです。 Apple が診断するのは自社コードであり、依存ライブラリの対応状況ではありません。 「どのライブラリのどのバージョンがシーンに対応しているか」という表は、複数の現場を通らないと作れません。 本案に残る価値があるとすれば、この表だけです。

第二のリスクは、買い手が金を払わないことです。

iOS 開発者向けの検査ツールは無償が既定であり、この前提は動きません。

対策は、売り先を開発者個人ではなく受託会社に変えることです。 「保守中の20本について、iOS 27 SDK でビルドしたときに壊れる箇所の一覧」は、見積の材料になります。 見積の材料は経費で通ります。

反証されたときの撤退条件は、受託会社3社への聞き取りで「移行はLLMに投げれば済む」という回答が大半を占めた場合です。

5. 参考ロードマップ (14日間MVPの想定仕様)

最有力候補である cws-window について、14日間の想定を置きます。 9月8日にケイデンスが変わるため、Day 1 は9月1日からの起算とします。 観測の基準値を取れるのは Day 1 から Day 7 までであり、この7日間は取り戻せません。

期間工程内容
Day 1事前検証リスク分析の前提を潰す工程。実装には入らない。(a) chromium-extensions グループと関連コミュニティで、直近6か月に差し戻しを経験した開発者を10名探し、差し戻し理由の内訳を聞く。(b) 「待つのは辛いが差し戻されたことはない」という回答が大半なら、検査に価値がないということであり、着手しない。(c) 提出時刻と公開時刻を記録することへの抵抗の有無を確認する。
Day 2-3観測の開始最優先。9月8日より前に動かす必要がある。 公開されている拡張機能のバージョン番号を定期的に読み、変化した時刻を記録するだけの収集器を書く。対象は Day 1 で接触した開発者の拡張機能と、インストール数上位の公開拡張機能に限る。提出時刻はこの時点では取れないため、公開間隔の分布だけを先に取る。4週ケイデンス下での基準値は、9月7日までしか観測できない。
Day 4-6提出前検査（権限）manifest の permissions / host_permissions と、コード上の chrome.* 呼び出しおよび実際に触れるオリジンを突き合わせる。出力は「宣言されているが使用箇所が見つからない権限」「<all_urls> を宣言しているが実際に触れているのは3オリジン」という事実の列挙に限る。通る/通らないの判定は出さない。
Day 7-8提出前検査（掲載情報）掲載文・単一目的の記述・権限justification・プライバシー開示と manifest の整合を照合する。掲載文に書かれた機能に対応する権限がない場合、逆に権限に対応する記述がない場合を指摘する。ここまでを無償のCLIとして公開する。
Day 9-10提出時刻の記録CLI の実行時に、拡張機能のIDとバージョン番号と時刻をローカルへ記録し、任意で送信する導線を作る。送信は追記のみで、失敗しても検査は成立する。Day 2-3 の公開検知と突き合わせることで、提出から公開までの実測値が初めて揃う。
Day 11-12提出タイミングの提示収集した公開間隔の分布と、Chrome の安定版リリース日程を重ねる。「次の安定版は9月22日、その前後48時間を外すなら9月18日までに提出」という形で、日付だけを返す。予測の精度を主張せず、観測された分布をそのまま見せる。
Day 13-14有償化の判断成功指標はダウンロード数ではなく、「検査の結果、提出前に権限宣言または掲載文を修正した件数」に置く。修正が起きないなら、指摘に価値がないということであり、有償化へ進みません。

課金設計は、提出前検査を恒久的に無償、提出タイミングの提示を有償とする二層構成を想定します。 無償側は模倣可能な静的解析であり、有償側は9月8日より前にしか取れない基準値を含みます。 この順序は逆にできません。 検査を有償にすると導入者が減り、導入者が減ると観測データが集まらず、有償にすべき側の価値が立たないためです。

6. スクリーニング結果と提案候補 (参考情報)

AIエージェントによる評価・分析結果

  • cws-window（総合19点、Tier 2）を最有力候補として選定しました。選定理由は、競合優位性が4点である唯一の案だからです。9月8日に Chrome のリリース間隔が4週から2週へ変わるため、それ以前の審査待ち時間の分布は、その日を過ぎると誰も観測できません。前回設定した探索軸「期限までにしか観測できないデータ」を、3案で唯一満たしています。Tier 1 に届かなかった理由は二点です。第一に、Chrome 拡張機能で収入を得る開発者という母数が小さく、市場規模の側で4点が上限であること。第二に、開発者向けCLIの有償化という構造的な壁があり、収益性が3点を超えないことです。着手の条件は Day 1 の接触であり、「待つのは辛いが差し戻されたことはない」という回答が大半なら着手しません。
  • taiguu-brief（総合17点、Tier 2）は、買い手の数が3案で最も多い案です。パート・有期雇用労働者を雇う事業者は企業規模を問わず対象であり、10月1日という日付も動きません。それでも17点に留まったのは、競合優位性が2点であることによります。明示事項の追加は人事労務SaaSが確実に対応する範囲であり、参入障壁が「まだ誰も作っていない」という一点にしか依存していません。着手するなら、製品ではなく社労士事務所向けの受託作業として始め、繰り返し発生する部分だけを後から製品化すべきです。
  • scenegate（総合16点、Tier 2）は、壊れ方の説明が3案で最も明快な案です。「iOS 27 SDK でビルドすると起動しない、起動しないから通知トークンが死ぬ」という連鎖は、買い手にそのまま伝わります。しかし収益性2点と競合優位性2点が重なり、16点に留まりました。Apple が Xcode 27 に移行診断を載せた時点で中核が消える位置にあり、残るのは依存ライブラリの対応状況の表だけです。着手するなら、その表を作ることから始め、検査ツールは表を配るための道具として扱うべきです。
  • 今回の探索で候補から落とした案が4件あります。
    • Chrome の非推奨APIの期日換算: 9月8日以降、マイルストーン番号は2週ごとに進むため、「M160 で削除」という告知の実際の日付が従来の見積より早く来ます。依存しているAPIの削除日を暦日へ換算する道具は成立しますが、課題の形が「依存の束の期限を棚卸しする」であり、2026-08-30 の mcp-sunset と実質的に同一です。重複判定フィルタに触れるため、総合13点で却下しました。
    • Sora 2 API の移行支援: 2026年9月24日に sora-2 系モデルと Videos API が削除されます（OpenAI Deprecations）。期限は鋭いものの、移行先の動画生成APIを叩く構成では原価率が課金額の50%を超えやすく、除外フィルタの「過度なAPI原価率」に該当します。加えて残り3週間では製品が間に合いません。総合11点で却下しました。
    • Content API for Shopping 停止後の復旧支援: 2026年8月18日に停止済みで、移行しなかった事業者の商品リスティングが既に止まっています。需要は現に発生していますが、Merchant API への移行はフィード管理ベンダーが既に商品化しており、正面衝突になります。総合12点で却下しました。
    • サイバー対処能力強化法のインシデント報告支援: 2026年10月1日から基幹インフラ事業者にインシデント報告義務が生じます。期限は確定していますが、買い手が15業種の大規模事業者に限られ、調達要件と実績が参入条件になります。個人開発適性が構造的に成立しないため、総合12点で却下しました。
  • 7回連続で Tier 1 に到達していません。 ただし今回は、前回設定した探索軸が実際に機能しました。「期限までにしか観測できないデータ」を条件に当てたところ、3案のうち1案（cws-window）だけが競合優位性4点に届き、残る2案は2点に沈みました。差がついたのは技術の難易度ではなく、データの取得可能期間が有限かどうかです。taiguu-brief の説明資料も scenegate の依存ライブラリ表も、来年でも同じものを作れます。cws-window の基準値だけが、9月7日を最後に観測不能になります。一方で今回明らかになった弱点は、収益性が3案とも3点以下に留まったことです。観測窓の有無は競合優位性を説明できても、支払意思を説明できません。 次回の探索軸には、「その期限までにしか観測できないデータ」に加えて、そのデータを必要とする側が既に金銭で解決を試みた形跡があるかを置きます。既に金を払って解決を試みた記録は、支払意思の存在を事後的に証明します。
