1. 調査の背景と市場の変曲点

前回（2026-10-21）は、Claude Code の Windows / VS Code 環境における auto-updater のサイレント EBUSY ロック失敗（Issue #61676）、2026年11月2日に全パブリックリポジトリへ強制適用される GitHub Actions pull_request_target 既定遮断ポリシー、および 2026年11月10日に公式 EOL を迎える AWS Lambda .NET 8 ランタイム非推奨化を検証しました。

今回は、2026年10月下旬から11月にかけて表面化している「AI コーディングエージェントの Git Worktree 隔離逸脱による親ワークスペースサイレント汚染事故」「主要 Git ホスティング基盤における SSH エンドポイント分離と強制ブラウンアウト断崖」、および「大手パブリッククラウド Kubernetes 基盤におけるマネージド Ingress 公式退役断崖」という 3 つの構造的断絶を検証します。 AI コーディングエージェントが複数タスクを並行処理するために Git Worktree（--worktree や isolation: "worktree"）を活用する運用が一般化しました。 しかし、探索用サブエージェント（Explore agent）がファイル探索時に親リポジトリのルートパスを拾い上げ、続く Edit / Write ツールがそのパスをそのまま使って親ワークスペース（main ブランチ）のファイルを直接書き換えてしまう致命的な不具合が長期にわたり放置されています。 また、世界中の企業開発を支える Bitbucket Cloud において、DDoS 対策とトラフィック分離を目的とした SSH ホスト名の変更（bitbucket.org から ssh.bitbucket.org への完全移行）が発表され、2026年11月12日（あと21日後！）より意図的に SSH トラフィックを遮断する段階的ブラウンアウトが開始されます。 さらに、Microsoft Azure のマネージド Kubernetes（AKS）において、アップストリームの Ingress NGINX プロジェクト引退に伴い、Application Routing アドオンで提供されてきたマネージド NGINX Ingress の公式セキュリティサポートが 2026年11月30日（あと39日後！）をもって完全終了し、後継の Gateway API への移行が必須となります。

2026年10月22日現在、開発・運用の現場では以下の 3 つの断絶が表面化しています。

  • Claude Code における Git Worktree 隔離逸脱と親ワークスペースサイレント誤爆事故（Issue #36182 / #44557）（Claude Code は安全な並行開発のため Git Worktree を自動生成してセッションを実行する。しかし Explore サブエージェントが親リポジトリのルートを基準にファイルを探索・報告するため、その後の Edit/Read/Write ツールが親ディレクトリのファイルを直接書き換えてしまう。作業中の検証アプリはワークツリー側を実行しているため変更が一切反映されず、ユーザーは何時間も原因不明のデバッグに忙殺される。エラーが一切発生しないサイレント破壊であり、Issue #36182 として 7 か月以上にわたり未解決のまま放置されている）
  • Bitbucket Cloud による SSH ホスト名分離（2026年11月12日ブラウンアウト開始、あと21日！）と CI/CD・npm 突然死断崖（Atlassian は 2026年10月21日に移行猶予スケジュールを更新し、11月12日より最大3時間の意図的 SSH 遮断ブラウンアウトを平日毎日実施し、12月10日に bitbucket.org への直接 SSH を恒久遮断することを確定した。ローカルの Git リモートだけでなく、package-lock.json 内に git+ssh://git@bitbucket.org/ で埋め込まれたプライベート npm パッケージ依存や、Git サブモジュール、各種 CI/CD パイプラインが一斉にビルド失敗・接続拒否を起こすパニックが発生している）
  • Azure Kubernetes Service (AKS) における Managed NGINX Ingress の公式サポート完全終了（2026年11月30日、あと39日！）（Kubernetes SIG Network による Ingress NGINX プロジェクト引退を受け、AKS の Application Routing アドオンにおけるマネージド NGINX Ingress のクリティカルセキュリティパッチ提供が 2026年11月30日をもって停止する。Azure DNS や Key Vault 連携を含む既存の networking.k8s.io/v1 Ingress 定義を、後継規格である Gateway API（Gateway および HTTPRoute）へ安全に移行するための検証が急務となっている）

これらの課題を解決し、AI エージェントの安全な Worktree 開発、Git ホスティングの SSH ホスト移行、およびマネージド Kubernetes の安全な Gateway API 移行を支援するツールの需要を検証します。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: claude-worktree-jail (Claude Code Git Worktree 隔離逸脱・親ワークスペース誤爆書き換え自動防止 & パスリダイレクト・セーフティ Proxy/Hook)

対象は、Claude Code の --worktree オプションやマルチエージェント機能を活用して機能開発・リサーチを並行実行しており、エージェントによる親ブランチ・親ワークスペースのサイレント改変事故を防ぎたい個人エンジニア、開発チームです。

入力は 2 つです。 1. 現在の Claude Code 実行コンテキスト（アクティブな Git Worktree パス、親リポジトリのルートパス、ブランチ名） 2. ファイルアクセス監視ポリシー（親ワークスペースパスの自動書換リダイレクトフラグ、逸脱検知時の即時中断フラグ、警告ログ出力先）

出力は次の 3 点です。 1. PreToolUse フックおよび Claude Code 透過ラッパーとして動作し、Edit / Write / Read / Bash ツールの引数に含まれるファイルパスをミリ秒単位で検査するセキュリティバリデータ 2. エージェントが親リポジトリの絶対パス（/path/to/repo/src/...）を指定してきた場合、自動で現在の Worktree 相対パス（/path/to/repo/.claude/worktrees/name/src/...）へと透過的に書き換えてツールを実行させるアトミックリダイレクトエンジン 3. 親リポジトリ側のファイルを破壊しようとした回数・対象ファイル・サブエージェントの呼び出し元を可視化し、セッション終了時にサマリーを表示する Worktree 健全性監査ログ

本体は 1 番目と 2 番目です。 Issue #36182 で生々しく告発されている通り、Claude Code はシステムプロンプトでは Worktree を認識しているにもかかわらず、サブエージェントの探索結果に引きずられて親ワークスペースのファイルを直接更新してしまいます。 本質的な価値は、公式の根本改修を待つことなく、外部の安全フックによってエージェントの「Worktree 脱獄」を物理的に遮断し、安全で確実な並行開発環境を担保する点にあります。

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、Anthropic 公式の claude-code リポジトリにおいて、Worktree 内で動作させたエージェントが親ワークスペースを誤爆編集する問題が Issue #36182（および重複報告 #44557）として詳細に報告され、26 件以上の賛同を集めて長期オープンとなっている事実です。

When Claude Code operates in a git worktree (created automatically by the harness), the Edit, Read, and Write tools consistently target files in the main workspace rather than the worktree directory, even though the system prompt correctly identifies the worktree as the primary working directory.

Actual Behavior: - Explore agents report file paths using the main workspace root - Subsequent Edit/Read/Write calls use those paths verbatim - All changes land in the main workspace (often main branch), not the worktree side branch - The running app (via preview_start) executes from the worktree and sees none of the changes - This is completely invisible to the user — no error is raised, edits succeed silently on the wrong files

Impact: In our session, every edit across ~15 iterations went to the wrong file. The app ran the original unmodified code the entire time. Hours of debugging a "not working" visual change were wasted because the changes were never in the file being executed.

— Worktree: Edit/Read tools use main workspace paths instead of worktree paths · Issue #36182 · anthropics/claude-code · GitHub

さらに重複 Issue #44557 でも以下の通り、Worktree からの脱獄挙動が確認されています。

When Claude Code is invoked in a git worktree (e.g. .claude/worktrees/my-branch/), spawned Agent subagents search and read files from the main repository root instead of the worktree. The worktree is a full checkout with all files present, but agents resolve paths against the original repo.

Expected: Subagents should respect the worktree as the project root. Actual: Subagents navigate to the main repo, which is a parent directory of the worktree location.

— [[Bug] Subagents ignore worktree working directory and resolve paths in main repository · Issue #44557 · anthropics/claude-code · GitHub](https://github.com/anthropics/claude-code/issues/44557)

開発者コミュニティでは「隔離環境で安全に新機能を試そうとしたら、裏で main ブランチのコードが書き換えられていて冷や汗をかいた」「テストが通らないと思ったら別ブランチのファイルを編集されていた」という悲鳴が上がっています。 「エラーにならずサイレントに成功する」という特性が、デバッグ時間を何倍にも膨らませる極めて凶悪な不具合です。

パターン判定 & Why Now

パターンはマイクロDevExツール型およびワークフロー糊付け・連携型の複合です。

Why Now は、Claude Code の日常利用における Git Worktree 運用の定着と、公式による 7 か月以上の修正放置です。 Anthropic 公式がクライアント内部のパス解決器（Path Normalizer）を全面刷新するまでの間、開発者は手動で差分を監視するか、PreToolUse フックで機械的にパスを補正するしか自衛の手段がありません。 エージェントが複数立ち上がる現代の開発現場において、リポジトリの完全性を守るガードレールの需要は極めて高いです。

境界線は以下のとおりです。

  • 解決済み: 開発者がセッション終了後に git diff で親リポジトリの未コミット変更を手動で確認し、手作業で revert すること。
  • 未解決: ツール実行直前のパス検査、親パスから Worktree パスへの透過的アトミック変換、および Worktree 外への書き込みの物理的ブロック。

アイデア 2: bb-ssh-migrator (Bitbucket Cloud 2026年11月12日 SSH ホスト名変更・ブラウンアウト直前救済 & package-lock / Submodule / CI-CD 一括移行 CLI)

対象は、Bitbucket Cloud 上にソースコードやプライベート npm パッケージをホストしており、2026年11月12日より開始される「SSH ホスト名変更に伴う強制ブラウンアウト（一時遮断）」によるビルド停止やデプロイ事故を回避したい開発チーム、DevOps / SRE エンジニアです。

入力は 2 つです。 1. ローカル環境およびプロジェクトリポジトリ群（.git/config, .gitmodules, package-lock.json, pnpm-lock.yaml, CI/CD ワークフロー定義） 2. 開発者および CI ランナーの SSH 構成（~/.ssh/config, ~/.ssh/known_hosts）

出力は次の 3 点です。 1. リポジトリ内の全リモート URL、Git サブモジュール、およびロックファイル（package-lock.json 等）を走査し、旧ホスト名 git@bitbucket.org: や git+ssh://git@bitbucket.org/ を含む箇所を 100% 洗い出す監査台帳 2. すべての旧 SSH URL を新ホスト ssh.bitbucket.org へ一括書換し、Git のグローバル設定（insteadOf）を構成して未移行リポジトリの通信を自動救済する Codemod エンジン 3. 公式の公開鍵を ~/.ssh/known_hosts へ安全にプレシード（先行登録）し、初回の対話型プロンプト（The authenticity of host... can't be established）による CI バッチ停止を未然に防止する接続テストランナー

本体は 1 番目と 2 番目です。 Atlassian が 2026年10月21日に発表した通り、11月12日以降、平日毎日 15 分〜3 時間にわたって bitbucket.org の SSH ポートが意図的に遮断されます。 本質的な価値は、Git リモートの更新にとどまらず、多くのエンジニアが見落としている package-lock.json 内の固定 URL や Git サブモジュール、CI/CD 構成の時限爆弾をワンライナーで無力化できる点にあります。

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、Atlassian 公式コミュニティにおいて 2026年10月21日にブラウンアウトの厳密なスケジュールが公表され、現場の開発者から切実な困惑と技術的課題が殺到している事実です。

Update as of October 21, 2026: Earlier this year, we shared our initial Changelog announcement about the upcoming change to Bitbucket Cloud SSH access. This is an important change to improve Bitbucket’s security posture and safeguard our customers from denial of service abuse...

We have decided extend a grace period starting from the original deprecation date: November 12, 2026 to December 10, 2026. During this time, we will run a series of controlled brownouts... During each brownout window, we will: - Temporarily block SSH traffic on bitbucket.org - Return clear error messages

Brownout schedule: - Nov 12, 2026: 15 minutes (00:00, 06:00, 12:00, 18:00 UTC) - Nov 16–20: 30 minutes - Nov 23–24: 1 hour - Nov 30–Dec 2: 2 hours - Dec 3–9: 3 hours - Dec 10, 2026: Final removal

— Upcoming change to Bitbucket Cloud SSH access: move from bitbucket.org to ssh.bitbucket.org | Atlassian Community

コミュニティのスレッドでは、単なる git remote set-url では済まない深刻な実害が告発されています。

We are hosting private npm packages on Bitbucket and give them a commit tag to then install them with npm install bitbucket:<workspace>/<package>#<tag> in our NodeJS application. This adds an entry in the package-lock.json file, similar to: "resolved": "git+ssh://git@bitbucket.org/<workspace>/<package>.git#<sha>" Unfortunately, the resolved URL is not correct, because it should have the ssh subdomain. With the proposed change, the npm install bitbucket:... syntax would be broken.

— Atlassian Community Comment

WTF?! We have tons of repos with submodules added with ssh config. This means we will not be able to check out older commits without manually checking out submodules.

— Atlassian Community Comment

You're kidding us, right? With just a month in advance we were just informed about this massive and mostly unnecessary change. We deploy everything through SSH, nobody uses HTTPS for automatic git deployments. All our customers websites, all CI/CD integrations, everything. This is going to take hours of work and talking with external IT to fix.

— Atlassian Community Comment

11月12日の初回ブラウンアウト発生時に、世界中の Bitbucket 利用企業で深夜バッチやデプロイが突発死することが確実視されています。

パターン判定 & Why Now

パターンはプラットフォーム変更・規約変更対応型およびマイクロDevExツール型の複合です。

Why Now は、2026年11月12日（あと21日後！）というブラウンアウト開始の絶対的期日です。 10月21日に確定スケジュールが発表されたばかりであり、多くの企業はまだ自社の CI/CD や依存関係（package-lock やサブモジュール）に潜む影響を棚卸しできていません。 手動で何十リポジトリも直すのではなく、ワークスペース全体を一括スキャン・修正できるツールの需要は今まさに発生しています。

境界線は以下のとおりです。

  • 解決済み: 開発者が自分の 1 つのリポジトリで git remote set-url origin git@ssh.bitbucket.org:... を叩くこと。
  • 未解決: マシン内の全リポジトリ走査、package-lock.json 内の推移的解決 URL の書き換え、.gitmodules の更新、および CI 用 known_hosts の自動構成。

アイデア 3: aks-gateway-api-shifter (Azure AKS Managed NGINX Ingress 2026年11月30日 公式サポート終了 & Gateway API / HTTPRoute 自動変換・事前監査 CLI)

対象は、Azure Kubernetes Service (AKS) 上で Application Routing アドオンの Managed NGINX Ingress を運用しており、2026年11月30日の公式セキュリティサポート終了に伴い、最新の Gateway API 規格へ安全に移行したいインフラエンジニア、SRE チームです。

入力は 2 つです。 1. クラスタ内の既存 Ingress リソース定義群（networking.k8s.io/v1 Ingress YAML マニフェストや Helm チャート） 2. 対象 AKS クラスタへの読み取り権限（kubeconfig、Application Routing アドオン構成状態）

出力は次の 3 点です。 1. クラスタ内の全 Ingress をスキャンし、Managed NGINX クラス（webapprouting.kubernetes.azure.com）を使用しているリソースと、Azure DNS / Key Vault 連携アノテーションを網羅した棚卸し台帳 2. レガシーな Ingress マニフェストを、AKS Application Routing Gateway API 仕様に準拠した gateway.networking.k8s.io/v1 Gateway および HTTPRoute 定義へ 100% 忠実に自動変換する Codemod エンジン 3. パスルーティング（Prefix / Exact）、ホスト名マッチング、および Key Vault TLS 証明書シークレットの参照が Gateway API 側で欠落・非互換を起こしていないかを検証する事前ドライランレポート

本体は 1 番目と 2 番目です。 Microsoft Learn 公式ドキュメントに明記されている通り、2026年11月30日をもって Managed NGINX Ingress の重大セキュリティパッチ提供が完全終了します。 本質的な価値は、Kubernetes アップストリームの標準である Gateway API への移行に伴う構文差異と Azure 固有の Key Vault / DNS 連携の書き換え工数を最小化し、移行時のルーティング事故をゼロにする点にあります。

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、Microsoft Learn 公式ドキュメントにおいて、Managed NGINX Ingress のサポート終了が 2026年11月30日と明記され、Gateway API への移行が強く推奨されている事実です。

The Kubernetes SIG Network and the Security Response Committee announced the retirement of the Ingress NGINX project, with maintenance that ended in March 2026. Microsoft will provide official support for critical security patches for application routing add-on NGINX Ingress resources through November 2026.

AKS aligns with upstream Kubernetes and uses Gateway API as the long-term standard for ingress and L7 traffic management. Migrate before support ends in November 2026, based on your requirements: - Application routing add-on users and OSS NGINX users: Migrate to the application routing Gateway API implementation for a Gateway API-based ingress traffic management experience, or to Application Gateway for Containers, which supports both Ingress API and Gateway API.

— Managed NGINX ingress with the application routing add-on | Microsoft Learn

クラウドインフラ現場では「NGINX Ingress のサポートが 11月末で切れるため Azure Advisor から警告が来ているが、Gateway API のマニフェスト記法が直感的でなく移行手順の作成に苦慮している」「Key Vault の TLS 自動更新が Gateway API でも問題なく動くか検証に時間がかかっている」という声が上がっています。

パターン判定 & Why Now

パターンはプラットフォーム変更・EOL対応型です。

Why Now は、2026年11月30日（あと39日後！）という Microsoft 公式サポート終了期限の到来です。 SOC2 や PCI-DSS などのセキュリティコンプライアンス要件を持つ企業にとって、サポート切れインフラの稼働継続は許容されないため、迅速なバージョン更新が必須となります。

境界線は以下のとおりです。

  • 解決済み: 公式ドキュメントのサンプルを見ながら、手作業で 1 つずつ Gateway API マニフェストを書き起こすこと。
  • 未解決: 既存の Ingress アノテーション（Azure Key Vault, Azure DNS）を保持したままの自動マニフェスト変換、および切り替え時のルーティング互換性静的検証。

4. 最有力候補の深掘り: bb-ssh-migrator

総合スコア 23 点を獲得した bb-ssh-migrator を今回の最有力 MVP 候補として選定します。 （次点の claude-worktree-jail も 22 点と極めて有望であり、並行検証の価値があります）

リスク・反証分析（失敗する理由と対策）

1. リスク 1: Git の insteadOf グローバル設定による問題の不可視化と副作用

  • 分析: git config --global url."git@ssh.bitbucket.org:".insteadOf "git@bitbucket.org:" を設定すれば、多くの Git コマンドは透過的に動きます。そのため、専用ツールを使わずにシェルワンライナーで済まされるリスクがあります。
  • 対策: insteadOf では解決できない「package-lock.json 内の固定 URL による npm install 失敗」「Docker ビルドコンテキスト内での SSH 解決」「CI ランナー環境での known_hosts 不在による対話プロンプト停止」という、現場で実際に爆発するエッジケースの自動修復を主軸に据えて差別化します。

2. リスク 2: 12月10日の移行完了後に市場需要が急減するフロー型リスク

  • 分析: SSH ホスト名の変更は一度きりのイベントであり、12月10日の最終遮断を過ぎると新規需要が急速に収束します。
  • 対策: 本ツールを Bitbucket 特化の移行ツールにとどめず、GitHub や GitLab を含む「エンタープライズ Git リモート & SSH 鍵・Known Hosts 健全性監査・一括更新スイート」へと発展させ、開発環境のセキュリティ監査ツールとして恒久的な価値を提供します。

3. リスク 3: 収益化の難しさ（個人開発者の支払い意欲の低さ）

  • 分析: 個人開発者は手作業で数リポジトリを直すため、課金動機が薄い可能性があります。
  • 対策: 個人エンジニア向けには単一リポジトリ修復機能を GitHub 上で OSS（MIT）として無料提供し、認知を拡大します。収益化の対象は「社内の数百リポジトリおよび全 CI/CD パイプラインの一括診断・自動 PR 生成」を求める企業組織向けとし、1 組織あたり $49 のスキャンライセンスで販売します。

14日間 MVP ロードマップ

実装から入らず、初日に前提の「事前検証」を置くことで仮説倒れのリスクを最小化します。

  • Day 1: 前提の事前検証（仮説の生死判定）
    • Bitbucket 上にホストされたプライベート npm パッケージを含む Node.js プロジェクトにおいて、git@bitbucket.org を遮断した状態で npm install が実際に package-lock.json の記述で失敗することを再現・検証。
    • git config insteadOf の適用有無による挙動差分、および known_hosts への事前投入による対話プロンプト抑止効果を実機確認。
  • Day 2〜3: リポジトリ & 構成走査エンジン（Scanner）の実装
    • ローカルディレクトリ配下の全 .git/config, .gitmodules, package-lock.json, pnpm-lock.yaml を再帰探索し、旧 URL を抽出する Go/Python CLI を作成。
  • Day 4〜5: 自動書き換え（Codemod）エンジンの実装
    • AST / JSON パーサーを用いて、フォーマットやインデントを崩さずに ssh.bitbucket.org へ置換するロジックを実装。
  • Day 6〜7: SSH 構成 & known_hosts プレシード機能の実装
    • Atlassian 公式の公開ホスト鍵（ECDSA, ED25519, RSA）を ~/.ssh/known_hosts へ安全に追加し、非対話型接続を確立するテストコマンドを整備。
  • Day 8〜9: CI/CD 定義（GitHub Actions, Jenkins 等）走査の実装
    • .github/workflows/*.yml や Jenkinsfile 内のハードコードされた URL を検出し、修正提案を出す機能を実装。
  • Day 10〜11: ドキュメント整備 & OSS 公開（GitHub / Homebrew / npm）
    • ワンライナー npx bb-ssh-migrator または brew install bb-ssh-migrator で即座に実行できる配布形態を整備。
  • Day 12〜13: 技術コミュニティ（Atlassian Community, Reddit, X, Zenn）への発信
    • 10月21日の Atlassian アナウンススレッドや関連コミュニティに対し、11月12日のブラウンアウト対策用 OSS として共有。
  • Day 14: 企業向け一括スキャン機能のフィードバック収集
    • 利用実績を分析し、企業向け複数リポジトリ一括 PR 生成機能の需要を検証。
