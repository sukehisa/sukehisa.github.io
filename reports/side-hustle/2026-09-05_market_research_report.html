1. 調査の背景と市場の変曲点

前回（2026-09-04）の終わりに、探索軸を積で絞ると宣言しました。 材料が公開されているかつ突き合わせた結果が先客に不都合、この2条件を同時に満たす位置だけを候補に残す、という条件です。

前々回までの失敗を要約すると、2つの軸が交換関係にありました。 利益相反だけで絞ると、先客が長年かけて溜めた資産を個人が独力で揃え直す羽目になりました。 公開情報の完備だけで絞ると、材料が誰の手にも届くために差別化が溶けました。 片方ずつでは、軸2（実現可能性）と軸4（競合優位性）が交互に沈みます。

今回はこの積を機械的に適用しました。 まず「その判定に必要な材料が、無償の公開ページまたは公開データセットとして既に存在するか」を確認しました。 次に「その材料を突き合わせた結果が、材料を公開している当人にとって不都合か」を確認しました。 残った変曲点は3つで、いずれもベンダーが自ら公開した記述と、実際の挙動または顧客の権利との差分という同じ形をしています。

1つ目は、ステータスページが語らない障害です。 IsDown は2026年4月の1か月間に、ベンダーが公式には一切報告しなかったインシデントを104件検知しました。 同社の集計では1月に101件、3月に87件と、この規模が毎月続いています。 さらに GitHub は2026年4月に稼働率の算出方法を公開しましたが、その方法では Degraded Performance が停止時間ゼロとして扱われます。 材料は公開されています。 ステータスページの履歴は JSON と RSS で読め、主要クラウドの SLA クレジット表は CC-BY-4.0 の機械可読データセットとして公開されています。 そして、この突き合わせを最も作らないのはベンダー自身です。 稼働率の記述を書く側と、クレジットを払う側が同一だからです。

2つ目は、Google Play のデータ安全性申告と SDK の実挙動の差分です。 Google は申告責任を開発者に一本化しており、第三者 SDK が収集するデータも開発者の申告対象だと明記しています。 材料は公開されています。 Google は SDK 提供者に「Play data disclosure」ページの公開を促しており、AdMob も Maps も、自 SDK が収集するデータ型を一覧で公開しています。 そして、この突き合わせを作らないのは SDK 提供者です。 「当 SDK を入れると広告 ID の申告が必須になります」と依存ツリー全体で集計して見せる道具は、そのまま自社 SDK の導入障壁の一覧になります。

3つ目は、ZDR 契約と実際の API 呼び出しの乖離です。 Anthropic は機能ごとの ZDR 適格性を表として公開したうえで、ZDR では不適格機能の呼び出しをブロックしないと明記しています。 HIPAA では 400 を返して止めるのに、ZDR では止めません。 材料は公開されています。 適格性の表も、Google 側の同種の記述も、認証なしで読めます。 そして、この突き合わせを作らないのはモデル提供元です。 「あなたのコードは自分で結んだ ZDR の外へ出ている」と名指しする道具は、自社の高機能 API の利用を抑制します。

3件は、差分の見つけ方が異なります。 1つ目は自社の観測と公開記述を突き合わせ、2つ目は依存ツリーと公開記述を突き合わせ、3つ目は自社のコードと公開記述を突き合わせます。 以下では、それぞれについて先客が止まっている境界線を明示したうえで、個人が入れる位置を探しました。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: outage-ledger (自社のログが記録した障害時間と、ベンダーが公開したインシデント史・稼働率算出方法を突き合わせ、未報告と過小分類の差分を請求期限つきの台帳として出すローカル検査)

自社の既存ログ（ロードバランサのアクセスログ、アプリの外部呼び出しエラー、監視の合成チェック）を入力に取り、ベンダーが公開したインシデント履歴と突き合わせるローカル CLI です。 出力は稼働率のダッシュボードではありません。 差分の台帳です。

行は3種類しかありません。 自社は落ちたがベンダーは何も報告していない区間、ベンダーは報告したが Degraded として稼働率に算入していない区間、そして双方が一致した区間です。 一致した区間には、SLA のしきい値とクレジット率、そして請求の締切日が付きます。

検知した生の声（リンク付きエビデンス）

第一に、未報告の障害が例外ではなく毎月の定量である点です。

Perhaps more concerning than delayed acknowledgments are the 104 incidents that vendors never officially reported at all. — IsDown, April 2026: IsDown Users Saved 16.5 Hours with Early Outage Detection

同じ記事は、この状態を次のように表現しています。

These "invisible outages" represent real user experiences that teams relying solely on vendor status pages would never know about — 同上

第二に、報告された障害であっても、分類の選択によって稼働率が動かない構造がある点です。 GitHub が2026年4月に導入した稼働率の算出方法について、次の指摘があります。

A service can have visible customer pain without lowering the published uptime percentage if GitHub classifies the incident as Degraded Performance. — Solomon Neas, GitHub Availability in April 2026: What the Status Page Misses

Degraded Performance counts as zero downtime in the published uptime calculation, so the headline percentages can stay high while developer pain is acute. — 同上

第三に、当事者が実際に請求で詰まっている点です。 Microsoft Q&A に投稿された顧客の記述です。

We are writing to raise a serious concern about our support request # 2510290040010571, opened in relation to the significant outage on October 29, 2025 (which affected Azure services globally). Despite the magnitude of the incident and the serious business impact we experienced, we have not received any meaningful response — no email, no phone call, no escalation. — Microsoft Q&A, We Were Impacted by Azure Downtime, Open Support Case Ignored

同じスレッドには、1か月後の追記があります。

After ONE MONTH we opened the case still not a solution — 同上

第四に、判定に必要な契約側の材料が既に公開データセットとして存在する点です。

Open dataset of standard SLA credit schedules for the major cloud providers. — Velprove, Cloud Provider SLA Terms

このデータセットは AWS・Google Cloud・Azure・Cloudflare・Vercel を対象とし、「Machine-readable JSON, maintained as terms change」として CC-BY-4.0 で配布されています。

パターン判定 & Why Now

references/market-analysis-patterns.md のマイクロDevExツール型と価格破壊・ローカルファースト型の複合です。

Why Now は3つあります。 第一に、大規模障害が2026年に密集し、GitHub の8月17日の停止のように開発の主要導線ごと止まる事例が続いています。 第二に、稼働率の算出方法をベンダー自身が公開し始めたことで、分類が稼働率に与える影響を第三者が計算できるようになりました。 公開されていなければ突き合わせようがなかった材料が、透明性の名目で出てきています。 第三に、SLA クレジット表の機械可読な公開データセットが CC-BY で利用できるため、契約条件の構造化という最も面倒な工程が既に済んでいます。

先客が止まっている境界線

この領域には既に製品があります。 境界線を引くために、先客自身の記述を読みます。

ServicePulse は次のように述べています。

AI reads your vendor contracts, tracks uptime against SLA targets, and drafts the credit-request email when a vendor breaches — ServicePulse

Reclivio は、監視の入力元を次のように明示しています。

Connects to status pages, API health endpoints, and public incident feeds. — Reclivio

境界線はここです。 先客は全員、ベンダーが公開した記述を真として起点に置いています。 だから、ベンダーが何も書かなかった104件も、Degraded と書いた区間も、先客の出力には現れません。 先客が解決したのは「ベンダーが認めた障害を、契約条件へ換算する」ところまでです。 解決していないのは「ベンダーの記述が、自社の観測と食い違っている」ところです。

この非対称には理由があります。 ステータス集約サービスの商品は、ベンダーの公開フィードそのものです。 その一次情報の正しさを否定する出力は、自社の商品の前提を否定します。

リスク・反証分析

最大のリスクは、差分を出しても請求が通らないことです。 SLA の多くは自社観測を証拠として受け付けず、ベンダー側のインシデント ID を要求します。 Azure の申請要件がまさにこれで、Service Health のインシデント ID が必要です。 未報告の障害には、定義上インシデント ID がありません。 つまり、最も価値のある差分（未報告分）が、最もクレジットになりにくい差分です。

対策は、出力の主目的をクレジット請求から交渉と調達の材料へずらすことです。 更新交渉の場に「過去12か月で貴社が報告しなかった障害が自社観測で N 分」という表を持ち込む用途、および複数ベンダーの候補比較で「公開稼働率と実測の乖離」を並べる用途は、インシデント ID を必要としません。

第二のリスクは、自社観測そのものが誤りである可能性です。 自社側のネットワーク・DNS・クライアント実装の問題をベンダー障害として数えれば、台帳は信用を失います。 対策は、単一の障害を「ベンダー障害」と断定せず、同一ベンダーの複数リージョン・複数経路で同時に観測された区間だけを差分候補へ昇格させる制約を初期から入れることです。

第三のリスクは、先客の追随です。 自社テレメトリの取り込みは、技術的に難しい機能ではありません。 ServicePulse が月額29ドルで既に価格の天井を作っているため、追随された場合の価格競争は不利です。

アイデア 2: sdk-declare (依存ツリーを解析し、各 SDK が公開しているデータ安全性の開示内容を合算して、Google Play へ提出済みの申告との差分を出すローカル検査)

Gradle または Podfile の依存ツリーを入力に取り、各 SDK が公開している「Play data disclosure」ページの内容を突き合わせるローカル CLI です。 出力は申告フォームの下書きではありません。 申告漏れの候補一覧です。

行は「この依存が公開ページで宣言しているデータ型」と「あなたの提出済み申告に含まれているか」の対で構成されます。 推移的依存で入ってきた SDK も対象に含めます。

検知した生の声（リンク付きエビデンス）

第一に、Google が申告責任を開発者へ一本化している点です。

You alone are responsible for making complete and accurate declarations in your app's store listing on Google Play. — Play Console Help, Provide information for Google Play's Data safety section

そのうえで、第三者 SDK の収集も申告対象だと明示しています。

This includes data collected and handled through any third-party libraries or SDKs used in their apps. — 同上

執行についても記述があります。

When Google becomes aware of a discrepancy between your app behavior and your declaration, we may take appropriate action, including enforcement action. — 同上

第二に、当事者が実際にリリースを止められている点です。 OSS の Wikimedia Commons Android アプリのイシューに、Google からの通知が記録されています。

We detected user data transmitted off device that you have not disclosed in your app's Data safety form as user data collected. — commons-app/apps-android-commons Issue #5708

同じ通知には、Google 自身が網羅性を保証しない旨の但し書きが含まれます。

this list of SDKs may not be exhaustive — 同上

第三に、判定材料が SDK 側から公開されている点です。 AdMob の公開ページは、自 SDK が収集するデータ型を明示しています。

Collects Android advertising (ad) ID, app set ID, and, if applicable, other identifiers related to signed-in accounts on the device. — Google, Google Play data disclosure (AdMob)

第四に、開発者が自力では確かめられないという学術的な裏づけです。

the opacity of SDKs' operations and their "black-box" nature hinders meaningful assessments, leaving both end-users and app developers in the dark — A Large-Scale Privacy Assessment of Android Third-Party SDKs

パターン判定 & Why Now

規制・プラットフォーム変更対応型とマイクロDevExツール型の複合です。

Why Now は2つです。 第一に、Play Console が提出前の自動チェックを走らせるようになり、申告漏れが人手のポリシーレビューではなく機械判定でのブロックとして返るようになりました。 不整合が確率的な指摘から、決定論的な障害へ変わっています。 第二に、Google が SDK 提供者に開示ページの公開を求めた結果、突き合わせの右辺が公開ドキュメントとして揃いました。 数年前は各 SDK のプライバシーポリシーを人手で読むしかありませんでした。

先客が止まっている境界線

隣接する先客は3種類います。 MMP（Adjust、Singular）は自社 SDK 分の申告ガイドを配りますが、対象は自社 SDK に限られます。 プライバシー静的解析（動的トラフィック解析を含む学術系ツール）は実挙動を測りますが、Play の申告フォームの語彙へ写像しません。 汎用のページ変更監視は、SDK の開示ページが変わったことを教えますが、あなたの依存ツリーを知りません。

境界線はここです。 誰も、依存ツリーと公開開示ページと提出済み申告の3つを同時に見ていません。 先客が解決したのは「1つの SDK について、何を申告すべきか」までです。 解決していないのは「あなたのアプリ全体で、申告すべき集合は何か」です。

この非対称にも理由があります。 SDK 提供者にとって、自 SDK の開示を依存ツリー全体で合算して見せる道具は、導入の心理的コストを可視化する道具でもあります。

リスク・反証分析

最大のリスクは、公開開示ページ自体が正しくないことです。 先の学術調査は、SDK の公開ポリシーと実挙動の乖離を定量しています。

40 out of 109 (36.7%) SDKs collected excessive privacy data compared with their privacy policies — A Large-Scale Privacy Assessment of Android Third-Party SDKs

つまり、公開ページを信じて申告を作ると、実挙動より過小な申告になり得ます。 これは Google の機械判定が拾う方向の誤りであり、この道具が防ぎたい事象そのものです。

対策は、出力を「申告すべき集合」と断定せず、「公開開示に基づく下限」と明示することです。 下限を満たしていない申告は確実に不整合であり、下限を満たしていても安全とは限らない、という二段の表現に限定します。

第二のリスクは、対応表の維持です。 AdMob の開示ページは人間向けの表であり、機械可読ではありません。 しかもバージョン別ではなく最新版のみの記載です。 上位50 SDK に絞っても、追随は恒常的な固定費として残ります。

第三のリスクは、買い手の財布です。 個人の Android 開発者は無償を期待する層であり、法人のモバイルチームへ届ける導線を別に作る必要があります。

アイデア 3: zdr-drift (コードと設定から LLM API の機能利用箇所を抽出し、各社が公開している ZDR / HIPAA 適格性の表と突き合わせて、黙って契約の外へ出ている呼び出しを名指しする検査)

リポジトリと実行時設定を入力に取り、使用している API 機能とモデルを抽出するローカル CLI です。 出力はコード品質の指摘ではありません。 契約外へ出ている呼び出しの位置です。

検知した生の声（リンク付きエビデンス）

第一に、ZDR では不適格機能の呼び出しが止まらない点です。 Anthropic の公式ドキュメントの記述です。

Under ZDR, the API does not block these features; using one is a choice to step outside your ZDR arrangement for that specific data, and the feature's own documented retention policy applies. — Claude Platform Docs, API and data retention

同じ段落は、HIPAA 側の挙動を対比しています。

Under HIPAA readiness, the API blocks requests that include a "No" feature and returns a 400 error, unless the feature's Details column says otherwise. — 同上

不適格になる理由も明示されています。

Features marked "No" for ZDR are typically stateful (they store jobs, files, or container state), which is why they cannot be zero-retention. — 同上

第二に、同じ構造が他社にもある点です。 Gemini の ZDR ドキュメントは、無効化できない保存を明記しています。

There is no way to disable the storage of this information if you use Grounding with Google Search. — Google AI for Developers, Zero data retention in the Gemini Developer API

つまり、ZDR を結んだ組織が Batch API・Files API・コード実行・MCP コネクタ・グラウンディングのいずれかを足した瞬間、エラーは出ないまま契約の前提が崩れます。 壊れ方が「静か」である点が、この課題の本質です。

パターン判定 & Why Now

規制・プラットフォーム変更対応型です。

Why Now は、各社が機能別の適格性を表として公開し始めたことです。 数か月前まで、この情報は営業担当への問い合わせでしか得られませんでした。 公開された結果、突き合わせが第三者にも可能になりました。

先客が止まっている境界線

コンプライアンス SaaS（Vanta、Drata）は、契約と方針の層で「ZDR を締結しているか」を管理します。 LLM 向けスキャナ（promptfoo など）は、プロンプトインジェクションや PII 露出というセキュリティの層を見ます。

境界線はここです。 誰も、コードの機能利用と契約の適格性表を突き合わせていません。 先客が解決したのは「契約が存在するか」と「コードが安全か」です。 解決していないのは「コードが契約の内側にあるか」です。

提供元がこれを作らない理由も明確です。 不適格機能は、いずれも上位の高機能 API です。 利用を抑制する方向の警告を、提供元は自ら出しません。 実際、Anthropic は HIPAA では 400 で止める一方、ZDR では止めないという設計を選んでいます。

リスク・反証分析

最大のリスクは、買い手の母数です。 ZDR や BAA を締結している組織は限られます。 個人開発者の顧客層ではなく、医療・金融の AI 導入チームです。 そこへ個人が売る場合、信頼の壁が価格より先に立ちます。

対策は、初期の配布を監査法人・コンプライアンスコンサル経由に絞り、直販を狙わないことです。 彼らは既に信頼を持ち、検査の道具を欲しています。

第二のリスクは、静的抽出の取りこぼしです。 機能利用は SDK の引数、設定ファイル、環境変数に散在します。 「該当なし」を安全と誤読させる出力は、無いより有害です。 対策は、検出できなかった経路を明示的に列挙する設計にすることです。

第三のリスクは、表の追随です。 適格性の表は機能追加のたびに変わります。 古い表は、既に適格になった機能を不適格と言い続けます。

配点理由

Idea 1: outage-ledger — 19点 (Tier 2)

  • タイミング 4: 未報告インシデントが1月101件・3月87件・4月104件と、単月の異常ではなく定常の水準で続いています。加えて GitHub が稼働率の算出方法を公開したことで、分類が稼働率に与える影響を外部から計算できるようになりました。対象は SaaS を業務で使う全組織であり、母数は3案で最大です。減点材料: 「この日までに対応しないと罰がある」という共通の期限がありません。請求期限はベンダーごとに散らばり、しかも請求が主目的にならない（後述）ため、購買のトリガーが弱い。5点は付けられません。
  • 技術的実現可能性 4: 右辺の材料は揃っています。Statuspage 系の履歴は JSON と RSS で読め、SLA クレジット表は CC-BY-4.0 の機械可読データセットが存在します。突き合わせのロジック自体は区間演算であり平易です。減点材料: 左辺、つまり自社観測の取り込み口が事業者ごとに異なります。ALB のアクセスログ、CloudFront のログ、アプリの構造化ログ、監視 SaaS のエクスポートと、入力形式が散らばります。2週間で1系統は届きますが、複数系統の正規化は MVP の外へ出さざるを得ません。
  • 収益性 3: 買い手は情報システム部門と SRE であり、予算は組織にあります。減点材料: 価格の天井が既に外部から決まっています。ServicePulse が月額29ドル・99ドルの階梯を、Reclivio が月額99ドル・399ドルの階梯を公開しており、後発が上を取る理由を説明できません。加えて、クレジット請求の成功報酬という個人にとって最も収益性の高い形は、契約主体になれない以上取れません。「誰がいくら払うか」を具体的に書けるのは月額10〜20ドルの水準までであり、4点は付けられません。
  • 競合優位性 4: 3案で最も明確に境界線が引けます。Reclivio は入力元を「Connects to status pages, API health endpoints, and public incident feeds」と自ら明示しており、顧客側のテレメトリを見ていません。ServicePulse も契約と稼働率の突き合わせに留まります。未報告と過小分類は、構造上、先客の出力に現れません。 しかもステータス集約の商品はベンダーの公開フィードそのものであり、その正しさを否定する出力は自社商品の前提と衝突します。利益相反が実在します。減点材料: 大手が3か月で真似したら、自社ログの取り込みを1系統足すだけで境界線は消えます。技術的な参入障壁ではなく、動機の非対称に依存した優位です。5点は付けられません。
  • 個人開発適性 4: ローカル CLI として完結し、ログを外部へ送りません。サーバーもデータベースも不要で、判定はすべて手元で完結します。減点材料: ステータスページの形式差分の追随が恒常的な固定費です。Statuspage、Instatus、自社実装が混在し、履歴の粒度も統一されていません。追随を止めると、静かに「差分なし」を返し続けます。

Idea 2: sdk-declare — 18点 (Tier 2)

  • タイミング 4: Play Console が提出前に自動チェックを走らせるようになり、不整合が人手のレビュー指摘から機械判定のブロックへ変わりました。リリースが止まるという直接の損失があり、購買動機は明確です。減点材料: 対象が Android アプリの配信者に限られ、Idea 1 より母数が一桁小さい。また期限型の圧力ではなく常時圧であるため、「今月中に買う」理由がありません。5点は付けられません。
  • 技術的実現可能性 4: Gradle の依存ツリー出力から推移的依存まで列挙する処理は既存コマンドで済みます。突き合わせは集合演算であり、2週間で下限判定までは届きます。減点材料: 右辺の材料が機械可読ではありません。AdMob の開示ページは人間向けの表であり、しかも最新バージョンの記載しかありません。バージョン別の差異を扱えないため、対応表は「最新版前提の近似」に留まります。
  • 収益性 3: 1回のリリースブロックの損失は大きく、法人のモバイルチームには支払い理由があります。減点材料: この領域の道具は無償が既定です。個人の Android 開発者に月額を課すのは難しく、CI 組み込みの法人向けに切り替えるにはサポート負荷が上がります。「100人で月10〜20万円」を満たす価格を説明できません。
  • 競合優位性 3: 依存ツリー・公開開示・提出済み申告の3点を同時に見る道具は見つかりませんでした。ここは空いています。減点材料: 突き合わせの上限が、右辺の正確さで決まってしまいます。SDK の36.7%が公開ポリシーより多く収集しているという調査結果がある以上、公開開示だけの突き合わせでは Google の機械判定に届きません。大手が3か月で真似したら、Play Console が「あなたの AAB に含まれる SDK の宣言済み収集」を表示するだけで消えます。しかも Google は既に検出側の実装を持っています。4点は付けられません。
  • 個人開発適性 4: ローカル完結で、AAB もソースも外部へ送りません。減点材料: 上位 SDK の対応表を人手で維持する必要があり、Idea 1 と同種の固定費が残ります。加えて、誤って「申告漏れなし」と返した場合の損害がリリース停止として直接ユーザーに当たります。

Idea 3: zdr-drift — 17点 (Tier 2)

  • タイミング 3: 各社が機能別の適格性表を公開したのは直近であり、突き合わせが可能になったこと自体は新しい変化です。ZDR では不適格機能がブロックされないため、違反が無音で発生する構造も明確です。減点材料: 3案で最も母数が薄い。ZDR や HIPAA readiness を締結している組織に限られ、しかもそうした組織は既に法務レビューの体制を持っています。「明確な課金動機」はありますが、対象が狭すぎるため4点には届きません。
  • 技術的実現可能性 4: 適格性の表は公開済みで、機能とエンドポイントの対応が明示されています。SDK の引数と設定を走査して突き合わせる処理は軽量です。減点材料: 静的抽出の取りこぼしが「該当なし＝安全」という誤答に直結します。機能の有効化は引数・設定ファイル・環境変数・上位フレームワークの既定値に分散し、リポジトリ走査だけでは網羅できません。最も価値の高い判定が、最も難しい部分に依存しています。
  • 収益性 3: 監査の文脈に載れば、検査1回あたりの単価は3案で最も高く取れます。減点材料: 母数が薄く、直販が効きません。信頼が価格より先に効く領域であり、個人が売り手として立つには代理店経由の導線が要ります。その導線の構築は MVP の外にあり、収益化までの距離が3案で最長です。
  • 競合優位性 3: コードの機能利用と契約の適格性表を突き合わせる道具は見つかりませんでした。提供元が作らない理由も明快で、不適格機能はいずれも上位の高機能 API です。減点材料: 差別化が「表を機能利用へ写像する」一点に依存します。大手が3か月で真似したら、公式 SDK が ZDR 契約テナントに対して HIPAA と同じ警告を出すだけで消えます。実装は数十行であり、しかも Anthropic は HIPAA 側で既にその実装を持っています。設計判断が変われば一夜で消える優位です。
  • 個人開発適性 4: ローカル完結で、コードを外部へ送りません。認証情報も不要です（デプロイ照会を行わない設計に限る）。減点材料: 適格性表の追随が固定費であり、しかも誤りの方向が「不適格」に偏ると、ユーザーに不要な機能制限を負わせます。

4. リスク・反証分析 (Fail-safe Analysis)

3案に共通する構造的なリスクを1つ挙げます。

「先客に不都合な突き合わせ」は、差別化を作る一方で、受益者を支払意思の低い側へ寄せます。

今回の探索軸は、材料の公開と利益相反の積で絞りました。 狙いどおり、3案とも境界線を先客自身の記述から引くことができました。 Reclivio の入力元の記述、Google の申告責任の記述、Anthropic のブロックしない旨の記述が、それぞれ空白の存在証明になっています。

しかし、突き合わせの結果が不都合なのは支払う側であって、買う側ではありません。 買う側は、その不都合を突きつける立場の顧客企業です。 そして顧客企業にとって、この突き合わせが生む金額は小さい。 未報告障害のクレジットは請求できず、申告漏れの回避は損失の予防であり、ZDR の逸脱は監査の指摘の予防です。 いずれも「増える金」ではなく「減らない金」です。

この構造が、3案とも軸3（収益性）が3点で止まった直接の理由です。

対策として現実的なのは2つです。 第一に、支払意思の高い代理人へ売ることです。 Idea 3 の監査法人経由がこれに当たり、彼らは検査結果を自社の商品に組み込めるため、予防価値をそのまま価格へ転嫁できます。 第二に、予防ではなく交渉の材料として売ることです。 Idea 1 の更新交渉用途がこれに当たり、値引き交渉の根拠になれば金額が確定します。

6. スクリーニング結果と提案候補 (参考情報)

  • 最優先で検証すべき候補: outage-ledger (総合19点、Tier 2)。境界線が先客自身の記述から引けており、右辺の材料が公開データセットとして揃っている点が3案で最も強い。着手は Day 1 の事前検証の結果を見てから判断すべきであり、差分が出なければ全体を破棄する。
  • 今回却下した候補と理由:
    • サイバー対処能力強化法の届出・報告対応（2026年10月1日施行）: 期日圧は今回調べた中で最も強く、届出は原則導入日から4か月以内、施行時点で導入済みの機器は2027年3月31日が期限、違反には200万円以下の罰金が科されます。しかし対象は15業種257社の基幹インフラ事業者に限定され、調達が個人開発者へ開いていません。買い手の母数と参入経路の両方で成立せず、総合13点で却下しました。
    • サブプロセッサ変更の異議申立期限の追跡: Microsoft が2026年5月22日に AI サブプロセッサの通知期間を6か月から30日へ短縮しており、探索軸には合致します。しかし PageCrawl・PageGuard・Registora など変更監視の先客が密集しており、差分は「自社 DPA の異議期限を計算する」一点のみです。模倣に3か月かからず、総合14点で却下しました。

  • 11回連続で Tier 1 に到達していません。 今回の探索軸は、狙った軸では機能しました。軸4（競合優位性）の平均が3.33点であり、前回の3.00点から改善しています。3案とも、先客が止まっている位置を先客自身の記述から特定できました。境界線が引けないアイデアを落とすという Phase 2 の制約が、初めて実質的に働いています。 同時に、軸2（実現可能性）の平均は4.00点を維持しました。前回崩れた交換関係が、今回は崩れていません。材料の公開と利益相反の積で絞る方法は、この2軸を同時に保つという当初の目的を達成しています。 一方で、3案とも軸3（収益性）が3点で揃いました。 平均3.00点であり、前回と同水準です。理由は第4節に書いたとおりで、突き合わせの結果が不都合な相手は支払う側であり、買う側ではないという構造にあります。買う側が得るのは「減らない金」であって「増える金」ではないため、価格を説明できる上限が低く止まります。 次回の探索軸は、この積に第三の条件を足します。「材料が公開されている」かつ「突き合わせが先客に不都合」かつ「突き合わせの結果が買い手にとって金額または期限として即座に確定する」の積で絞ります。予防価値で止まる案は、軸4がいくら高くても軸3で頭打ちになることが、今回の3案で揃って確認できました。
