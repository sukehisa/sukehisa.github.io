1. 調査の背景と市場の変曲点

前回（2026-09-26）は、OpenAI Reusable Prompts/Evals の提供終了や Google Ads API v22 の停止など、AI基盤や広告APIの仕様撤退を検証しました。 ベンダーがプラットフォーム機能を打ち切ることで、利用者がコードへの退避を余儀なくされる現象を扱いました。

今回は、クラウドインフラとアイデンティティ基盤において「単一サービスとして完結していたものが強制的に分解・分裂する」変曲点を検証します。 提供元の都合により、これまで1つの画面やAPIで管理できていたワークフローが複数の異質なサービスへ解体される現象です。

クラウド事業者は運用効率化や責任境界の再定義を理由に、レガシーな統合基盤を閉鎖します。 しかし、移行先として案内されるのは「別々のサービスを組み合わせて自力で再構築せよ」という分散構成です。 単一の受け皿が存在しないため、現場のエンジニアは散らばった設定の再設計と配線の繋ぎ直しを強いられます。

2026年秋から冬にかけて、以下の3つの解体・分裂が開発現場を直撃します。

  • Amazon Pinpoint の完全終了（2026年10月30日にコンソールおよびジャーニー、セグメント、キャンペーンが全削除されアクセス不能になる）
  • Docker Content Trust（Notary v1）の完全閉鎖（2026年12月8日に notary.docker.io が停止し、CI/CD やクラスタ内の DOCKER_CONTENT_TRUST=1 が突発死する）
  • Microsoft Entra Privileged Identity Management（PIM）Iteration 2 beta API の退役（2026年10月28日に単一の /beta/privilegedAccess が消滅し、Graph API と ARM API の2系統へ分裂する）

3者とも、公式からは「複数の代替サービスへ移行せよ」という指針しか与えられていません。 散らばるロジックを吸い出し、軽量な代替基盤へ自動変換するマイグレーションツールの需要が急速に高まっています。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: pinpoint-journey-bridge (Amazon Pinpoint 2026年10月30日完全終了に伴うジャーニー・セグメント定義抽出 & AWS Step Functions / OneSignal 互換自動変換 CLI)

対象は、Amazon Pinpoint を用いてユーザーオンボーディング、リエンゲージメントのステップ配信（ジャーニー）、動的セグメント、メッセージテンプレートを本番運用してきたプロダクトマネージャーおよびグロースエンジニアです。

入力は2つです。 1. Pinpoint Application ID および AWS 認証情報（pinpoint:GetApp, GetSegments, GetCampaigns, GetJourneys 権限） 2. 移行先の実行ターゲット指定（軽量サーバーレス step-functions または外部CEP onesignal / customerio）

出力は次の3点です。 1. Pinpoint 内の全動的セグメント条件、ジャーニー定義（有向グラフ、待機時間、条件分岐、イベントトリガー）、メッセージテンプレートの一括JSONエクスポート 2. 移行先に応じた実行可能定義への自動トランスパイル（AWS Step Functions ASL定義 + EventBridgeルール、またはOneSignal Journeys互換JSON） 3. 送信テストと機能ギャップ診断レポート（移行先で未サポートとなる条件式の可視化と代替提案）

本体は2番目と3番目です。 単にエンドポイント（顧客リスト）を S3 へエクスポートするだけなら AWS 標準機能でも可能です。 本質的な価値は、Pinpoint の画面上で非エンジニアが組んだ「3日後にメール送信、開封したらプッシュ通知、未開封ならSMS」というジャーニーロジックを有向グラフとして保ったまま、代替基盤で動くコードへ変換することです。

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、AWS 公式ドキュメント自身が 2026年10月30日の完全終了とリソースへのアクセス喪失を明記している事実です。

End of support notice: On October 30, 2026, AWS will end support for Amazon Pinpoint. After October 30, 2026, you will no longer be able to access the Amazon Pinpoint console or Amazon Pinpoint resources (endpoints, segments, campaigns, journeys, and analytics)...If you are using Amazon Pinpoint engagement features (endpoints, segments, campaigns, journeys, and analytics), we recommend you to migrate to Connect Customer proactive engagement solutions...to manage inbound and outbound using one unified application. — Amazon Pinpoint end of support | AWS Documentation

さらに、開発者コミュニティや導入支援現場（AWS re:Post、r/aws）では、AWS が推奨する「Amazon Connect への移行」がコンタクトセンター向けで重厚すぎる点、そして移行ツールが存在しないことへの悲鳴が上がっています。

The migration from Amazon Pinpoint is a major architectural undertaking...The primary pain stems from the fact that Pinpoint is being sunset as a unified marketing suite, and there is no single drop-in replacement. Moving away requires splitting workloads across at least four different AWS services: Amazon SES for email, Amazon Connect for outbound campaigns, Amazon Kinesis for analytics, and AWS End User Messaging for SMS/push. Because there is no automated tool that migrates the logic of your journeys and segments, many teams are forced to rebuild workflows from scratch. — AWS Community Discussions on Pinpoint Discontinuation & Migration Hurdles

画面上で組んでいたチームは、10月30日までに全ジャーニーを退避させなければ、施策が物理的に停止します。 しかし、大規模なコールセンター基盤である Amazon Connect を契約したくないチームにとって、自前で Step Functions を組む工数は膨大です。

パターン判定 & Why Now

パターンは規制・プラットフォーム変更対応型とワークフロー糊付け・連携型の複合です。

Why Now は、2026年10月30日という完全終了期限（あと33日）です。 10月末を迎えた瞬間にコンソールもAPIも遮断されるため、今すぐ移行を実行しなければならない切迫した締め切りが存在します。

境界線は以下のとおりです。

  • 解決済み: AWS 公式による顧客データ（エンドポイントCSV）の S3 エクスポート、および SES v2 向け単体メールテンプレート移行スクリプト。
  • 未解決: 「ジャーニーの分岐ロジック・待機時間」と「セグメントの動的ルール」を抽出し、代替の軽量実行基盤（Step Functions / EventBridge）へ自動コード化するマイグレーションパイプライン。

アイデア 2: dct-to-cosign (Docker Content Trust / Notary v1 2026年12月8日完全閉鎖に伴う CI/CD 署名パイプライン & Kubernetes ポリシーの Sigstore/Cosign 自動移行 CLI)

対象は、セキュリティ基準（SOC2, SLSA, PCI-DSS等）に基づき DOCKER_CONTENT_TRUST=1 や docker trust を CI/CD パイプライン（GitHub Actions, GitLab CI）や Kubernetes クラスタ（Kyverno, Gatekeeper）で運用してきたインフラエンジニア・DevSecOps 担当者です。

入力は2つです。 1. CI/CD リポジトリ群（ワークフローYAML、Dockerfile、デプロイスクリプト） 2. 既存の Notary v1 レジストリおよび署名ポリシー設定

出力は次の3点です。 1. コードベース内の DOCKER_CONTENT_TRUST 環境変数、docker trust sign/inspect コマンド、Notary 鍵参照箇所の静的検出 2. 現代標準である Sigstore/Cosign（GitHub Actions OIDC キーレス署名）または CNCF Notation への CI ワークフロー自動書き換えパッチ（Unified Diff） 3. Kubernetes クラスタ検証ポリシー（Kyverno ClusterPolicy や Gatekeeper Constraint）の Notary v1 から Cosign/Notation 署名検証への自動置換マニフェスト生成

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、Docker 公式ドキュメント自身が Notary v1 サービスの 2026年12月8日完全シャットダウンを明記している事実です。

Docker Content Trust (DCT) and the Notary v1 service at notary.docker.io are being fully retired. If you've never set DOCKER_CONTENT_TRUST=1 or used docker trust commands, this change doesn't affect you. The service shuts down completely on December 8, 2026, following brownout windows in July and August. For the timeline, migration guidance, and modern alternatives such as Sigstore/Cosign and Notation, see the Docker Content Trust retirement and migration blog post. — Deprecated and retired Docker products and features | Docker Docs

さらに、Docker Docs のセキュリティページでも明確な警告が出されています。

Docker Content Trust (DCT) is being retired. The Notary v1 service at notary.docker.io will shut down on December 8, 2026. — Content trust in Docker | Docker Docs

すでに2026年夏から計画的なブラウンアウト（一時的シャットダウン試験）が実施されており、環境変数を放置していた企業のビルドパイプラインで散発的な障害が発生しています。 12月8日を過ぎると、未署名イメージのブロックだけでなく、信頼検証そのものが接続タイムアウトで即座にビルドエラーを起こします。

パターン判定 & Why Now

パターンは規制・プラットフォーム変更対応型とマイクロDevExツール型の複合です。

Why Now は、2026年12月8日の Notary v1 サービス停止期限です。 サプライチェーンセキュリティの認証を維持しながら、旧来の静的暗号鍵ペア運用から OIDC キーレス署名（Cosign）へ切り替える絶好の変曲点となっています。

境界線は以下のとおりです。

  • 解決済み: Docker 公式ブログに記載された「Cosign や Notation を使いましょう」という概念レベルの推奨事項。
  • 未解決: 散らばった GitHub Actions や Kubernetes マニフェストから DCT 依存を洗い出し、GitHub OIDC キーレス署名と Kyverno 検証ポリシーへワンコマンドで書き換えるマイグレーション支援。

アイデア 3: pim-split-migrate (Microsoft Entra PIM Iteration 2 beta API 2026年10月28日完全退役に伴う Graph API / ARM API 自動分離＆スクリプト互換パッチ CLI)

対象は、Microsoft 365 / Azure 環境において、社内の JIT（Just-In-Time）権限昇格スクリプト、Slack/Teams 承認ボット、運用自動化バッチ、カスタムポータルを運用している情シス・クラウドインフラエンジニアです。

入力は2つです。 1. 社内スクリプト・リポジトリ（PowerShell, Python, TypeScript, Bash, Terraform） 2. Entra テナント設定情報

出力は次の3点です。 1. コード内の /beta/privilegedAccess（/aadRoles および /azureResources）呼び出し箇所の静的検出 2. リクエスト対象（ディレクトリロールかAzureリソースか）に基づく、Microsoft Graph API 用コードと Azure Resource Manager (ARM) API 用コードへの自動分離パッチ 3. 認証トークン取得部（Audience: graph.microsoft.com vs management.azure.com）の自動分離および必要な API 許可権限のチェックリスト生成

検知した生の声（リンク付きエビデンス）

決定的なエビデンスは、Microsoft 公式ドキュメント自身が Iteration 2 (beta) API の 2026年10月28日完全停止と、Iteration 3 でのAPI分裂を明記している事実です。

Under the /beta/privilegedAccess endpoint, Microsoft supported both /aadRoles and /azureResources segments for managing Microsoft Entra roles and Azure resource roles, respectively. This endpoint is deprecated and will stop returning data on October 28, 2026. Microsoft recommends against starting any new development with these APIs...Iteration 3 (Current) includes: PIM for Microsoft Entra roles in Microsoft Graph API - Generally available; PIM for Azure resources in Azure Resource Manager API - Generally available. — API concepts in Privileged Identity Management | Microsoft Learn

これまで社内スクリプトは単一のエンドポイント /beta/privilegedAccess に同一のベアラートークンを渡すだけで、Entra ロール（全体管理者など）と Azure ロール（仮想マシン管理者など）の両方を昇格できました。 10月28日以降は、宛先ドメイン、要求するトークンの Audience、JSON ペイロードの階層構造が完全に2つに分裂するため、既存の社内スクリプトはすべて沈黙します。

パターン判定 & Why Now

パターンは規制・プラットフォーム変更対応型とマイクロDevExツール型の複合です。

Why Now は、2026年10月28日という完全退役期限（あと31日）です。 放置すると社内エンジニアの緊急権限昇格や当直対応の自動化スクリプトが突然動作しなくなり、本番障害対応の遅延に直結します。

境界線は以下のとおりです。

  • 解決済み: Microsoft Learn に記載された Iteration 3（Graph API / ARM API）の個別の仕様書。
  • 未解決: 旧エンドポイントを叩いていた社内スクリプトを、Graph API と ARM API の2系統の認証・スキーマへ自動トランスパイル・パッチ修正するツール。

4. 各アイデアの詳細分析 & 参考ロードマップ

最有力候補: pinpoint-journey-bridge (総合 21/25 点, Tier 1)

リスク・反証分析

  • 失敗する理由・最大のリスク: 1. 一過性のサンセット需要: 2026年10月30日の Pinpoint 完全閉鎖を過ぎると、移行需要がゼロになる。 2. 大手CEPによる無料インポーターの提供: OneSignal、Customer.io、Braze 等が自社への乗り換え施策として公式の Pinpoint ジャーニー移行スクリプトを無料公開するリスク。
  • 対策: 1. 「移行ツール」として売り切るだけでなく、移行後の「AWS Step Functions + EventBridge + SES v2 によるサーバーレス・マーケティング自動化フレームワーク」として継続販売する。 高額な外部 SaaS（月額数十万円）を契約せず、AWS 原価（月数百円〜数千円）だけでステップ配信を運用し続けたい開発者の定番スタックに昇華させる。 2. 競合 CEP が「自社 SaaS へのロックイン」を前提とするのに対し、本ツールは「自社の AWS アカウント内で完結するオープンな IaC（Terraform / CDK）」を出力することで、データ主権と低コストを重視する開発者の支持を固める。

参考ロードマップ (14日間 MVP)

  • Day 1: 【前提の事前検証】AWS SDK（Python/boto3）を用いて、Pinpoint の get_journey API から待機条件（Wait）、条件分岐（Yes/No）、アクティビティ定義が完全なグラフ構造として欠落なく抽出できるか、実アカウントで検証する。
  • Day 2-4: Pinpoint のジャーニー定義 JSON を読み込み、抽象構文木（AST）に正規化するパーサーの実装。
  • Day 5-7: 正規化したジャーニー AST から、AWS Step Functions の Amazon States Language（ASL）定義および EventBridge イベントルールを自動生成するコンパイラの実装。
  • Day 8-10: メール送信（SES v2）、SMS/Push送信（AWS End User Messaging）を実行する Lambda タスクコードと Terraform テンプレートの自動生成機能の実装。
  • Day 11-12: 抽出したセグメントルール（属性フィルタ）を DynamoDB / RDS クエリへ変換するマッパーの実装。
  • Day 13: ドキュメント作成、テスト自動化、GitHub リポジトリ公開、AWS 開発者コミュニティおよび Product Hunt へのローンチ告知。
  • Day 14: 初期ユーザーからのフィードバック収集と、複雑な多重分岐ジャーニーのエッジケース修正。

第二候補: dct-to-cosign (総合 20/25 点, Tier 2)

リスク・反証分析

  • 失敗する理由・最大のリスク:
    • セキュリティエンジニアは公式ドキュメントを読みながら手動で CI を直すことを好むため、設定自動生成ツールへの課金意欲が想定より低いリスク。
  • 対策:
    • 単なる YAML の置換にとどまらず、移行後の Kubernetes クラスタ側で「未署名コンテナの混入を100%遮断する Kyverno ポリシー」と「SLSA Level 3 準拠の来歴（Provenance）検証設定」をセットにした包括的なコンプライアンスパッケージとして差別化する。

5. まとめと推奨ネクストアクション

本リサーチでは、直近で生じた「マーケティング自動化の消滅」「コンテナ署名基盤の閉鎖」「PIM API の分裂」という3つのクラウド断層を検証しました。

最も推奨されるアイデアは、総合スコア 21点（Tier 1）を獲得した pinpoint-journey-bridge です。 Amazon Pinpoint の完全終了（2026年10月30日）まであと約1ヶ月に迫っており、世界中のプロダクト開発現場で「ジャーニーやセグメントのロジックをどう退避させるか」という切実な問題が発生しています。

公式の重厚な Amazon Connect への移行を避けたいチームに対し、オープンなサーバーレス構成（Step Functions + SES v2）へのトランスパイラを提供することで、即時の移行需要を獲得できます。 まずは Day 1 の事前検証（Pinpoint get_journey API からの完全なグラフデータ抽出確認）に着手することを推奨します。
