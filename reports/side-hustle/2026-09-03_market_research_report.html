1. 調査の背景と市場の変曲点

前回（2026-09-02）の終わりに、次回の探索軸を宣言しました。 金が動いた形跡があり、かつその金を受け取っていた側が構造的に手を出せない位置を探す、という軸です。 手を出せない理由として想定したのは利益相反でした。 乗り換えを助ける道具をクラウド事業者は作らず、許可リストの無効さを示す道具を IdP ベンダーは作らない、という構図です。

今回はこの軸を最初から当てて探索しました。 判定の手順は2段です。 第一に、その課題に対して現金の移動が公開情報として観測できること。 第二に、その現金を受け取っている事業者が、その道具を作ると自社の売上を削ること。 両方を満たす領域だけを候補に残しました。

この手順で見たとき、変曲点は3つに絞れました。

1つ目は、OpenSSL 3.0 のサポート終了です。 2026年9月7日、つまり4日後に、2021年9月7日リリースの 3.0 系列が上流の保守を離れます。 ここで観測できる現金は、延命サポートの契約料です。 OpenSSL Corporation は 3.0 に対する有償の延長サポートを提供しており、HeroDevs や TuxCare も EOL 版の保守を商品として売っています。 延命に金を払う顧客が現に存在するということは、EOL が金銭に換算される課題であることの証明です。 そして延命ベンダーは、「あなたのビルドは実は distro 側がまだパッチを当てているので契約は不要です」とは言えません。

2つ目は、前払式支払手段の基準日です。 2026年9月30日、つまり4週間後が、資金決済法の定める年2回の基準日にあたります。 ここで観測できる現金は、発行保証金の供託額です。 基準日未使用残高が1,000万円を超えた発行者は、その2分の1以上を法務局へ供託しなければなりません。 現金が実際に法務局へ積まれるという、極めて明瞭な金銭の移動です。 そしてポイント基盤や決済 SaaS のベンダーは、「あなたの残高はまもなく規制ラインを超えます」と顧客に告げる道具を作りません。 それは自社サービスの利用を萎縮させる通知だからです。

3つ目は、EUDI ウォレットの依拠当事者登録です。 2026年12月24日から規則が適用され、ウォレットのクレデンシャルを受け取る側は国の登録簿へ登録しなければなりません。 ここで観測できる現金は、本人確認の単価です。 ウォレット経由の受け入れは、1件あたり70〜100ユーロかかっていた顧客オンボーディングを3〜8ユーロへ落とすと報告されています。 差額がそのまま、これまで KYC ベンダーへ支払われていた金額です。 そして KYC ベンダーは、自社への支払いを消す移行を加速させる道具を作りません。

この3件は、現金の見え方が異なります。 1つ目は延命に払われている契約料、2つ目は法務局へ積まれる供託金、3つ目はこれまで検査1件ごとに払われていた単価です。 以下では、それぞれについて「受け取っていた側が作れない理由」を明示したうえで、個人が入れる位置を探しました。

2. 抽出されたビジネスアイデア候補と「生の声」

アイデア 1: eol-cliff (そのバイナリを誰がいつまでパッチするのかを出所から判定し、保守の断崖を先出しするローカル検査)

コンテナイメージやファイルツリーを走査し、含まれる各コンポーネントについて「このビルドを、誰が、いつまでパッチするのか」を出所の種別から判定するローカル CLI です。 出力は脆弱性の一覧ではありません。 保守の帰属先と、その帰属が切れる日付のカレンダーです。

この道具が答えるのは、既存のスキャナが答えない問いです。 既存のスキャナは「このバージョンに既知の CVE があるか」を答えます。 eol-cliff は「このバージョンに、これから CVE が出たとき、直す人がいるか」を答えます。

検知した生の声

Sonatype の2026年版サプライチェーンレポートは、EOL 版が脆弱性情報から抜け落ちる構造を正面から書いています。

EOL versions omitted from advisories gave organizations a false sense of security, masking risks that upstream maintainers no longer track.

— Vulnerability Management | 2026 Software Supply Chain Report（Sonatype）

同レポートは、この構造が生む誤りを件数で示しています。

Sonatype identified 20,362 false positives, or packages incorrectly marked as vulnerable ... and 167,286 false negatives, meaning exploitable components went unflagged entirely.

— 同上

見逃しが誤検知の8倍あります。 そして見逃しが起きる理由は、スキャナの実装ではなく、脆弱性情報そのものの作られ方にあります。

maintainers determine which versions are affected and file a CVE with a defined affected range. Every vulnerability scanner, SBOM tool, and CVE feed in the industry consumes that range. If your version falls outside it, you get no alert. Not because you're safe, but because no one checked.

— The EOL Blind Spot in Your CVE Feed: What SCA Tools Miss（BleepingComputer）

同記事は、EOL 版がその範囲から外れる理由と、外れた結果の規模を続けて書いています。

EOL versions fall outside that range almost by default.

— 同上

... approximately 80% of the time ... an unlisted EOL version is also affected ... Current tools track only ~7,000 EOL versions, yet analysis shows 5.4 million package versions are actually end-of-life ... these are versions actively appearing in enterprise SBOMs today, with no CVE investigation coverage.

— 同上

もう一方の誤り、つまり誤検知の側も、出所を見ないことから生じます。 Red Hat は、バージョン番号だけを見る検査が誤検知を出す構造を、自社の公式ドキュメントで説明しています。

Some security scanning and auditing tools make decisions about vulnerabilities based solely on the version number of components they find ... which results in false positives as the tools do not take into account backported security fixes.

— Security Backporting Practice（Red Hat Customer Portal）

見逃しと誤検知は、同じ一つの欠落から出ています。 すなわち、そのバイナリがどこから来たのかを見ていないことです。

4日後に起きること

2026年9月7日に、OpenSSL 3.0 系列のサポートが終了します。

系列リリースサポート終了位置づけ
OpenSSL 3.02021-09-072026-09-07LTS（今週終了）
OpenSSL 3.52025-04-082030-04-08現行 LTS
OpenSSL 4.02026-04-142027-05-14非 LTS

出所: Roadmap（OpenSSL Library） および endoflife.date

ここで決定的なのは、同じ 3.0.x という文字列が、出所によって全く違う意味を持つことです。

Ubuntu 22.04 LTS が配布する openssl パッケージは、Canonical の標準セキュリティメンテナンスが2027年5月まで、Ubuntu Pro の拡張セキュリティメンテナンスが2032年5月まで続きます（Ubuntu release cycle）。 つまり、Ubuntu 22.04 上の 3.0.x は9月8日以降もパッチされ続けます。

一方、同じイメージの中に静的リンクされた、あるいは vendor/ 配下へコピーされた 3.0.x は、9月8日以降誰もパッチしません。 distro のセキュリティ情報は、distro が管理するパッケージにしか効かないからです。

同じ数字が並んでいるファイルツリーの中に、生きている 3.0 と死んだ 3.0 が混ざっています。 その区別を、いまのスキャナは出力しません。

同じ形の断崖は、この数か月で連続して来ています。 Node.js 20 は2026年4月30日に、Python 3.10 は2026年10月31日に、それぞれ上流の保守を離れます。

パターン判定 & Why Now

market-analysis-patterns.md の分類では、マイクロ DevEx ツール型に該当します。 毎日発生するが誰も測っていない地味な不確実性を、1コマンドで消す位置です。

Why Now は日付そのものです。 9月7日を越えると、世界中のイメージの中で 3.0.x の意味が二分されます。 それまでは「まだ全部生きている」ため、この道具の出力は自明です。 8日から自明でなくなります。

需要側の圧力も同時期に立ちます。 EU サイバーレジリエンス法の第14条にもとづく報告義務が、2026年9月11日から適用されます。 HeroDevs はこの義務と EOL 依存の関係を、次のように書いています。

A new CVE gets published, exploitation is confirmed, and your 24-hour clock starts ticking, but there's no patch coming from the community.

— CRA Reporting Obligations Start September 2026（HeroDevs）

ただし本案は、この報告義務そのものを扱いません。 報告義務の起動判定と証跡管理は、2026-08-25 に cra-clock として別途提案済みであり、重複判定フィルタに触れます。 本案が扱うのは報告の前段、すなわち「パッチが来ない場所がどこにあるか」を先に知る工程です。

受け取っていた側が作れない理由

EOL 版の保守は、既に商品として売られています。 OpenSSL Corporation は 3.0 に対する有償の延長サポートを提供しており、HeroDevs は EOL 依存の追跡と保守を事業にしています。 この領域には、現に金が動いています。

そして、その金を受け取っている側は、この道具を作れません。 eol-cliff の出力の半分は、「あなたのこの 3.0.x は Ubuntu 22.04 のパッケージなので、2027年5月まで Canonical がパッチします。延命契約は要りません」という否定の答えだからです。 延命ベンダーにとって、これは自社の見込み客を減らす機能に他なりません。

スキャナベンダーの側にも、別の形の抑制が働きます。 EOL ブラインドスポットを製品の正面に置くことは、自社の検知率に構造的な穴があると認めることです。 Sonatype がレポートでこれを認めたのは、製品の機能としてではなく、業界分析としてでした。

アイデア 2: kijunbi-line (自社発行のポイント残高が資金決済法の基準額をいつ超えるかを、法定の合算単位で先出しするローカル計算機)

有償のクレジットやポイントを自社で発行しているサービス提供者に対して、資金決済法上の基準日未使用残高を法令の定義に沿って算定し、1,000万円の基準額までの距離と、超過が見込まれる基準日を出すローカルツールです。

会計上の前受金残高とは別物を計算します。 両者は一致しません。 一致しない理由が、そのままこの道具の存在理由です。

自家型前払式支払手段発行者は、基準日（毎年3月31日、9月30日）における未使用残高が最初に基準額（1,000万円）を超えたとき、当局へ届出を行う必要があります。

該当性の判定は、事業者が自分で行うには境界が細かすぎます。 日本資金決済業協会の Q&A は、判定を誤りやすい点を具体的に書いています。

課金 DB がどう作られているかで、同じ事業の同じ残高が、規制対象になったりならなかったりします。

パターン判定 & Why Now

規制・プラットフォーム変更対応型と、コミュニティ特化型の複合です。 特化先は、クレジット制・回数券制の課金モデルを採る国内の小規模 SaaS と個人開発サービスです。

Why Now は2026年9月30日です。 4週間後が基準日にあたり、そこで超過していれば届出期限は2か月後、供託はその時点の残高の2分の1です。 加えて、2026年6月12日に改正資金決済法が施行され、クロスボーダー収納代行が資金移動業の規律へ取り込まれるなど、周辺の線引きが動いた直後にあたります。

この課題には、成長そのものが引き金になるという性質があります。 クレジット制の課金は、売れるほど未使用残高が積み上がります。 事業が順調であることが、そのまま規制ラインへの接近です。 そして残高は毎日少しずつ増えるため、越える瞬間に警報が鳴りません。

受け取っていた側が作れない理由

この課題には、現金の移動が二重に観測できます。 一つは供託金であり、もう一つは供託に代える保全契約・信託契約の手数料です。 金融機関と信託会社は、この手数料を現に受け取っています。

一方、ポイント基盤ベンダーと決済 SaaS は、この道具を作れません。 「あなたの残高は次の基準日に基準額を超え、供託義務が生じます」という通知は、顧客に自社サービスの利用を控えさせる通知だからです。 ポイント発行量は、そのまま自社の課金指標に直結します。

会計 SaaS が作らない理由は、利益相反ではなく管轄です。 会計 SaaS が計算するのは前受金であり、それは会計基準にもとづく数字です。 法令上の未使用残高は、無償分の区分管理という会計帳簿の外にある実装事実に依存します。 帳簿だけを見ている限り、この数字は出せません。

アイデア 3: rp-declare (EUDI 登録簿へ申告した属性と、実装が実際に要求している属性の差分を突き合わせる検査)

EU デジタルアイデンティティウォレットのクレデンシャルを受け取る側、すなわち依拠当事者（Relying Party）に対して、国の登録簿へ申告した属性リストと、本番の提示要求が実際に求めている属性の差分を機械的に突き合わせるローカル検査です。

— EUDI wallet-relying party registration（Procivis） が引用する eIDAS 2.0 第5b条第2項

Procivis は、この登録を実装上の難所として位置づけています。

ギャップの境界線

登録は静的な書類です。 「これらの属性を、この目的で要求します」と一度申告します。

実装は動きます。 機能追加のたびに提示要求へ属性が足され、A/B テストのたびに要求の分岐が増えます。

申告と実装がずれたとき、それはデータ最小化義務の違反です。 そしてこのずれは、どちらの側からも見えません。 登録簿は実装を知らず、実装は登録簿を読みません。

商用スタックが埋めているのは、この手前です。 Procivis や walt.id は、証明書の発行フローと登録の手続きを一つの流れにまとめています。 登録を済ませるところまでが商品であり、済ませた後に実装がずれることは商品の対象外です。

パターン判定 & Why Now

規制対応型です。 適用日は2026年12月24日であり、3か月半後です。

加盟国の3分の1未満しか準備が整っていないという事実は、二方向に読めます。 需要の立ち上がりが遅れるリスクであると同時に、まだ誰も本番運用の失敗パターンを持っていないという意味でもあります。

受け取っていた側が作れない理由

ウォレット経由のオンボーディングは、1件70〜100ユーロを3〜8ユーロへ落とします。 その差額は、これまで KYC ベンダーが検査1件ごとに受け取っていた金額です。

KYC ベンダーは、この移行を速める道具を作りません。 自社の単価が消える方向の移行だからです。 ウォレット基盤ベンダーは登録の完了までを売っており、登録後の乖離検知は売上に結びつきません。 移行の前と後にそれぞれ売り手がいて、移行の途中を見る者がいません。

Idea 1: eol-cliff — 18点 (Tier 2)

  • タイミング 4: 2026年9月7日という日付が上流のリリース戦略に固定されており、動きません。対象は OpenSSL を含むイメージを配布・運用する全事業者であり、母数は3案で圧倒的に最大です。Node.js 20、Python 3.10 と同型の断崖が半年以内に3回来るため、単発の期限ではなく反復する構造になっています。減点材料: 期限の切迫感が薄い。9月8日に何かが壊れるわけではなく、壊れるのは「次に CVE が出たとき」です。切迫が条件付きである以上、購買は先送りできます。規制のように「この日までに対応しないと罰がある」という圧力を欠くため、5点は付けられません。

  • 収益性 3: 買い手は EU 向けに製品を出荷する事業者と、SBOM の提出を求められる受託開発事業者です。CI で回すチームライセンスの帯は説明できます。減点材料: 開発者向け CLI は無償が既定の領域です。Trivy も Grype も OSS であり、この隣に有償の CLI を置くのは構造的に不利です。個人が月10〜30ドルを払う動機は弱く、法人へ売る導線が別途必要になります。「100人で月10〜20万円」の条件を、単価ではなく販売経路の側で満たせません。
  • 競合優位性 3: 「見逃しと誤検知が同じ欠落から出ている」という説明は、既存製品のどれも正面に置いていません。帰属判定をローカルで完結させる設計は、SBOM を外部へ送りたくない相手にそのまま説得材料になります。減点材料: EOL データベースは商用が先行しています。HeroDevs は1,200万を超えるパッケージバージョンの EOL 状態を既に追跡しており、データの量では勝てません。大手が3か月で真似したら、Snyk や Sonatype が「このコンポーネントは distro がまだ保守している」という帰属表示を1カラム足すだけで、差別化の大半は消えます。技術的な障壁がないため、4点は付けられません。
  • 個人開発適性 4: ローカル CLI として完結し、イメージも SBOM も外部へ送りません。サーバーもデータベースも持たず、生成物は JSON と静的な HTML です。減点材料: EOL データの追随が恒常的な作業として残ります。distro のリリースサイクルは変わり、上流の LTS 指定も変わります。データが古いと出力は静かに誤り、しかも誤りの方向が「安全である」に偏ります。この保守は、機能追加とは別に払い続ける固定費です。

Idea 2: kijunbi-line — 18点 (Tier 2)

  • タイミング 3: 2026年9月30日という基準日は法定であり動きません。年2回、恒久的に反復します。減点材料: 3案で最も母数が小さい。対象は「有償のポイントやクレジットを自社発行し、かつ未使用残高が1,000万円規模へ育った国内事業者」に限られます。この2条件を同時に満たす層は薄く、しかも国内に閉じています。個人開発者が到達できる相手の数として、4点の水準に届きません。
  • 技術的実現可能性 4: 付与・消費・失効のトランザクションログを読み、基準日時点の残高を積み上げる計算そのものは平易です。合算判定も、複数の発行手段を横断して足すだけです。減点材料: 入力データの前提が満たされていないことが多い。無償分と有償分の区別がテーブルに存在しない場合、残高の復元は不可能であり、法令上は最も不利な扱い（全額を対象に算入）になります。この場合ツールが出せるのは「区分できていないので全額が対象です」という警告までであり、正確な数字ではありません。前処理の設計が製品の大半を占めます。
  • 収益性 4: 3案で最も強い軸です。基準額を超えた場合に発生するのは、届出という事務ではなく、基準日未使用残高の2分の1以上の現金の供託です。数千万円規模の資金拘束を事前に予測できることの価値は、買い切り数万円の帯を十分に説明します。金額インパクトが明確に金銭で表現できる、3案で唯一の案です。減点材料: 継続課金の根拠が弱い。一度届出を出して体制を作れば、以後は既存の残高管理に組み込まれます。年2回の基準日ごとに払い続ける理由を、届出後の事業者に対して説明できません。5点は付けられません。
  • 競合優位性 4: 会計 SaaS は前受金を計算し、法令上の未使用残高は計算しません。両者が一致しない理由（無償分の区分表示・区分管理、有効期間の形骸化、最大単価換算）は、いずれも会計帳簿の外にある実装事実に依存します。ポイント基盤ベンダーには、前述の利益相反があります。減点材料: 日本資金決済業協会が、この判定を支援する簡易ツールを公開すれば市場は消えます。同協会は既に詳細な Q&A を無償で公開しており、次の一歩として自然です。優位性が「まだ協会が出していない」という一点に依存するため、5点は付けられません。
  • 個人開発適性 3: 3案で下位の軸です。ローカル CLI として完結し、課金データを外部へ送らない設計は取れます。減点材料: 法令とガイドラインの改正へ追随し続ける必要があり、2026年6月の改正のような変更が今後も来ます。より重いのは責任の所在です。この道具の誤算定は、事業者の無届出という法令違反に直結します。「該当性の判定」ではなく「該当し得る条件の網羅と数値の算定」に出力を限定する設計上の制約を恒久的に守る必要があり、その制約は製品を分かりにくくする方向に働きます。

Idea 3: rp-declare — 17点 (Tier 2)

  • タイミング 4: 2026年12月24日という適用日が規則に書かれています。対象は EU でウォレットのクレデンシャルを受け取る全ての事業者であり、金融・通信・EC・公共と業種を横断します。加盟国の3分の1未満しか準備が整っていないという状況は、参入余地が残っていることの裏返しでもあります。減点材料: その準備の遅れが、需要の立ち上がりを後ろへずらします。登録簿が稼働していない国では、依拠当事者は登録そのものができず、申告と実装の差分を検査する動機も生じません。市場の開始時期を自分で決められないため、5点は付けられません。
  • 技術的実現可能性 3: 3案で最も低い軸です。提示要求から要求属性を抽出し、申告した属性リストと突き合わせる中核処理そのものは平易です。減点材料: 到達すべき仕様の量が多い。ARF、OpenID4VP、ISO/IEC 18013-5、ETSI TS 119 475 を横断して読む必要があり、しかも仕様が確定していません。2週間で作れるのは、限られたクレデンシャル形式に対する属性抽出までです。仕様の追随そのものが製品の実体になる構造であり、実装の巧拙で差がつきません。
  • 収益性 3: 買い手は EU の中小規模の依拠当事者です。KYC 単価が70〜100ユーロから3〜8ユーロへ落ちるという差額の大きさは、この領域に予算があることを示します。減点材料: 買い手への到達経路が個人開発者から遠い。EU 法人の調達は稟議と契約を伴い、日本の個人事業者が売り手として入るには、言語・時差・請求形態の全てが障壁になります。単価は説明できても、販売可能性が説明できません。4点は付けられません。

  • 個人開発適性 3: 検査はローカルで完結し、クレデンシャルそのものを預かりません。減点材料: 仕様更新への追随が、Idea 1 の EOL データ追随より重い。ARF は改訂が続いており、改訂のたびに検査ルールの再確認が発生します。加えて顧客が EU 域内であるため、サポートの応答が時差をまたぎます。個人が副業として抱えるには、応答時間の期待値が合いません。

4. リスク・反証分析 (Fail-safe Analysis)

1. eol-cliff のリスクと対策

最大のリスクは、出力の誤りが「安全である」の方向へ偏ることです。

この道具は「Ubuntu 22.04 のパッケージなので2027年5月まで保守されます」と言います。 その判定を誤ったとき、利用者は保守されていないバイナリを保守されていると信じます。 誤検知は無視されるだけですが、この方向の誤りは害になります。

対策は、判定を三値にすることです。 「保守されている」「保守されていない」に加えて、「判定できない」を明示的に出します。 静的リンクの同定に確信が持てない場合は、必ず第三の値へ倒します。 判定できない件数が多いことは、この道具の弱点ではなく、正直さの指標として提示します。

第二のリスクは、endoflife.date への依存です。

サポート期限のデータを外部の1つのソースへ依存すると、そのデータの誤りや停止が製品の停止に直結します。

対策は、期限データをリポジトリへ同梱し、更新を明示的なコマンドにすることです。 実行時にネットワークへ出ないことは、SBOM を外へ出したくない相手に対する設計上の利点でもあります。 加えて、主要な distro については公式のリリースサイクルを一次ソースとして別途保持し、二重化します。

第三のリスクは、大手が1カラム足すだけで差別化が消えることです。

これは反証というより、確度の高い予測です。 帰属表示は技術的に難しくなく、価値が説明された後であれば追随は容易です。

対策は、追随されない場所へ価値を寄せることです。 候補は時系列です。 「このイメージは、3か月前は全て保守下にあったが、9月7日を境に3件が無保守になった」という履歴は、後から始めた者が遡って作れません。 無償の単発検査で価値を証明し、履歴の保持を有償側へ置きます。

2. kijunbi-line のリスクと対策

最大のリスクは、対象事業者の母数が想定より小さいことです。

有償ポイントを自社発行し、未使用残高が1,000万円へ育っている国内事業者が何社あるのか、公開情報からは分かりません。 届出済みの発行者は登録簿から数えられますが、これから超える事業者の数は数えられません。

対策は、順序を逆にすることです。 残高が1,000万円へ近づいている事業者を探すのではなく、クレジット制の課金を採用しているサービスの一覧から入ります。 その中で、無償ポイントの区分管理を実装していないものが、潜在的な対象です。 Day 1 の検証で、この母数の実在を確認してから実装へ進みます。

第二のリスクは、法令判断の外観です。

「あなたは届出が必要です」という出力は、事実の提示ではなく法令の当てはめです。 個人が提供する道具がこれを行うことには、責任上の問題があります。

対策は、出力を二層に分けることです。 第一層は事実の算定であり、「基準日時点の未使用残高は X 円です。うち無償発行分として区分管理されていない額が Y 円含まれます」まで。 第二層は条文の引用であり、「資金決済法第5条は、基準額を超えた場合に届出を求めています」まで。 両者を接続して結論を出す工程は、利用者と専門家に残します。 この分離は製品を分かりにくくしますが、この領域では譲れません。

第三のリスクは、協会や当局が同等のツールを公開することです。

対策は、公開されても価値が残る部分に寄せることです。 協会が作るとすれば、それは判定の手引きであって、自社の課金 DB からの算定ではありません。 この道具の価値は法令の説明ではなく、雑多なスキーマのトランザクションログから残高を復元する部分にあります。 実装をそちらへ寄せます。

3. rp-declare のリスクと対策

最大のリスクは、市場の開始が自分で決められないことです。

加盟国の登録簿が稼働しなければ、依拠当事者は登録できず、申告と実装の差分という課題自体が発生しません。 3分の1未満という準備状況は、2026年内に需要が立たない可能性を含みます。

対策は、登録簿の稼働を前提としない価値を先に置くことです。 「登録簿へ申告すべき属性リストを、実装から生成する」機能は、登録の前に必要になります。 提示要求のコードから要求属性を抽出し、申告用のリストを作る。 これなら登録簿が動く前から使えます。 差分検査は、その後の拡張として置きます。

第二のリスクは、仕様の非確定です。

ARF は改訂が続いており、検査ルールが仕様の改訂に追随できなければ、出力の信頼性が落ちます。

対策は、検査ルールを仕様バージョンごとに分離し、どの版に対する検査かを出力へ必ず刻むことです。 「ARF 2.x に対する検査結果」と明示すれば、仕様が動いても出力の意味は保たれます。

第三のリスクは、販売経路です。

EU 法人へ日本の個人が売る導線が細いという問題は、製品の設計では解けません。

対策は、直接販売を最初から諦めることです。 無償の OSS として公開し、EU の実装コンサルタントやウォレット基盤ベンダーに使われる側へ回ります。 収益化するなら、彼らへのライセンス提供か、検査ルールの受託開発です。 これは個人開発の理想形ではありませんが、この案の販売経路に合った形です。

5. 参考ロードマップ (14日間MVPの想定仕様)

最有力候補である eol-cliff について、14日間の想定を置きます。 Day 1 は実装ではなく、リスク分析で挙げた前提の検証に充てます。

期間工程内容
Day 1事前検証リスク分析の前提を潰す工程。実装には入らない。(a) 手元とチームのコンテナイメージを10本選び、既存のスキャナ（Trivy / Grype）を当てて、出力に「EOL」「サポート終了」に相当する情報が含まれるかを目視で確認する。(b) 同じイメージの中に、3.0.x の distro パッケージと静的リンク版が同時に存在する例を1件でも見つける。(c) 見つからない場合、この道具が指摘できる差分は実在しない。10本中1本も混在が無いなら着手しない。
Day 2-3出所の同定イメージまたはファイルツリーを走査し、コンポーネントを3種に分類するだけの器を書く。distro パッケージ（dpkg -l / rpm -qa 相当のメタデータ）、言語パッケージ（ロックファイル）、それ以外（静的リンク・ベンダリング）。ここでは期限の判定を一切行わず、分類の取りこぼし率だけを測る。 第三分類が正しく取れるかが、この案の生死を決める。
Day 4-5期限データの同梱endoflife.date のデータと、主要 distro の公式リリースサイクルを取得し、リポジトリへ同梱する。実行時にネットワークへ出ない構成にする。二重化の目的は冗長性ではなく、両者が食い違ったときにそれを検出することにある。食い違いはそのまま「判定できない」へ倒す。
Day 6-8帰属の判定Day 2-3 の分類と Day 4-5 の期限を結合し、コンポーネントごとに「誰が、いつまで」を出す。出力は三値とし、確信が持てないものは必ず「判定できない」へ倒す。OpenSSL 3.0 を含む Ubuntu 22.04 ベースのイメージで、distro パッケージが「Canonical / 2027年5月」、静的リンク版が「該当なし / 2026年9月7日」と分かれて出ることを、この工程の合格条件とする。
Day 9-10断崖カレンダー帰属が切れる日付順にコンポーネントを並べ、90日以内に無保守へ落ちるものを先頭へ出す。出力は JSON と静的な HTML の2形式。CI から実行し、しきい値を超えたら失敗させられる終了コードを持たせる。
Day 11-12履歴の記録実行結果をリポジトリ内の追記型ファイルへ記録し、前回実行との差分を出せるようにする。「先週まで保守下だったが、今週から無保守になった」という遷移を検出する。この時系列が、後発が遡って作れない唯一の資産である。 ここまでを無償の CLI として公開する。
Day 13-14有償化の判断成功指標はインストール数ではなく、「検査の結果、ベースイメージまたはビルド構成を変更した件数」に置く。指摘が構成変更を引き起こさないなら、それは知って終わりの情報であり、有償化へ進まない。

課金設計は、単発の検査と断崖カレンダーを恒久的に無償、複数リポジトリの横断監視と履歴の長期保持を有償とする二層構成を想定します。 無償側は模倣可能です。 有償側が持つのは遷移の記録であり、これは後から始めた者が過去に遡って作れません。 CRA のもとで「いつからパッチが来ない状態だったか」を後から示す必要が生じたとき、この記録がそのまま証跡になります。

6. スクリーニング結果と提案候補 (参考情報)

AIエージェントによる評価・分析結果

  • eol-cliff（総合18点、Tier 2）を最有力候補として選定しました。選定理由は、今回の探索軸「受け取っていた側が構造的に作れない道具」に、最も明快に当てはまるからです。EOL の延命は既に有償の商品として売られており、金が動いていることは疑いようがありません。そして延命ベンダーは、この道具の出力の半分を占める「あなたのビルドは distro がまだ保守しているので契約は不要です」という否定の答えを、自社製品として作れません。加えて、見逃し（167,286件）と誤検知（20,362件）が同じ一つの欠落から出ているという説明は、既存製品のどれも正面に置いていない切り口です。Tier 1 に届かなかった理由は二点です。第一に、切迫感が条件付きであること。9月8日に壊れるものはなく、壊れるのは次の CVE が出たときであり、購買は先送りできます。第二に、大手が帰属表示を1カラム足すだけで差別化の大半が消えること。技術的な参入障壁がありません。
  • kijunbi-line（総合18点、Tier 2）は、金銭インパクトの明瞭さで3案の最上位です。基準額の超過が引き起こすのは事務ではなく、基準日未使用残高の2分の1以上の現金の供託です。数千万円規模の資金拘束を4週間前に予測できることの価値は、他の2案のどれよりも直接的に金額へ換算できます。それでも18点に留まったのは、市場規模と個人開発適性が同時に3点であることによります。対象は国内の、クレジット制課金を採り、かつ残高が1,000万円規模へ育った事業者に限られます。この層へ到達する導線と、法令判断の責任を個人が負う構造が、同時に重石になります。着手するなら、判定ツールとしてではなく、課金 DB のスキーマ監査として設計する場合に限ります。無償分の区分管理が実装されていないことは、残高が育つ前に直すべき設計の問題であり、そこなら法令判断を含みません。
  • rp-declare（総合17点、Tier 2）は、ギャップの説明が3案で最も構造的です。登録簿は実装を知らず、実装は登録簿を読まないため、両者の乖離はどちらの側からも原理的に見えません。見えないものを見せる道具には、常に位置があります。しかし技術的実現可能性3点と収益性3点が重く、17点に留まりました。仕様の量が多く、買い手が遠い。着手するなら、差分検査からではなく、提示要求のコードから申告用の属性リストを生成する機能から入るべきです。登録簿が稼働していない国でも、登録の前段として使えます。市場の開始を他者に握られている案では、他者の準備を待たずに使える機能を先に置く以外にありません。
  • 今回の探索で候補から落とした案が5件あります。
    • EU 包装規則（PPWR）の空隙率検査: 二次記事の多くが「2026年8月12日から空隙率40%以下」と書いており、EC 事業者向けの実測ツールとして有望に見えました。しかし規則本文を確認したところ、この前提は誤りでした。 Regulation (EU) 2025/40 第24条が定める上限は50%であり、適用は2030年1月1日（または実施法の発効から3年後のいずれか遅い方）です。2026年8月12日に始まったのは規則そのものの適用であり、空隙率の数値基準ではありません。期日と数値の両方が誤っていたため、候補から除外しました。 二次情報の要約だけで採点していれば、存在しない期限を根拠にした提案になっていました。
    • EU CRA 第14条の報告義務対応: 2026年9月11日から実際に適用が始まり、ENISA の単一報告プラットフォームが同日稼働します。期日として今回最も鋭い変化でしたが、課題の形が「24時間の報告義務の起動判定と証跡管理」であり、2026-08-25 の cra-clock と実質的に同一です。重複判定フィルタに該当するため、総合13点で却下しました。本レポートでは eol-cliff の需要側の圧力として言及するに留めています。
    • Chrome Manifest V2 拡張の棚卸し: 2026年8月31日にウェブストアから全ての MV2 拡張が削除されました。ただし調査の結果、MV2 の実行そのものは2025年7月に停止済みであり、8月31日はストアの掃除に相当する日付でした。まだ MV2 拡張が動いている環境は Chrome 138 以前に固定された端末に限られ、母数が薄いため、総合12点で却下しました。同型の案は2026-09-02 でも却下しています。
    • Android 開発者確認の9月施行: ブラジル・インドネシア・シンガポール・タイで2026年9月から適用され、F-Droid のリポジトリの約85%が配布不能になると報じられています。課題として切実ですが、パッケージ名と署名鍵の組で判定される構造への対応は、2026-08-30 の signkey-gate と同一です。総合14点で却下しました。
    • 2026年分年末調整の「源泉控除対象親族」対応: 扶養控除等申告書の様式が変わり、特定親族特別控除が月次の源泉徴収税額計算にも影響するようになりました。年の途中の異動が月次へ反映されないと、年末調整で追徴が発生します。ただし買い手は給与計算 SaaS を既に使っており、freee・マネーフォワード・弥生が正面に立つ領域です。除外フィルタの「大手との正面衝突」に該当するため、総合13点で却下しました。
  • 9回連続で Tier 1 に到達していません。 今回の探索軸は、狙った軸で機能しました。競合優位性の平均が3.67点であり、前回の3.0点、前々回の2.7点から明確に改善しています。「受け取っていた側が利益相反で作れない」という条件で絞ったことが、そのまま差別化の説明力になりました。3案とも「なぜ既存プレイヤーが手を出さないか」を、優先度ではなく構造で説明できています。 一方で、今回沈んだのは技術的実現可能性と個人開発適性です。 軸2の平均が3.67点、軸5の平均が3.33点であり、いずれも過去数回より低い水準です。理由は、探索軸の選び方に内在しています。利益相反で先客が作らない領域は、先客が既に持っている知識や資産を、後から個人が独力で揃え直さなければならない領域だからです。 延命ベンダーは EOL データベースを持ち、ポイント基盤ベンダーは課金スキーマの実例を持ち、ウォレットベンダーは仕様の追随体制を持っています。彼らが作らないのは、作れないからではなく、作りたくないからです。作りたくない者と、作れない者の差が、そのまま個人開発者の工数として現れます。 次回の探索軸には、この非対称を埋める条件を足します。すなわち、先客が利益相反で作らず、かつ必要な資産が公開情報として既に揃っている位置を探します。今回の3案でこの条件を満たしていたのは kijunbi-line だけでした。判定に必要な法令・Q&A・様式は全て無償で公開されており、揃え直す資産がありません。一方 eol-cliff は EOL データを、rp-declare は仕様追随を、それぞれ自前で抱える必要がありました。公開情報の完備性を、次回の判定基準に加えます。
